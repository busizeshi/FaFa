# FaFa 日记｜宠物陪伴与照护记录

> **文档用途：** 产品初步设计与功能范围讨论  
> **本次修订：** 2026-10-15  
> **产品暂定定位：** 帮助猫狗主人轻松记录照护、管理日程、找回宠物记忆；AI 用来整理和检索个人资料，不代替兽医。

## 一、产品定位与设计原则

### 1. 目标用户与核心价值

首期面向养猫、养狗的个人主人和共同照护者，先解决三件高频小事：

1. **记得住：** 快速记录喂食、体重、疫苗、驱虫、用药、就医和日常变化。
2. **找得到：** 按宠物、时间、事件和照片内容找回资料。
3. **不漏掉：** 把主人自己设定或确认的照护事项变成清楚、可管理的提醒。

产品不要求用户每天填完整问卷。默认提供一键复用、快捷模板和可选备注；所有自动识别结果都可以查看、修改或取消。

### 2. 产品原则

- **先让记录和提醒可靠，再做复杂 AI。** 没有持续、可信的宠物资料，AI 对话和报告就没有稳定依据。
- **数据归用户管理。** AI 回答应指出引用了哪条记录及其日期；资料不全时明确说不知道，不补造宠物信息。
- **AI 做辅助，不做诊断。** 可以整理就医资料、解释一般养护知识、提示主人联系兽医；不判断疾病、不处方、不建议自行停药或改剂量。
- **记录事实与推测分开。** “实际称量 120 克”“主人估计喝得少”“AI 从包装照片识别，待确认”不能混成同一种确定数据。
- **隐私默认收紧。** 宠物照片、就诊材料和家庭照护记录默认仅自己可见；发布和交给 AI 处理都应让用户知道发生了什么。
- **减少打扰。** 提醒由用户设置，可完成、延期、跳过或关闭；不把不可靠的“异常推送”包装成健康结论。
- **首期聚焦猫狗。** 其他宠物种类在数据字段和营养规则经过准备后再评估。

### 3. 用户最短路径

主路径尽量保持在三步内：

- 添加宠物：填写基本信息 → 保存。
- 记录事件：选择快捷记录 → 填数量或时间 → 保存。
- 处理提醒：查看事项 → 完成、延期或调整。

注册、授权通知、上传照片等非必要权限不要挤在首次启动流程里；在用户第一次使用相应功能时再解释并请求权限。

## 二、客户端风格与信息架构

### 1. 视觉与交互

保留温柔、自然、浅色和可爱感，但把“苹果圆角、液态玻璃”作为视觉参考，不要求跨平台照搬系统效果。优先保证：

- 字体清楚、字号可读、文字与背景对比足够；可爱字体不能影响长文本和数字识读。
- 首页突出下一件要做的事和快捷记录，不以持续动画或 3D 模型占据主要操作空间。
- 动效可关闭或降低；常用操作不依赖动画才能理解。
- Android 与 iOS 的页面结构保持一致，遵循各自平台的基础交互习惯。

### 2. 建议的一级导航

1. **首页：** 今日照护事项、最近动态、快速记录。
2. **记录：** 宠物时间线、健康与日常记录、统计。
3. **相册：** 照片视频、标签和搜索。
4. **AI 助手：** 基于本人已保存资料的问答与整理。
5. **我的：** 个人资料、家庭成员、提醒偏好、隐私和账号设置。

“宠物圈子”建议作为后续单独入口，在具备内容审核与举报处理能力后再开放，不要在首版首页混入随机内容流。

## 三、功能构思

### 1. 账号、个人资料与家庭协作

#### 首期

- 邮箱和密码注册、登录、找回密码；注册邮箱验证方式需确定可在中国境内稳定使用的邮件服务。
- 个人资料只保留昵称、头像、时区和提醒偏好等直接用于产品的字段。
- 删除原构想中的“用户性别、年龄、INTP 类型”必填项。它们不是完成宠物记录所必需的信息；如未来确实有具体用途，再说明用途并设为可选。
- 提供修改密码、退出登录、账号注销和个人资料删除入口。

#### 后续：共同照护

- 允许主人邀请家庭成员共同查看和维护宠物档案。
- 明确“所有者、可编辑照护者、只读照护者”等权限；主人可随时撤销。
- 变更记录显示操作者和时间，避免多人协作时不知道是谁改了喂食或提醒。
- 可生成用户主动选择内容的临时照护清单，供寄养或亲友照看时使用。默认不包含家庭住址、账号信息等无关内容。

### 2. 宠物档案

- 一个账号可以添加多只宠物，并随时切换当前宠物。
- 基本字段：昵称、猫/狗、性别（可选）、生日或大致年龄（注明估算）、到家日期、品种（可选）、绝育状态（可选）、照片和备注。
- 体重不要只存成档案里的一个数值，应作为带日期的记录保存，并在档案中展示最近一次数据。
- 允许信息未知，不强迫用户编造生日、品种或历史数据。
- 删除宠物前说明关联照片、记录和共享关系会如何处理；可优先提供“已离世/已归档”状态，保留主人愿意留下的资料。

**调整原构想：** 首版不要求用户拍摄正面、侧面、背面三视图，也不承诺据此自动生成准确 3D 宠物。三张普通照片无法保证模型外观、毛发和动作准确，采集成本也高。先用用户选择的头像或照片；Unity 3D 形象作为后续装饰功能，必须允许跳过，不能影响记录和提醒。

### 3. 首页与照护概览

首页建议由以下卡片组成：

- **待办事项：** 最近的疫苗、驱虫、复诊、用药或主人自定义提醒，标出来源和日期。
- **快速记录：** 喂食、饮水、体重、排便观察、用药、疫苗、洗护、就医和随手记。
- **最近动态：** 最近添加的记录和照片。
- **趋势入口：** 体重、喂食量等确有连续记录的指标，展示时间范围和原始数据点。
- **AI 今日整理（可关闭）：** 只总结已有记录，例如“本周记录了三次体重”；不能把一次缺记录说成“宠物异常”。

不要默认生成没有数据依据的“健康异常”“今日喂食不足”通知。首页的 3D 模型可以作为后续可选装饰，首版用宠物照片和轻量互动即可。

### 4. 日常与健康记录

记录类型建议包括：

- **饮食与饮水：** 食物、时间、实际份量或大致情况、是否吃完；饮水可记录实测量，也可选“少/一般/多/不清楚”。
- **体重与身体状况：** 体重、日期、称重来源；身体状况评分作为可选自评参考，说明评分方法。
- **预防照护：** 疫苗、驱虫、洗澡、梳毛、剪指甲、清洁等。
- **用药：** 药品名称、兽医处方或主人填写的用法、开始和结束日期、执行记录；AI 不推算剂量。
- **就医：** 就诊日期、机构/医生（可选）、主人记录的主诉、检查资料、诊断与处方原件、复诊安排及费用（可选）。
- **日常观察：** 精神、食欲、排便、皮肤毛发等，使用“主人观察”而非“AI 诊断”标签。
- **纪念与成长：** 到家、生日、训练进步、旅行和重要照片等。

支持文字备注和照片/文件附件。需要 AI 从自然语言中提取事件时，先显示待保存的结构化预览（宠物、日期、事件类型、数量等），用户确认后再写入；置信度低的字段要求补充，不静默入库。所有记录可编辑、删除、标记为估算，并能按宠物和时间筛选。

就诊记录是主人保存的资料，不等于由 FaFa 日记出具的电子病历或诊断意见。

### 5. 喂食计划与饮食记录

#### 喂食计划

- 支持主人按宠物、食物和喂食时段建立计划；计划显示份量、单位和适用日期。
- 初步计算可参考 WSAVA 营养评估资料中的能量需求起始估算，并明确展示公式、输入项、来源、版本和“仅供参考”说明。WSAVA 提供健康犬猫的能量需求起点和营养评估工具；计算时应选用适合目标宠物和场景的资料，不要把住院喂养指南中的公式直接当成所有健康宠物的通用食谱。
- 计划至少考虑猫狗种类、体重、年龄阶段、绝育情况、活动水平、身体状况和用户选择的目标；缺项时降低精度并提示补充。
- 能量起始估算不是完整食谱。疾病、怀孕/哺乳、幼年、老年、肥胖管理或特殊处方粮等情况应提示由兽医确认。
- **移除“AI 对计算结果进行一定程度修改”。** AI 不应在后台改写数值。若提供调整，只能根据明确规则展示可解释的建议区间，由主人确认；涉及疾病或治疗饮食时转介兽医。

#### 食谱卡与食品档案

- 用户可维护常喂食品/食谱卡：名称、种类、每份重量、包装标注的能量和营养成分、开始使用日期、备注。
- 拍摄包装后，AI 可以预填可识别的字段，但必须让用户核对标签、单位和数值；不把包装照片识别结果直接当作准确营养数据库。
- 记录食物来源和原始包装照片，便于日后纠错。暂不宣称能从普通包装照片还原完整配方或判断食品是否适合某只宠物。

#### 喂食与饮水记录

- 提供“按上次记录”“按计划记录”快捷入口，可修改实际食物、份量和完成情况。
- 喂食计划与实际喂食分开保存，不将“计划投喂量”误当成“宠物实际吃下的量”。
- 饮水记录允许快速选择主观程度，也允许填写实测量；报表明确区分两种来源，不把主观选项换算成毫升。
- 不连接自动喂食器或饮水设备，除非未来另行确定设备与接口方案。

### 6. 提醒与日历

- 用户可为疫苗、驱虫、复诊、用药、洗护、喂食和自定义事件设置一次性或重复提醒。
- 每条提醒显示来源：主人创建、根据主人已保存的日期生成，或 AI 建议待确认。
- 用户可以完成、稍后提醒、跳过、暂停、修改周期或关闭。
- 首版使用客户端系统本地通知和应用内待办，减少对尚未选定的服务端推送服务的依赖；Android/iOS 通知权限在用户创建提醒时再请求。
- 时区变化、免打扰时间、通知失败和重复提醒都需要有清楚的设置与状态。

### 7. 宠物相册与素材搜索

#### 素材管理

- 上传照片和视频，可手动关联宠物、日期和自定义标签。
- 默认私密；用户发布到圈子或交给 AI 处理前明确展示可见范围和处理用途。
- 支持按宠物、日期、照片/视频、标签、事件类型筛选。
- 允许用户改正误关联的宠物和标签；删除素材时同步清理对象存储文件、业务元数据和对应向量索引。

#### AI 搜索

- 在结构化筛选基础上，增加自然语言检索，例如“去年冬天雪球在窗边睡觉的照片”。
- 可使用文档中已选定的阿里云多模态 Embedding 与 Qdrant 做图片/文本语义检索；MySQL 保留权威业务记录和素材元数据。
- 检索结果应标明匹配依据，允许用户反馈“不相关”。
- **不要用宠物三视图自动判定素材里的宠物身份。** 多模态语义相似度适合帮助找内容，不等于经过验证的个体身份识别。首期由用户选择宠物；未来若提供识别，只能给候选并要求主人确认，不应自动写入档案。

### 8. 宠物 AI 助手

AI 的产品职责限定为“基于个人资料的记录助手和一般养护知识助手”。

#### 可以做

- 查询本人已保存的记录：“上次驱虫是什么时候？”“最近一个月体重怎么变化？”
- 从文字中提取记录字段，生成确认预览后保存。
- 解释一般性的日常照护知识，并区分通用资料与用户自己的记录。
- 汇总周报/月报、整理就医资料目录、按关键词或语义找照片。
- 用卡片、时间线、指标摘要等结构展示结果，不局限于长段文字。

#### 必须做好的边界

- 个人记录类回答显示宠物名称、记录日期和来源；没有记录时直接说明“资料里没有”。
- 不诊断疾病、不替代兽医检查、不推荐处方药或自行给药剂量；出现急重症迹象时建议尽快联系动物诊疗机构。
- 用户上传的检查报告和照片仅用于用户要求的整理或解读，不把模型输出当作正式诊断。
- 写入、修改、删除记录或创建提醒前展示动作和内容并取得用户确认；只读查询不应擅自修改资料。
- 对话和图片只发送完成当前请求所需的最少内容；明确 AI 服务商、处理用途和保存规则，提供清理历史记录的入口。
- 回答给出“通用知识”或“根据你的记录整理”的标识，不能混淆二者。

文档中提到的 Harness、LangGraph 和内部工具可用于约束 Agent 的步骤和权限。工具只提供必要的查询、草稿和经用户确认后的写入操作，不给 Agent 无限制数据库访问权限。MCP 若实际采用，应先限定为内部受控工具接口，不代表必须接入境外服务。

### 9. 周报、月报与分享内容

- 周报/月报优先从真实记录生成：本期记录数量、体重变化、已完成提醒、重要照片和主人备注。
- AI 可以把资料整理成摘要，但展示引用的记录，允许主人编辑后保存或分享。
- 分享前由用户逐项选择照片、文字和资料范围；默认不公开。
- 首版用模板卡片呈现文字、数据和用户照片。
- **暂缓自动生成“照片翻转视频”或 AI 视频。** 当前技术选型没有明确的视频生成服务；如以后加入，需要确认境内模型服务能力、成本、数据处理规则，并按适用规则处理生成内容标识。

### 10. 宠物圈子与社区

建议列为后续功能，而不是首版必做。

#### 功能方向

- 用户发布宠物照片、日常、成长记录和经验。
- 支持公开、仅关注者、仅家庭成员、仅自己等可见范围。
- 用户可关注其他宠物主、点赞、评论、收藏、举报和屏蔽。
- 首页默认展示关注内容或按时间排序的内容；第一版不做“完全随机”，也不做难以解释的个性化推荐。
- 作者可以决定是否开放某个相册、记录或帖子，并可随时取消授权。

#### 开放前置条件

- 具备违规内容审核、用户举报、屏蔽、投诉受理、处置记录和申诉处理能力。
- 明确平台规则、内容可见范围、转载/分享边界及账号处罚流程。
- 若以后采用个性化算法推荐，评估告知、关闭推荐和用户标签管理等要求；若服务具有舆论属性或社会动员能力，另行评估算法备案和安全评估要求。
- 不公开家庭住址、实时位置或带有位置元数据的原始照片；分享前提醒用户检查隐私。

社区需要持续运营与审核，不应只按开发工作量评估。早期可先做宠物家庭协作和可控分享，避免一开始承担公开 UGC 平台的运营成本。

## 四、功能优先级

### P0｜可用的第一版

- 邮箱账号和最小化个人资料。
- 多宠物档案、宠物切换、归档。
- 喂食、饮水、体重、预防照护、就医和日常记录。
- 提醒与客户端本地通知。
- 首页待办、最近记录和快捷记录。
- 相册上传、手动标签、普通筛选。
- 隐私说明、记录更正/删除、账号注销。
- 核心流程先做到可靠、少步骤；没有 AI 也能完整使用。

### P1｜形成 FaFa 的 AI 特色

- AI 自然语言转记录（用户确认后入库）。
- 基于个人资料的只读问答和周/月报。
- 多模态素材语义搜索。
- 食品标签字段预填、用户核对后保存。
- 家庭成员协作和照护清单。

### P2｜验证运营与能力后再做

- 宠物圈子与公开内容流。
- Unity 3D 形象、个性化互动。
- AI 图片/视频生成。
- 基于长期数据的个性化营养调整或机器学习。
- 智能设备接入、线上兽医服务、商品交易或附近服务推荐。

P2 中的线上诊疗、交易、地图/附近服务和设备接入都需要新的业务合作、服务商或合规准备；不属于现有技术列表可以直接推出的能力。暂不承诺上线时间。

## 五、技术与实施建议（限于当前已列技术）

### 1. 现有技术栈的分阶段使用

目前列出的 Nacos、Spring Boot、MySQL、Redis、RocketMQ、Qdrant、Dubbo、Sa-Token、Prometheus、FastAPI、LangChain、LangGraph、阿里云百炼和 OSS 足以支撑产品设想，但不建议第一阶段全部启用。

- 先以 Java 21 / Spring Boot 和 MySQL 完成用户、宠物、记录、提醒等核心闭环。
- Redis 用于确有需要的缓存或短期状态；RocketMQ 用于实际出现的异步任务。
- 多模态检索上线时再引入 Qdrant；向量是搜索辅助索引，不是权威业务记录。
- Nacos、Dubbo、Prometheus 和微服务拆分按实际部署、流量和团队维护能力逐步使用。一个人或小团队同时维护多个服务会明显增加联调和运维负担。
- Python / FastAPI / LangChain / LangGraph 仅承载需要独立迭代的 AI 流程；业务数据仍由 Java 服务按权限提供。
- Android 客户端使用 Kotlin 和 AndroidX；iOS 客户端使用 Swift 和 UIKit；两端按对应阶段实现，保持核心流程一致。
- Unity 仅用于后续可选 3D 形象和互动，不应成为首发依赖。

以上是对现有技术的分期建议，没有要求新增其他开发框架或云平台。

### 2. 阿里云模型与素材存储

- AI 使用阿里云千问系列的对话、文本/多模态向量和重排序能力；按百炼当前官方 API 文档确认目标模型、调用区域、输入限制、价格、可用性和服务条款。境内部署选择对应境内地域和 API 入口，不接入未确认可在境内稳定使用的海外模型或存储服务，也不假设模型名称、能力和配额永久不变。
- 阿里云多模态 Embedding 文档目前列出文本、图像和视频输入能力，适合验证素材检索；这并不证明模型能识别同一只宠物的身份。
- OSS 素材默认私有访问；访问图片时使用受控的临时访问方式，不把桶设为公开。
- 为上传、模型调用和向量索引设置文件大小、格式、失败重试和删除流程；用户删图后同步删除 OSS 文件和 Qdrant 向量。

### 3. 开发与原型工具

- 客户端和服务端开发继续使用 Codex 辅助；代码、接口和安全边界仍由开发者检查与确认。
- UI 原型继续使用 PenPot；可通过现有 MCP 操作原型，先确定首页、快速记录、宠物切换和提醒等核心页面，再扩展视觉细节。

### 4. 中国境内上线约束

- 面向境内用户提供互联网信息服务的 APP，按工信部要求完成相应 APP 备案后再开展服务；备案编号按要求展示。
- 邮箱验证码需要选择境内可稳定送达的邮件服务；目前设计未列出邮件服务商，这是一项上线前需明确的运营依赖。
- 使用生成式 AI 能力前，确认实际服务模式、模型服务商提供的备案信息、用户协议、数据处理范围和适用管理要求。不能仅因为调用的是第三方模型，就默认应用端的责任全部由模型服务商承担。
- 对 AI 生成的图片、视频或其他适用内容，按《人工智能生成合成内容标识办法》及配套标准落实显式/隐式标识；生成结果在用户发布前也应有审核与举报入口。
- 遵循个人信息最小必要原则。收集前说明目的、方式、范围和保存期限；提供访问、更正、删除和注销入口。宠物照片、就医材料可能包含主人身份、家庭环境或位置线索，应按最小范围处理，未经清晰告知和授权，不把用户资料用于模型训练或公开展示。
- 社区内容发布和个性化推荐分别带来内容治理与算法管理义务，应在功能上线前按实际服务形态评估；社区开放之前先准备审核、举报、投诉及处置流程。
- AI 不提供动物疾病诊断、处方和治疗服务。农业农村部规定动物诊疗活动由符合规定的动物诊疗机构和执业兽医开展；如未来接入线上兽医服务，应由合规动物诊疗机构及其备案执业兽医提供，另行设计合作和责任边界。

## 六、对原构想的重点修改

| 原构想 | 修订建议 | 原因 |
|---|---|---|
| 收集用户性别、年龄、INTP 类型 | 删除必填项，仅保留产品必要资料 | 与宠物照护核心流程无关，增加数据收集和维护负担 |
| 首次注册后必须立即填写完整宠物档案 | 先填昵称和猫狗类型，其余可跳过、以后补全 | 降低首次使用门槛 |
| 三视图生成 3D 模型并识别照片中的宠物 | 首版用宠物头像；素材由用户关联，模型只给候选 | 三视图采集和自动个体识别可靠性不足 |
| AI 修改公式算出的喂食计划 | 规则计算透明展示，AI 只辅助解释；主人确认后保存 | 避免无依据改动喂食数值和健康风险 |
| 自动推送“检查到的异常” | 改为对已记录事实的中性汇总与提醒 | 现有模型能力不足以承担健康监测或诊断 |
| 主观饮水程度折算成精确饮水量 | 主观观察和实测量分别保存 | 避免把估计值伪装成测量数据 |
| AI 从包装照片准确得出全部营养数据 | AI 预填，主人核对标签和单位 | OCR/视觉识别可能错读，包装也未必提供完整配方 |
| AI 可直接写数据库、修改资料 | 先预览，确认后写入；关键操作记录来源 | 防止误识别改变健康记录或提醒 |
| AI 自动生成翻转视频 | 暂缓，首版使用模板化图文摘要 | 当前未选定视频生成能力，内容标识也需处理 |
| 宠物圈内容完全随机 | 先按关注关系或时间排序；具备审核能力后开放 | 随机流缺少用户控制和相关性，也增加治理成本 |
| 一开始完成微服务全家桶 | 先做核心闭环，再按需要启用现有组件 | 控制一个人/小团队的部署和运维复杂度 |
