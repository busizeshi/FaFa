# 每日状态打卡设计方案

> 状态：需求分析定稿，待评审 → 待开发
> 关联文档：[产品功能设计.md](./产品功能设计.md)、[功能需求重新设计.md](./功能需求重新设计.md)

## 一、背景与问题

现有日常记录（喂食/体重/饮水/排便）把宠物主当成了**计量员**：

- `water_record` 要求填毫升数——但主人无法知道宠物实际喝了多少，只能观察「水碗见底比平时快」
- `feed_record` 记「我喂了多少」，没记「它吃了多少」
- 精确计量导致记录成本高 → 用户一周后放弃 → 数据稀疏 → 趋势分析无米下锅 → AI 闭环失效

**产品闭环「记录 → 数据 → AI 理解 → 用户获益」的转速，完全取决于日活记录成本。**

## 二、核心设计公理

记录必须拆成三类，**不得混放**（water_record 的错误就是把第 3 类的要求放进了第 1 类的位置）：

| 类别 | 定义 | 例子 | 形态 |
|------|------|------|------|
| **状态观察** | 它表现如何 | 食欲、精神、饮水程度、便便质量 | 主观量表，一天一格，upsert |
| **照护动作** | 我做了什么 | 喂食、换水、给药、驱虫 | 事件流，几点几分发生 |
| **周期测量** | 精确数值 | 体重、克数、毫升 | 独立流程 + 温和提醒，**绝不进每日打卡** |

铁律：**任何每日记录 ≤2 次点击完成。**

## 三、维度评估结论

按可观察性 / 临床价值 / 记录成本 / 纵向价值四把尺子评估：

### v1 必备（六项）

| 维度 | 形态 | 选项 | 核心价值 |
|------|------|------|---------|
| 食欲 | 量表 | 很好 / 正常 / 下降 / 拒食 | 几乎所有疾病的共同首发信号；猫拒食 >2 天有肝脂沉积风险 |
| 精神/活动 | 量表 | 活跃 / 正常 / 低迷 | 猫生病天性躲藏不动；措辞必须是「比平时」而非绝对档位 |
| 饮水程度 | 量表 | 正常 / 偏多 / 偏少 / **没注意** | 猫多饮多尿 = 肾病/糖尿病/甲亢三大最早期信号（10 岁以上猫 30%+ 有慢性肾病）；必须有「没注意」逃生口 |
| 排便 | 量表 | 正常 / 偏软 / 腹泻 / 便秘 / 没看到 | 特权数据（每天铲屎/捡屎一目了然）；现有 excretion_record 结构可平移 |
| 呕吐 | 症状开关 | 无（默认）/ 一次 / 多次 | 拒食+呕吐 = 急症组合信号 |
| 排尿 | 症状开关 | 正常 / 异常 / 没看到 | 公猫排尿困难是按小时计的急症（尿道阻塞）；全产品唯一可能「救命」的场景 |

### 明确不做 / 延后

| 项 | 结论 | 理由 |
|----|------|------|
| 每日体重 | **不做** | 家庭无宠物秤，日测制造「没称」噪音；保留独立流程 + 每周提醒（猫建议抱人上秤法） |
| 换水 | 不做独立功能 | 卫生代理指标，几乎不改变任何决策；归入自由备注 |
| 情绪/行为分类 | v2 | 认知负担高，先做「行为异常」开关 + 自由备注 |
| 咳嗽/喷嚏/跛行/瘙痒 | v2 症状开关组 | 默认「无」，出现才点 |
| 强制精确数值 | 永不 | 克数/ml 一律可选 |

## 四、v1 打卡页形态

**三个量表**（食欲/精神/饮水）+ **排便量表** + **两个症状开关**（呕吐、排尿）+ **一键正常** + 自由备注。

### 习惯养成三原则

1. **「今天一切正常」一键完成**——95% 的日子是平淡的，平淡日成本必须最低，做不到这点其他都空谈
2. **漏记不惩罚**——漏一天标「未记录」，绝不做愧疚式 UI（打卡产品死于第三周的头号原因）
3. **晚上九点问一次**——观察类数据的采集时点是「一天结束时」，而非随时提醒

### 数据密度目标

- 计量模式：7 日留存后记录率大概率 <20%，时间序列千疮百孔
- 量表模式：目标 60%+ 天数覆盖；**连续 14 天即可建立个体基线**，之后所有偏离检测才有个人化参照，而非教科书阈值

## 五、物种差异（配置，非两套代码）

| | 猫默认面 | 狗默认面 |
|--|---------|---------|
| 维度 | 食欲、精神、饮水（加权提示多饮多尿）、呕吐、排便、排尿 | 食欲、精神、排便、饮水、呕吐（排尿降权） |
| 依据 | 猫肾病/糖尿病早期信号靠多饮多尿捕捉；猫砂盆排尿行为完全可见 | 狗捡屎是每日特权数据；排尿观察难 |

## 六、数据模型（推荐）

**新增 `daily_status` 宽表**：一行 = 一宠物一天全维度，upsert 语义（当天可改）。

- 每维度一列（tinyint 枚举）+ remark 自由备注 + status_date + pet_id + user_id，唯一键 `(pet_id, status_date)`
- **喂食保留为动作日志**（feed_record 加可选「吃完程度」字段），精确克数可选
- **water_record 废弃**并入 daily_status 饮水维度（ml 变可选字段），接口标记 deprecated
- 对 AI 侧是完美形态：Python 查趋势 = 单表单列，chat_agent 上下文注入干净

备选：改造现有各表（改动分散，AI 侧查询仍要跨四张表拼「某宠物某天全貌」，不推荐）。

## 七、解锁的能力路线

| 阶段 | 能力 | 依赖 |
|------|------|------|
| 打卡上线 | 时间轴每天有状态色块——「它的一生」从流水账变生命体征曲线 | daily_status 表 |
| +1 迭代 | **规则预警引擎**（纯 Java 规则，不需要 AI）：<br>· 拒食 + 呕吐 → 红色：建议尽快就医<br>· 连续 2 天食欲下降 + 精神低迷 → 黄色提醒<br>· 猫饮水偏多 ≥3 天 → 提示查肾指标/血糖<br>· 腹泻 ≥2 天 / 呕吐多次 → 黄色提醒 | 状态表 + 规则表 |
| AI Agent 落地 | **就诊摘要一键生成**：近 7 天症状时间线 + 基线对比（「平时食欲正常，周三起下降伴呕吐两次」）——解决主人到院想不起哪天开始的痛点 | chat_service |
| 长期 | 基线自学习、照片估体重（VL 可行）、周报叙事化（「本周食欲稳定，周三有点蔫但周四恢复了」） | 数据积累 |

## 八、与前四个维度的对应（PU/PD 交叉验证）

食欲 / 饮水 / 精神 / 排泄正是兽医问诊时依赖的 owner-reported 临床观察四件套。**这套打卡表不是随口设计，它天然是一张「居家临床观察日志」。**
