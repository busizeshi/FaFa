# 宠物 App 产品需求与交互原型设计（PRD v2.0）

> **产品暂定名：伴宠 / PawLife（待品牌检索）**  
> **版本：v2.0 · 2026-10-24**  
> **目标：先完成面向中国大陆猫狗宠主、家庭/亲友照护者的低成本验证版本，之后扩展 AI 深度分析、智能设备、知识服务与社区。**  
> **本文定位：可供产品、UI/UX、Flutter、Java 后端与 AI 工程师协同使用的需求基线，不是已完成的高保真视觉稿。**

## 0. 阅读说明与来源可信度

本方案以用户提供的《原型设计.md》为**现有需求基线**，对账号与登录、宠物档案、首页、相册、饮食与生活记录、提醒、亲友照护、AI Chat/Agent、报告、社区进行了保留、重组与深化。

- **[原案]**：来自现有原型的既定方向，不表示已完成市场验证。
- **[调研]**：来自公开行业报告、竞品官方资料、专业兽医指南或监管部门文件；来源见末尾参考文献。
- **[方案]**：本 PRD 的产品推演、界面结构或技术建议，需要通过用户测试与开发验证。
- **[假设]**：尚未证明的用户需求、商业结论或 AI 质量假设，不以行业数据包装为事实。

**边界**：重点设计猫/狗宠主与照护者的日常管理产品。本文不把 AI 视为兽医，不提供确诊、处方或自动调整药物剂量能力；对于疫苗、药物、慢性病和特殊膳食，实际方案由具备资质的兽医确定。

## 1. 市场与需求：哪些痛点值得解决？

### 1.1 基础证据

| 11pets 官方产品 [R05] | 疫苗、驱虫、病历、药物、体重、洗护、日历同步、导出 | 体系化记录是成熟需求，差异化来自低负担与智能化 | 具体免费/付费功能可能变更 |
| PETKIT 官方产品与 2026 AI 健康介绍 [R06][R07] | 智能猫砂盆/喂食器/饮水机连续收集行为数据，AI 用趋势汇总与解释 | “建立个体基线→发现变化→解释上下文”的方向值得借鉴 | 部分 AI 能力仍处于计划上线/逐步发布阶段 |

### 1.3 用户分层 / JTBD

1. **第一次养宠者**：希望知道该做什么，不想读长篇专业说明；核心是新手计划、疫苗/驱虫日历、可靠知识解释。
2. **双职工/同居家庭**：希望一眼确认“喂过了吗、谁带出去了吗”；核心是共享任务、防重复执行、通知同步。
3. **多宠家庭**：不希望宠物 A 的数据记到 B；核心是宠物切换、相册归属校对、事件关联多宠。
4. **精细化健康管理者**：持续追踪体重、BCS、饮食结构、药物、便便和症状；核心是趋势与就医摘要。
5. **临时照护者/寄养者**：接手时迅速理解禁忌和日程；核心是限时授权与交接卡。
6. **成长记录爱好者**：喜欢拍照但不愿每张单独填标题；核心是自动整理与回忆生成。

**首发主目标用户**：城市猫狗主人中的“需要多人协作”和“愿意偶尔主动记录”的用户。不要把“每天记录十余项”当作默认用户行为。

## 2. 竞品拆解：模仿哪些机制，避开哪些陷阱？

| 产品 | 已公开功能优势 | 可借鉴的设计 | 我们的差异化切口 |
|---|---|---|---|
| **11pets** [R05] | 医疗史、药物、疫苗、洗护、行为、测量曲线、费用、分享与导出 | 完整的“事件→提醒→历史”结构 | 让一次记录自然触发后续提醒和 AI 汇总；更快操作 |
| **DogLog** [R04] | Pack 家庭协作、自定义事件、通知、统计 | 明确是谁记录、何时完成 | 细粒度权限、照护交接、冲突处理、任务认领 |
| **PetDesk** [R03] | 诊所预约、电子记录、补药、提醒 | 医疗数据的可携带性、可分享性 | 不依赖诊所接入，支持拍照/OCR 导入与人工校对 |
| **PETKIT/小佩** [R06][R07] | 智能硬件与自动化饮水/进食/如厕数据 | 连续数据、个体健康基线 | 不绑定任何设备，先支持手动+半自动记录，再考虑硬件接入 |
| **Tractive** [R09] | 活动、睡眠等健康趋势提醒 | 不以单个数值作判断，重点看偏离基线 | 解释数据来源、缺失程度、提醒理由及下一步建议 |
| **宠物家** [R10] | 洗护、线下服务与商品 | 线下服务的预约/履历联动 | 不在初期投入交易履约与门店运营 |
| **宠胖胖** [R11] | 宠物指南、购物与线下服务 | 养宠知识可以连接行动场景 | 不做通用内容流，做围绕宠物个人数据的“可执行知识” |

**竞品共同问题机会（综合推断，待访谈验证）**：单项功能并不稀缺，但跨越“记录、多人确认、解释、提醒、回看”的无缝体验仍存在开发空间。不要将“行业空白”“首创”等未查证词汇用于商业宣传。

## 3. 产品定位、北极星指标、差异化优势

- **定位句**：帮每个家庭轻松照顾好每一只宠物，自动留下可靠的健康与成长记忆。
- **北极星指标**：每周活跃照护家庭数（WAH：7 天内至少发生 1 次有效事件记录、提醒完成、健康档案查看/分享或照护交接的独立家庭数）。
- **辅助指标**：首日建档完成率、首个有效记录率、7/30 日留存、每周记录家庭占比、多人照护邀请接受率、提醒完成率、AI 纠错率、成功分享就医摘要数。
- **产品护城河方向**：高质量长期个人历史、家庭合作网络、用户可验证的结构化记录、可信 AI 工作流，而不是单纯依赖大模型聊天。

### 3.1 五个差异化产品提案

**A. 家庭照护驾驶舱（先做）**：所有参与照护者共享同一状态；喂食/服药可设置禁止重复确认、执行人、备注与操作日志。跨人同步是体验中心。

**B. 宠物生活知识图谱（逐步建立）**：把一次事件关联到食品、药物、宠物、症状、医院、照片与费用，从而回答“最近换粮之后有什么变化？”；先用关系表与时间关联，不必一开始上图数据库。

**C. 个人基线与“变化雷达”（1.2 版）**：分析当前 7 日与个人过去 28 日模式的差异，显示“发生了什么、有哪些相伴变化、需要补哪些信息”，而不是直接判病。

**D. 自然语言一键照护（MVP 有限版）**：如“团子刚吃了 35g 猫粮，顺便记一下”，AI 解析后弹出待确认卡片，一次确认写入正式记录，支持撤销。

**E. 回忆与健康双时间轴（1.1 版）**：用户看得到生活故事，也能把照片关联到体重、医院、饮食变化；隐私回忆永不默认向社区发布。

### 4.1 依赖顺序

```text
账号与隐私 ─→ 家庭空间 ─→ 宠物主数据
                               ├─→ 结构化事件 ─→ 提醒/任务 ─→ 趋势/报告
                               ├─→ 食品卡/喂食计划 ─→ 喂食事件
                               ├─→ 素材/病历附件 ─→ 检索/回忆
                               └─→ 权限模型 ─→ 亲友照护

结构化事件 + 有来源的知识 ─→ AI 查询/解释 ─→ AI 草稿 ─→ 用户确认执行
```

## 6. 全局 UX 设计系统

| 维度 | 明确建议 |
|---|---|
| 视觉语气 | 温暖、干净、轻松；不是玩具风，也不是医院管理系统 |
| 色彩 | 中性暖白底色、自然绿色/青蓝表达“已完成”、柔和琥珀表达“需要关注”；不要全屏红色制造健康焦虑 |
| 字体 | 标题 20–24sp，分组 16–18sp，正文 14–16sp，说明文字 12–13sp（最终按平台系统字体与动态字号调整） |
| 卡片 | 8pt 网格；卡片圆角 12–16；列表优先，指标与操作采用轻卡片，不滥用磨砂玻璃 |
| 信息密度 | 首屏只保留当前最相关 1–3 个行动；高级指标折叠在详情页 |
| 触控与无障碍 | 触控目标至少符合对应平台规范；文字可放大；图表有文本结论；所有状态不仅依靠颜色 |
| 交互 | 一键完成、长按多选、左右滑动切换内容可作为辅助；关键操作始终提供可见按钮，避免隐藏式唯一入口 |
| 反馈 | 即时乐观更新但失败可回滚；保存成功/冲突/离线/权限不足都有明确反馈 |
| 信息层级 | **宠物是谁 → 今天发生了什么 → 需要做什么 → 进一步分析** |
| 通知策略 | 严重性分层、可静默、自定义时段、提醒合并；不做无意义的强制提醒和宠物健康“评分焦虑” |

### 6.1 三种卡片模板

1. **状态卡**：主题 + 最新值 + 何时/由谁记录 + 趋势 + 进入详情，如“体重 4.2kg · 3 天前记录”。
2. **待办卡**：行动名 + 宠物 + 到期时间 + 执行人 + `[完成]` `[稍后]`；高风险药物增加二次确认。
3. **故事卡**：首图/短视频 + 日期 + 标题/正文两行 + 宠物标签 + 相簿信息；默认私密。

### 6.2 UI 文案规则

避免“你今天又忘记喂水了！”、“你的猫不健康”等惩罚性表达；使用“今天还没有饮水记录”“与过去几周的记录相比，近日饮水频次有所变化；这也可能与记录不足有关”。清晰区分**未完成、未记录、已跳过、未知、已完成**。

# 第三部分：完整模块原型

## 7. 注册、登录与首次引导

**[原案]** 邮箱注册、验证码重设、密码规则、用户协议、Sa-Token、邀请码。**[方案]** 保留邮箱首发，同时通过低摩擦流程提高转化。

### 7.1 页面：`AUTH-01 欢迎` → `AUTH-02 登录/注册` → `AUTH-03 建档/接受邀请`

- 欢迎页上半部宠物主题插画或写实照片，主 CTA“开始记录宠物生活”，次 CTA“我有照护邀请码”。
- 账号：MVP 邮箱+密码及邮箱验证；后续按审核与实际需求增补手机号、微信/Apple 登录。
- 密码长度建议至少 8，支持更长的密码与密码管理器，禁止常见弱密码；不建议**硬性规定必须同时具备三类字符**来换取形式合规；后端限流、撞库保护与泄露密码筛查更重要。
- 二次密码用于**注册/重置**；使用系统安全凭证库保存刷新凭据，不设“保存明文密码”。
- 服务协议/隐私政策在账号创建前清晰展示；相册权限在真正添加素材时申请，不在首屏强要全部权限。
- 首次选择：`创建我的宠物` / `通过邀请码加入家庭`，用户可以跳过宠物生日、品种、头像、三视图。
- 邀请码登录路径：**先完成账号注册/登录，再校验邀请码**，无需为已有家庭成员创建“自己的宠物”。
- 安全：Sa-Token 认证与授权、刷新 Token、设备撤销、异地登录提示、敏感操作二次验证；是否限制“单设备”应为产品选项，默认允许合理的跨设备使用。

### 7.2 初次成功标准

用户在约一分钟内可：创建一只仅含昵称/猫狗类型的宠物，进入首页并完成第一条记录；或者接受邀请直接进入家庭首页。其余档案建议在使用过程中渐进补全。

## 8. 宠物与家庭档案

### 8.1 宠物字段（强制与可选）

| 分组 | 字段 | 要求/控件 | 备注 |
|---|---|---|---|
| 必需 | 昵称、物种（猫/狗） | 文本 + 两选一 | 首屏只要两项也可建档 |
| 推荐 | 性别、出生日期/大致年龄、当前体重 | 单选、日期或年龄区间、数字 | 支持“不知道”，区分估计与实测 |
| 扩展 | 品种、混血/未知、绝育状态、到家日 | 后端可更新字典 | 缺省不强推断 |
| 身体 | 体重时间序列、BCS、MCS | 结构化事件 | 不把“当前体重”当作唯一真相 |
| 医疗 | 过敏史、慢性病、禁忌事项、芯片号（可选） | 受限可见 | 个人信息最小化原则 |
| 生活 | 爱好、性格、照护说明、紧急联系人 | 可选 | 遗失/照护场景可用 |
| 媒体 | 主头像、封面图、可选识别样本 | 上传/拍摄/裁切 | 不强制三视图 |
| 系统 | pet_id、owner_household_id、created_at、archived_at | 后端 | ID 不可变；昵称可变 |

**形象裁切**：不要要求用户为同一照片填写三个头像。上传 1 张图，编辑器中提供`头像 1:1`、`横幅 16:9`等裁切预览；裁切参数存服务端，分别生成缩略图；原图仍保留。原来“首次只能从手机文件上传，后续才能相册选择”的限制没有明显用户价值，应取消。

**物种、品种**：动态字典 API；本地缓存与版本号；提供搜索、无匹配自填，允许“未知/混血”。

### 8.2 宠物详情 `PET-01`

页面顺序：横幅照片（含昵称、年龄、体重）→“今天的照护”摘要→健康快捷指标（体重/BCS/上次疫苗）→最近 3 张照片→关键里程碑 → 各类记录/资料入口。

- 多宠：顶部头像选择器，超过 3 只时进入底部抽屉，含搜索、置顶/拖动排序。
- **已归档**列表折叠，显式提供恢复、导出、删除，不将归档和删除混为一谈。
- **纪念模式（后期）**：适用于离世宠物，停止待办但保留回忆；显式选择，不自动标注。
- 免费前期建议最多 2 只的商业策略先做 A/B 验证；切忌把已加入共享家庭的宠物误计为用户“自己创建额度”。

### 8.3 家庭空间与邀请 `FAM-01`

核心实体采用 **Household（照护家庭） → Pets → Members → Permissions**，而非“一个人关联一只宠物，其他人仅看”。

| 角色 | 默认权限 | 备注 |
|---|---|---|
| 所有者 Owner | 宠物管理、邀请、权限、导出、归档/删除、账单 | 每只宠物需明确归属；转移所有权双重确认 |
| 共同管理员 Admin | 大多数记录/提醒维护、成员管理（不含所有权转移） | 由 Owner 授权 |
| 照护者 Caregiver | 查看允许的档案、写喂食/排便/护理记录、完成分配任务 | 不可默认删除他人记录 |
| 访客 Viewer | 只读允许的范围 | 支持限时失效 |
| 临时照护者 Temp | 任务范围 + 时间窗口 + 指定宠物 | 出差、寄养等 |

权限维度不只 role：`pet_scope` × `resource_type` × `action` × `valid_until`。医疗附件、住址、紧急联系人、费用和私人日记分开授权，前后端均校验。

**邀请流程**：成员入口→选择宠物/权限/有效期→生成一次性或限时邀请码/深链→接收者登录→预览家庭与授权范围→接受→通知 Owner。邀请码随机不可猜、防爆破，可撤销、可过期。

**照护交接卡（差异化）**：`宠物信息 + 近期饮食 + 药物确认清单 + 禁忌 + 紧急联系人 + 下次待办`，由 Owner 选择字段后生成私密临时链接或 PDF；权限到期不可继续读取服务器数据。

### 8.4 删除与归档 `PET-02`

- `归档`只是隐藏活跃状态，用户可恢复，无需设置必然销毁倒计时。
- `删除宠物`需要独立危险操作与明确影响清单：结构化记录、共享授权、缩略图、原件、向量索引、报告/缓存等。
- 允许选择例如 **30 天撤销期**，到期执行真正清理流程；对保留法定义务、备份期限和系统日志的部分作清晰告知，而不是“后端永远假删除”。
- 账号注销应单独提供，用户可导出自己的资料，并撤销亲友授权；删除需向 OSS、数据库、向量库、CDN 等异步下发清理任务并检查完成结果。

**比原案更适合的交互**：
- 原案只展示“今日未记录项”，但**未记录不等于未执行**。将计划任务和实际事件拆开：提醒系统显示“待处理”，记录系统显示“尚无记录”。
- 原案提醒每 10 秒自动轮播，可能导致用户错过信息且不利无障碍阅读。改为**按紧急程度排序的静态卡**；如超过 2 项，可手动水平滑动或“查看全部”。
- 顶部横幅尽量控制高度，确保在常见小屏幕首屏就看到首个可执行任务。
- 顶部切换宠物后页面指标、计划和 AI 对话上下文同步切换；支持“全家概况”模式。
- 下滑刷新，顶部清晰表明“最后同步时间”。

### 9.2 任务状态模型

`PLANNED → DUE → (DONE | SKIPPED | SNOOZED | CANCELLED | MISSED)`。

- `DONE` 记录执行人、执行时间、相关事件 ID、是否代替别人完成。
- `SNOOZED` 延后到指定时间，保留原到期时间。
- `MISSED` 只表示时间逾期，没有事实证据表明用户没做；文案为“待确认”。
- 重复提醒频率由任务规则生成；所有执行事件通过唯一任务实例 id 防重复入库。

## 10. 记录中心：统一事件设计

核心不是十几个独立表单，而是**一条统一记录事件模型**，不同类别有各自的结构化字段。

### 10.1 统一事件基础结构

| 字段 | 用途 |
|---|---|
| event_id / household_id / pet_ids | 主键与授权边界；支持 1 条事件涉及 1–多只宠物 |
| event_type / schema_version | 事件类型与可演化的字段定义 |
| happened_at / created_at / timezone | 发生时间、录入时间、时区；可补录但不能混淆 |
| actor_id / source | 记录人、来源（manual/AI_confirmed/device/import） |
| attributes | 类型特有数据，JSON 结构；关键统计字段可以同时索引结构列 |
| attachments | 图片、音频、文件、视频关联对象 |
| note / tags | 可选文字、标签 |
| quality / confidence | 实测/估算/用户确认/AI 提取草稿等，不用“假精确” |
| updated_at / revision / deleted_at | 版本、并发修改及软删除状态 |

**交互统一**：详情页右下 `[+ 记录]` → 类型网格/搜索 → 简化表单/上次复用 → 保存，保存后可撤销、可编辑、可查看历史。常用记录可添加“快捷按钮”到首页。

### 10.2 记录优先级与入口

| 类型 | 默认一键 | 详细模式 | 分析/可视化 |
|---|---|---|---|
| 喂食 | 上次计划 1 次点击 | 食品、份量、时间、吃完比例、喂食人 | 每日 kcal、计划 vs 实际、周趋势 |
| 饮水 | 已换水/观察到喝水 | 估算毫升或“少/中/多”；采集方法 | 有效记录覆盖率与趋势，非精确值不混算 |
| 排便 | 一次排便 + 状态 | 时间、形态、颜色、异常描述、照片 | 日频次、7 日趋势、症状关联 |
| 排尿 | 一次排尿/铲砂 | 次数、观察特征、困难/异常 | 频次趋势，不直接诊断 |
| 体重 | 输入一个数字 | 设备、测量时间、误差、体况 | 7/30/90 天折线图 |
| 疫苗 | 添加接种记录 | 疫苗名、批次、医院、日期、凭证、下次日期 | 接种历史/未来待办 |
| 驱虫 | 记录一次 | 内/外驱、产品、剂量单位、按兽医计划的下次日期 | 历史时间轴 |
| 用药 | 确认已按处方服用 | 医嘱来源、药品、处方剂量、频率、开始结束 | 执行率与遗漏提醒 |
| 就医 | 添加一次就诊 | 症状、诊断（兽医记录）、处置、费用、附件、复诊日期 | 就医事件轴和摘要 |
| 洗护 | 一键完成 | 洗澡、梳毛、刷牙、剪甲、洗耳等 | 完成率与间隔 |
| 运动 | 一次遛狗 | 距离、时间、强度、路线（明确授权） | 时长与频次 |
| 行为/症状 | 一次观察 | 食欲、精神、呕吐、咳嗽、瘙痒、疼痛等 | 症状日历与组合视图 |
| 日记 | 一句话 | 富文本、媒体、AI 辅写 | 回忆时间轴 |
| 开销 | 金额 + 类别 | 产品、数量、渠道、商家、关联事件 | 月账单与类别构成 |

**关键原则**：默认**手动容易、准确可选**；不用要求每个用户每天精细记录所有类别。


## 11. 饮食模块：食品卡 → 喂食计划 → 实际记录 → 反馈

这是产品最重要的可长期复用的数据模块，设计上必须把**食品本身、组合食谱、计划安排、真实发生的进食**拆开。

### 11.1 页面树

```text
照护 > 饮食
├─ 今日营养概况（计划能量 / 已记录能量 / 水 / 零食）
├─ 喂食计划（当前启用、日程表、历史版本）
├─ 食品库（在用、收藏、停用）
│  ├─ 添加食品卡：手填 / 包装扫码或拍照识别（1.1）
│  └─ 食品详情：标签、能量、成分、批次、备注
├─ 喂食记录（时间轴、日历、统计）
└─ 能量估算工具（RER/MER 与使用说明）
```

### 11.2 食品卡 `FOOD-01`

| 字段类别 | 推荐字段 | 交互与说明 |
|---|---|---|
| 身份 | 品牌、名称、食品类型（主粮/湿粮/零食/处方粮/自制） | 搜索建议；支持手动添加；食品“处方粮”不意味着平台提供处方 |
| 规格 | 包装净重、单位、开封日期、保质期、批次号 | 下次提醒/库存可选 |
| 能量 | kcal/100g、kcal/kg 或 kcal/份，能量口径 | **必须保存数值与分母单位**，禁止只存一个裸数 |
| 保证分析值 | 粗蛋白、粗脂肪、粗纤维、水分、灰分等，% | 标注“标签保证值”，不自行视为精确含量 |
| 适用信息 | 猫/狗、幼年/成年/老年、全价/补充食品 | 源自包装标识，未经确认的不当作真实结论 |
| 配料 | 配料原文、关键过敏原提示（仅信息辅助） | 不做绝对“好粮/坏粮”评级 |
| 来源 | 录入人、照片、OCR 识别版本、人工核对状态 | AI 识别出的单位必须确认 |
| 私有信息 | 购买价格、渠道、备注 | 支持批次价格变化 |

**页面结构**：顶部产品封面 + 品牌标题 → 单行“能量 380kcal/100g（用户已确认）”→ 配料/营养折叠卡 →“加入喂食计划”“记录一次喂食”双 CTA → 食品使用历史。

### 11.3 喂食计划 `FOOD-02`

定义“团子的日常食谱”包含多份食品条目，支持早中晚安排、工作日/周末、启停日期。

- 计划条目：`food_id`、`amount_g`、`meal_time`、`frequency`、`effective_from/to`。
- 同一份计划可以包含干粮+湿粮+零食，营养合计按食品能量密度换算；没有明确能量信息时展示“无法精确计算”，不默认为 0。
- 保存计划后显示：`每日计划总 kcal`、`每餐份量`、`待办时间`、`可能重复的时间段`。
- 新计划发布后生成未来任务实例；旧计划保留历史，不 retroactively 覆盖既往记录。
- **实际喂食 ≠ 计划喂食**：记录时可以选“按计划完成”“实际吃了多少”，宠物剩余食量另记；否则报告会误把“主人投喂量”当作“宠物摄入量”。

### 11.4 科学估算小工具 `FOOD-03`

常见能量基础公式：

\[
\mathrm{RER\,(kcal/day)} = 70\times (\mathrm{BW\,(kg)})^{0.75}
\]

\[
\mathrm{MER} = \mathrm{RER}\times k
\]

其中 `k` 因物种、绝育、年龄、生理阶段、活动量和体况而异。[R13][R08]

**示例系数只作为参考起点，不是治疗建议**：健康成年已绝育犬 `k≈1.6`，健康成年已绝育猫 `k≈1.2`；幼龄、肥胖风险、疾病、妊娠哺乳等需另行评估。兽医手册特别说明任何热量计算都只是起点，应根据体重和体况反馈调整 [R13]。

**计算交互（六步）**：①选择宠物 → ②确认近期体重（非自报不确定数值要标明）→ ③绝育/生命周期/活动概况 → ④展示 RER 与 MER 的估算含义 → ⑤关联已有食品换算克数 → ⑥选择“仅保存估算”或“用作新计划草稿”，需要用户确认才能生效。

**安全阈值**：过瘦、肥胖、患病、处方粮、快速体重变化、幼龄成长阶段等情况不自动给出具体减重/处方计划，应提示咨询兽医；不能鼓励快速减重。零食和湿粮计入能量，单位换算一律显示。

### 11.5 饮食差异化扩展

- **换粮观察日历**：用户设定换粮起止日期，关联排便、食欲、体重记录；AI 只总结时间相关性，不得断言因果。
- **食品对比**：热量密度、保证分析值、单位成本；说明不同水分口径不能直接比较，营养对比需要干物质换算及明确数据来源。
- **库存/补货提醒**（后期）：按真实消耗与剩余包装量估算，不经授权不推送购物广告。

## 12. 饮水、排泄、活动与症状记录

### 12.1 饮水 `WATER-01`

原案“精准/少量/适中/大量”建议保留，但绝不能把主观少中多直接赋值成固定毫升数混入总饮水量。

| 模式 | 入口 | 记录字段 | 汇总规则 |
|---|---|---|---|
| 实测饮水 | 量杯/带传感器饮水器 | ml、测量方式、时间 | 可计算合计，展示数据来源 |
| 近似观察 | 少/中/多/没看到 | 观察等级、时间、置信度 | 只看事件频次/分布，不假设数值 |
| 换水事件 | “刚换水” | 时间、饮水器、添加量 | 不等同于宠物喝掉该水量 |
| 湿粮水分 | 引用食品水分（可选） | 估算水分摄入 | 与主动饮水分开展示，且标记估算 |

### 12.2 排便 `STOOL-01`

- 一键记录“正常/偏软/偏硬/未观察”。
- 高级模式：粪便形态图谱（使用犬猫适用、来源合规的标准）；数量、颜色、黏液/血液疑似、气味、照片、备注。
- 展示：最近 7 天日历热力点、一次事件的小照片预览、与换粮时间轴叠加。
- 若用户报告便血、持续腹泻、无法排尿等高风险表现，进入**求医建议提示**；AI 不作诊断、不让用户等待系统再次判断。

### 12.3 活动/遛狗 `ACT-01`

MVP：遛狗起止时间、时长、强度标签、照护者；可直接按“上一次路线/时长”复用。后期才考虑 GPS 路线及设备数据。路线地图属于可选敏感位置数据，应在当次操作中单独授权。

### 12.4 症状与行为 `SYM-01`

字段：症状类型、发生时间、频率、持续时间、严重程度（主观分级）、饮食/精神/排泄相关变化、照片视频、是否已联系兽医。支持“添加为就医前观察包”。AI 可将用户自由描述转成待确认结构化字段，但不能自动填入诊断名。

## 13. 体重、BCS、MCS 与长期健康趋势

### 13.1 体重详情 `BODY-01`

首页卡展示最新值及测量时间；详情页三挡`7天 / 30天 / 90天`折线图、最小最大值、测量频次、单次来源和注释。若两次记录间隔太长或数据稀疏，显示“样本不足”，不要计算误导性趋势。

### 13.2 BCS（Body Condition Score，体况评分）`BODY-02`

推荐默认 **9 分制**，记录具体分数例如 `5/9`，与使用 5 分制的数据严格区分；按 WSAVA 营养指南，许多成年健康宠物目标参考约 `4–5/9`，但个体判断需兽医结合病史、物种、品种和体格决定 [R08]。

**向导分为三步**：

1. **看**：犬猫专属参考图，从上方观察腰身，从侧方观察腹线；用户可对照标准图，而非让 AI 仅凭一张照片打分。
2. **摸**：提示需轻触摸肋骨、腰椎等部位；因为照片无法感知皮下脂肪，用户触诊结论非常重要。
3. **选分**：单选 1–9，输入“确定/不太确定”，附照片，保存测评者、时间和指导标准版本。

图表不应把 BCS 与体重硬放在同一坐标轴；采用上下两行、共同时间轴。

### 13.3 MCS（Muscle Condition Score，肌肉状况）`BODY-03`

MCS 与 BCS 衡量的不是一件事：BCS 偏体脂，MCS 偏肌肉流失。向导引导观察颞部、肩胛、腰背与骨盆区域，记录 `正常/轻度流失/中度流失/严重流失/无法判断`，支持兽医确认状态。体型、毛量、照片角度及用户经验都可能影响家庭评估，不能由“纯照片算法”自动宣布评分。

**临床启发而非诊断功能**：以“体重 + BCS + MCS + 饮食变化 + 发生时间”组成纵向观察摘要，输出“建议带给兽医的问题”。

## 14. 预防医学、就医与用药 `HEALTH`

### 14.1 医疗总览 `HEALTH-01`

从上到下：`下一次待办` → `疫苗/驱虫状态` → `正在服用药物` → `近期就医与化验附件` → `健康史/过敏史`。

### 14.2 疫苗 `VAX-01`

字段：宠物、疫苗名称（可手填/字典）、接种日期、医院/兽医、批号（可选）、证明照片、后续日期、安排依据（兽医建议/用户输入/通用提醒）。

- **禁止**仅凭“猫狗+年龄”在无地区和风险信息条件下自动强制给出下一针日期；不同疫苗适应症、方案与当地规定有区别 [R14][R15]。
- 可提供参考资讯，但实际到期日期由用户按兽医记录确认。
- 接种事件保存后，弹出“是否创建下次提醒？”预填建议但必须确认。

### 14.3 驱虫 `PAR-01`

内部/外部驱虫类型、产品名、时间、包装照片、兽医指导的用量/周期、下次日期、记录人、是否已执行。不得在仅有体重信息时自动生成药品剂量处方。

### 14.4 用药 `MED-01`

记录医嘱原文、药物、剂量及单位、给药途径、开始/结束日期、频次、执行记录、提醒领取人。对同一天同一任务重复点“已服药”要求提醒检查，避免双重给药。AI 解析处方必须逐字段确认，原图/原文永久关联直至用户删除。

### 14.5 就医与病历盒 `VISIT-01`

| 卡片层级 | 内容 | 呈现 |
|---|---|---|
| 就诊摘要 | 日期、医院、主诉、诊断（若兽医确诊）、处理、费用 | 时间轴卡片 |
| 附件 | 血常规/生化、影像、处方、检查单、出院单 | 可放大、分类、下载 |
| 结构化项目 | 医院检查指标（OCR 后校对）与检验单位、参考区间 | 按**同一指标/相同单位**纵向比较 |
| 后续安排 | 复诊时间、注意事项、医嘱 | 独立待办，由人确认 |
| 共享 | 导出“最近 30/90 天照护摘要 + 指定附件” | 一次性/限时授权 |

**OCR 流程**：拍照→原图上传→文字识别→自动标注不确定字段→用户逐项核对→生成结构化病历。影像 OCR 的参考范围因医院、仪器、样本而异，切忌直接跨医院对比判异常。

### 14.6 紧急场景

可由用户自定义“紧急联系人、就近熟悉医院、禁忌、药物过敏、既往情况”。如用户输入明确急症表现，首先展示“尽快联系兽医/急诊”的行动入口，不能用继续聊天取代线下救治；不基于模糊 AI 推断自动声称发生急症。

## 15. 提醒、计划与日历中心 `TASK`

### 15.1 关键区分

- **事件 Event**：真实发生过的事，例如 10 月 24 日 08:30 喂了 35g 食物。
- **计划 Plan**：预期频率与安排，例如每天早上 8:30 投喂 35g。
- **任务 TaskInstance**：某次应执行的事项，例如“今天 08:30 给团子投喂”；可指派具体人。
- **提醒 Notification**：针对任务实例的通知渠道，不等于任务本身。

### 15.2 功能

周期支持每日/每周/按月/按固定间隔/指定日期，允许当次跳过、不改变整个计划；提醒支持距到期前 N 小时、当时、逾期后的有限次数。时区改变和夏令时按本地日历规则处理；不应简单加 `86400s` 模拟“每天 8 点”。

**任务列表三个分段**：`待办` / `已完成` / `全部`；可按宠物、成员、日期、类别过滤。任务完成后立即在全部成员界面同步，必要时发送“X 已完成”的轻通知。

## 16. 相册与素材库 `MEDIA`

### 16.1 必须修正原案的两点

1. **取消“上传所有宠物三视图才能使用相册”**：这是新用户转化的明显阻碍。单宠用户也可能有很多非宠物照片，不能默认所有上传都是该宠物；用户必须能手动管理归属。
2. **取消“所有素材默认按标题分组”**：大多数用户上传没有标题。默认给出`时间流（按日/月）`，另设`相簿`、`主题/故事合集`与`搜索`。

### 16.2 `MEDIA-01 相册首页`

```text
[我的回忆]                [搜索 🔍] [添加 +]
[全部媒体] [相簿] [收藏] [故事]

```

### 16.3 上传 `MEDIA-02`

选择原图/拍摄 → 预览与批量操作 → 可选相簿/宠物/拍摄时间/标题/描述/标签 → 开始上传 → 上传进度与失败重试 → 背景 AI 处理。**不要求逐张填写标题**；允许在上传后补充元信息。

保存三种时间：`拍摄时间`、`上传时间`、`用户设定展示时间`；EXIF 中包含地理位置的部分默认不对外显示，可在上传前给“移除位置信息”选项。

**文件模型**：照片原件、派生多尺寸图、封面缩略图、视频原件/转码版/关键帧，统一以不可猜测 `object_key` 引用。数据库不只保留一个永久 URL；下载使用签名 URL。上传通过临时权限/签名直传 OSS，避免长期密钥进入 App [R16]。

### 16.4 AI 归属识别（可选）

模型不能因为“图片相似度高”就可靠断定两张照片一定是同一只动物，更不能将未识别成功解释为“不是用户的宠物”。推荐流程：

```text
素材上传 → 视觉质量/宠物目标检测 → 候选宠物打分
                    ↓
              置信度 + 分数差
                    ↓
        高置信：建议标签（用户可撤销）
        中置信：候选 A / B → 用户选择
        低置信：未分类（绝不强猜）
                    ↓
          用户修正 → 后续检索改善
```

多宠同框允许多标签，多只外观相似的猫会显著提高误判概率。三视图或参考样本作为**可选增强识别**，以实例识别评测（跨时间/姿势/光照、同窝宠物难例）决定实际阈值，不能预设“达到某个相似度百分比就肯定是该宠物”。

### 16.5 双搜索 `MEDIA-03`

- **精准检索**：宠物、时间段、相簿、标签、媒体类型、标题关键词、收藏。
- **语义检索**：如“团子去年冬天在草地上奔跑的视频”；文本转多模态向量检索，先按家庭/权限与明确过滤条件筛选，再对候选结果重排。
- **融合结果**：展示命中的文本提示“匹配：草地、奔跑”，但标注 AI 可能有误；可反馈“不相关”。
- 视频初期采用关键帧 + 用户标题/描述索引，不要对所有长视频逐帧高成本处理；进阶使用服务商支持的视频向量能力 [R17]。

### 16.6 相册权限

查看、上传、修改标签、删除分别授权；默认只有 Owner 能删；公开分享必须显示范围、时效与可撤销选项。用户删除时同步删除索引和派生图片；引用该素材的日记需显示“关联资源已删除”而不是悬空空白。

## 17. 日记、成长时间轴与情感回忆 `MEMORY`

### 17.1 日记编辑器 `NOTE-01`

**最小可用编辑器**：标题、正文、图片/视频、清单、加粗、标题、引用、列表、链接、自动保存、草稿恢复、撤销/重做。存储可用 Markdown/结构化文档 JSON（二选一确定单一主格式），渲染时严格做 XSS 过滤，导出 Markdown/HTML/PDF。**手机端不要照搬桌面语雀的全工具栏**，用选中文字时出现的浮动格式工具、底部附件栏。

- 记录形式：`一行日记`（默认） / `完整日记`（高级）。
- 可附带已存在的喂食、就医、体重事件作为“引用卡片”，不复制原数据。
- AI 辅写：输入“今天带团子去公园，拍了三张照”，生成温暖但可编辑的草稿；不能凭空编造具体事迹、对话或宠物感受。
- 日记中的“下月要驱虫”触发**待办草稿建议**，弹窗展示日期推断依据；只在确认后入库。

### 17.2 成长双时间轴 `MEMORY-02`

**生活视图**：照片、故事、里程碑、生日、到家纪念；**健康视图**：体重、就诊、疫苗、饮食计划变化。默认切在生活视图，用户可对某一事件“显示关联健康事件”。时间轴需支持年/月快速跳转、标签过滤、多个宠物同框以及指定宠物聚合。

### 17.3 自动回忆卡（后期）

“来到家的第 100 天”“最常去的公园（用户明确记录过才展示）”“这月最快乐的 10 张照片”，用户先选择素材再生成，不允许自动公开发表。用户可对 AI 生成的文案逐项校正或直接删除。

## 18. 养育账本、消费计划与会员 `BILL`

- 类别：主粮、零食、医疗、洗护、设备、消耗品、寄养、交通、其他。
- 字段：金额、货币、购买日期、分类、商家、关联宠物、关联食品卡/就诊、照片凭据、记录人；共享开销可以按宠物比例或“公共家庭费用”归属。
- 首页：本月合计、近 6 月趋势、费用结构、单宠平均，不拿不同家庭未统一口径的数据排名。
- 可选：预算提醒、订阅/年费清单、食品单价与天数估算。
- **会员边界**：基础安全记录、就医资料导出、账号删除不应收费；可考虑高级储存空间、AI 报告次数、长期云备份等透明增值，避免通过宠物健康焦虑施压。

## 19. 自定义记录与高级模板（v1.2）

用户可创建如“刷牙”“训练”“情绪评分”的自定义类型；字段组件限制在`单选/多选/数值（单位）/时间/文本/布尔/照片`，类型版本化。默认数据字典由后端配置，不开放任意脚本和公式执行。

**一键复用**：复用上次已确认的**非高风险**记录模板；原案的“10 天以内”可以作为默认，但应允许调整。药物剂量、医疗决定、紧急联系人等高风险字段必须重新确认。系统明确区分“复用字段值”和“复用发生时间”，绝不把旧记录原样当今日事件。


# 第四部分：AI 产品体系

## 20. AI 不是一个聊天按钮，而是四层能力

```text
           用户语言 / 图片 / 文档 / 操作入口
                         ↓
      ① 意图识别与场景路由（记录、查询、知识、报告）
                         ↓
      ② 可信数据获取（MySQL 结构化 / Qdrant / 知识库）
                         ↓
      ③ 分析与生成（计算、摘要、解释、草稿）
                         ↓
      ④ 人类确认与执行（预览字段、权限验证、事务落库）
```

| 层 | 功能 | 默认规则 |
|---|---|---|
| AI-Read | 只读数据问答、个人记录检索、资料检索 | 可以直接回应，但必须引用记录与来源 |
| AI-Create | 生成日记/记录/提醒/食谱草稿 | 用户检查后才写正式数据 |
| AI-Analyze | 历史趋势、报告、照护规律、疑似变化 | 显示样本量、缺失比例和方法 |
| AI-Assist | OCR、相册标签、病历提取、图片描述 | 不覆盖原文，不确定性明确可见 |

**产品层不必向普通用户暴露 Chat/Agent 两套复杂模式**。界面统一叫“AI 助理”，在回复中显示“正在查找记录”“生成了一条待确认记录”“查看资料来源”，高级用户才可以查看工具执行详情。

## 21. AI 对话页 `AI-01`

```text
[当前宠物：团子 ▼]              [历史]

你可以让我：
[查最近喂食] [整理病历] [记录今天的事]
[做月度分析] [查找照片] [科学养宠知识]

用户：昨天团子吃了什么？最近体重呢？

AI：根据你已经记录的信息：
    10月23日：早/晚两次喂食，合计 65g ...
    最新体重：4.2kg（记录于 10月21日）
    注意：没有全天饮食完整性的证据。

    [查看喂食明细] [体重趋势图]
    引用：记录 #A001、#A002、#W031

[输入文字…]    [添加照片/附件] [发送]
```

### 21.1 AI 对话的四种响应组件

1. **文本/Markdown**：简短解释，引用来源。
2. **数据卡**：结构化指标、时间、单位、来源，支持“查看详细记录”。
3. **图表卡**：折线/柱状/日历分布，图下附文字结论与样本提示。
4. **操作确认卡**：展示将写入哪些字段，按钮`确认保存` `编辑字段` `取消`。

不要将所有回复自由生成任意 HTML 发到客户端，图表建议由**受控 UI schema + Flutter 原生组件**渲染；月报可以生成受控 HTML 模板以便导出。

```json
  "unresolved_fields": [],
  "user_confirmation_required": true,
  "source_text": "今天早上给团子喂了35g猫粮"
}
```

`commit` API **绝不接受模型自己传来的“已确认=true”**：需要服务端发放与用户会话关联的确认凭据，严格权限、时效和幂等检查。对于超出用户授权的 pet_id，后端直接拒绝，不把“模型说可以”当权限依据。

### 22.1 结构化回答协议

内部 Agent 可以使用函数调用和 JSON Schema；对 Flutter 的流式展示建议规范事件：`message.delta`、`tool.status`、`ui.card`、`ui.chart`、`action.draft`、`message.done`、`error`。模型不直接返回任意可执行 JS、HTML、SQL 或代码。复杂图表由应用层生成标准数据序列，模型负责解释。

## 23. RAG 与个人知识问答

### 23.1 知识来源分级

1. **用户自己的结构化记录**（最高个人事实优先级；但若记录是估计则保留估计属性）。
2. **用户上传的就医文件**（视为文件原文而非必然正确、且不自动变成兽医诊断）。
3. **经编辑审核的兽医指南/权威知识**（版本、地区、发布时间、许可/版权条件）。
4. **普通公开文章**（可用于资料拓展；不得将抓取网页文字无验证地变成医疗知识事实）。

**知识库建构**：收录授权材料 → 解析 → 按语义和标题层级切分 → 去重/质量标注 → 引用元信息 → Embedding → Qdrant → 检索→重排→回答。持续维护文档来源、发布时间、适用物种/国家/范围、内容更新日。

**重要限制**：不能大规模抓取任意版权文章并将全文公开重发；对用户只展示必要短引文、摘要与原始链接。疾病与用药的专业指南必须优先，不让论坛回答与兽医协会指南同权。

### 23.2 组合检索

- 数据查询：先用关系数据库精确过滤/聚合，然后由 AI 解释。
- 文本私有资料：用户授权范围+时间/宠物过滤→文本 Embedding 与关键词混合召回→重排。
- 图像/视频：多模态 Embedding+源文件权限校验+相似度及标签重排。
- 公共知识：与用户隐私数据**分开** collection、审计和缓存策略。
- 对结论显示`引用列表`；无依据时明确“我在现有记录中没找到”。

Qdrant 支持混合检索与多阶段查询；多用户共享 collection 推荐采用 household_id 等 payload 分区过滤，同时仍需 MySQL 权限校验 [R18][R19]。

## 24. AI 健康变化雷达（v1.2）

**[方案]** AI 健康模块的核心不是“健康评分 98 分”，而是建立宠物个人时间序列基线。

### 24.1 算法原型

- 指标：体重、日喂食量、排便频次/分型、饮水有效观测、活动量、症状事件。
- 对有足够且可比记录的指标建立参考窗（如过去 28 天），与最近 7 天比较；**窗口长度只是可测试参数**。
- 对缺失率很高的指标不生成显著变化判断。
- 采用规则阈值、稳健统计指标与多个信号的联合变化描述，避免大模型单凭几个数值自由推断。
- 同一只宠物不同生活阶段的基线可能改变；换粮、搬家、绝育、疾病、设备更换等事件可作为上下文标签。

### 24.2 结果卡片

> **近期喂食记录有所下降**  
> 最近 7 天记录均值低于过去 28 天的个人记录水平。  
> 有效天数：5/7；另有 2 天未记录。  
> 你可以补充：是不是换了食品、是否有剩粮、食欲有没有变化？  
> `[查看依据]` `[补充观察]` `[生成就医摘要]`

**绝不输出**“检测到肾病”“预测 7 天后会生病”等缺乏临床验证的宣传或判断。变化雷达用于辅助观察与咨询兽医，不能替代检查。

## 25. AI 健康与成长报告 `REPORT-01`

### 25.1 报告类型

| 报告 | 周期 | 面向用户 | 内容 |
|---|---|---|---|
| 月度照护报告 | 按月，可手动 | 普通宠主 | 完成情况、饮食、体重、护理、成长照片 |
| 就医前摘要 | 指定 7/30/90 天 | 兽医/宠主 | 症状时间轴、用药/饮食/体重、上传病历 |
| 饮食观察报告 | 用户选开始/结束日 | 精细养宠 | 换粮节点、体重、排便、食品能量 |
| 年度回忆报告 | 按年 | 情感纪念 | 里程碑、精选照片、故事（默认私密） |

### 25.2 一份月报的固定模块

1. 宠物头像、日期范围、报告生成时间、数据覆盖率。
2. 核心摘要（只陈述记录可支持的事实）与重要未完成待办。
3. 饮食：计划/已记录热量对比图，食品占比和缺失说明。
4. 体重与体况：折线 + BCS/MCS 轨迹 + 记录次数。
5. 日常：喂食、排泄、洗护、活动和饮水可比指标。
6. 医疗：接种、驱虫、药物和就诊时间线。
7. 费用：分类占比与总金额。
8. 成长瞬间：已授权照片 3–6 张，附手动/AI 可编辑文案。
9. 值得关注的变化：证据、可信度、建议补充观察问题。
10. 数据来源、缺失项与非诊断声明。

### 25.3 图表规则

- 体重：折线图（时间 vs kg），相邻间隔大时用断点，不虚构连续测量。
- 每日摄食：堆叠柱状图（食品类别）+ 计划水平线，必须标清计划与实际已记录。
- 任务完成：分段环图或进度条，分母只包含用户启用的任务。
- 费用：堆叠柱/条形图比饼图更利于对比小类别。
- 一切图表必须包含文字“本图说明了什么”，移动屏支持点选数据点。

### 25.4 导出链路

后端汇总结构化数据 → 计算统计量 → LLM 生成可审校解释 → 固定 HTML 模板渲染 → 应用内 WebView 预览 → 服务端/客户端 PDF 或长图导出。**更建议固定模板，不允许 LLM 直接拼接任意 HTML+JS**，避免 XSS、布局失控及不可复现。

生成结果含 `report_version`、`data_snapshot_at` 和引用事件 ID；如源数据后来修改，报告提示“按某日数据生成”。

# 第五部分：社区、增长与商业化

## 26. 社区 `DISCOVER`（计划，首发默认关闭）

原案希望采用小红书式内容流：双列图文/视频卡、点赞、评论、收藏、转发。视觉形式可以研究，但**不建议在 100 人首测时上线完全公开的 UGC 社区**，原因包括内容冷启动、审核举报、安全维护、个人信息泄露与持续运营成本。

### 26.1 两阶段策略

**阶段 A：非公开“家庭圈/好友分享”**
- 用户自行选定相册故事生成可分享卡；默认仅本人可见。
- 分享对象明确、可撤销、可设置过期；公开可见与家庭可见是不同开关。
- 初期不开放陌生人评论、私信、关注、排行榜。

**阶段 B：公开社区**
- 双列发现瀑布流；笔记详情含媒体、标题、正文、作者、可信来源（如养宠经历/专业资质）、发布时间、评论收藏。
- 标签更适合按`猫/狗`、`新手养宠`、`训练`、`营养`、`成长日记`、`问题经验`组织。
- 内容不得自动携带病历、住址、宠物芯片号、位置 EXIF、家庭成员信息。
- 上线前必须建设实名认证/账号策略（依法依规确定）、内容审核、举报、屏蔽/拉黑、申诉、反垃圾、反广告营销、侵权处理、内容日志留存与 AI 生成内容标识。
- 医疗经验贴必须标明“个人经历，非诊疗建议”，平台不能默认用点赞量评判医疗可信度。

**差异化内容形式（验证后）**：`养宠经验卡`可以由用户自愿选择自己的一段**去隐私化**记录生成“换粮观察”“疫苗提醒心得”等图文，用户审核并确认发布。通过自己的真实经历形成有用内容，而非先复制泛娱乐推荐流。

## 27. 激活、留存与商业化

### 27.1 激活旅程

`首次安装`→`建一只宠物或接受邀请`→`一键记录一次`→`启用一个真正需要的提醒`→`第 2 天回来看是否同步成功`→`第 7 天查看记录趋势`。

在刚建立账户时，**不要连发提醒催促完善所有字段**；每次触达都有具体价值，尤其是“即将到期任务”“你保存的体重趋势已积累到三个点”等。

### 27.2 付费原则（实验，而非已定价策略）

- 免费核心：基础档案、基础记录、关键提醒、基础导出与隐私控制。
- 增值项：云相册容量、长视频/高阶检索、增强版年度报告、跨平台高级备份、更多可选 AI 额度。
- `最多 2 只免费宠物`可作一个价格实验，但先测会不会导致共享家庭、临时寄养等场景挫折。
- AI 成本按模型输入/输出 Token、向量索引新增量、媒体处理秒数/大小和报告次数计费、限额；不宜无限量承诺。

# 第六部分：技术架构与关键实现

## 28. 建议架构：优先低成本、可拆分的模块化单体

结合当前**小规模首测、Java 后端、阿里云 OSS/Qdrant/AI 组合**的技术方向，建议首发架构如下：

```text
[Flutter iOS/Android]
   │ HTTPS / SSE / Push
   ▼
[API Gateway / Nginx]  ──→  [Spring Boot 模块化单体 + Sa-Token]
                               ├── Identity / Household / RBAC
                               ├── Pet Profile / Care Event
                               ├── Food / Plan / Task / Reminder
                               ├── Media / Notes / Billing / Report
                               └── AI Gateway / Tools / Audit
                                       │
                ┌──────────────────────┼──────────────────────┐
                ▼                      ▼                      ▼
             [MySQL]               [Redis]              [Job Worker]
                                                         │
                                             ┌───────────┼─────────┐
                                             ▼           ▼         ▼
                                          [OSS]       [Qdrant]  [百炼/OCR]
```

**不建议 MVP 拆为 10+ 个微服务**：用户少时，日志排错、分布式事务、权限和部署成本远高于拆分收益。采用按领域划分的 Java 包、明确内部接口与事务边界即可。

### 28.1 技术选型

| 层 | 建议 | 注意 |
|---|---|---|
| 移动端 | Flutter（Android/iOS 共用 UI）；若已有小程序则可通过独立接口复用后端 | 图片/文件选择、推送、原生权限、编辑器需真机验证 |
| API | Java Spring Boot、REST JSON；AI 回复用 SSE | 为 SSE 配置超时、断线恢复策略和代理缓冲 |
| 认证 | Sa-Token + Refresh/设备会话管理 | 每请求从服务器身份和家庭成员关系判断权限 |
| 数据库 | MySQL 8.x + Flyway/Liquibase 迁移 | 账单/健康事件关键数据保留结构列与约束 |
| 缓存/调度 | Redis；调度首先使用数据库任务扫描或 XXL-JOB 等合适工具 | 定时提醒采用幂等任务，不依赖单次内存 Timer |
| 异步处理 | **起步数据库 Outbox + 后台 Worker**，有压力再加 RocketMQ/RabbitMQ | 先解决可靠性与重试，别为 100 人超前引入 MQ 运维 |
| 对象存储 | 阿里云 OSS，STS/短签名直传、分片上传 | 不把 AK/SK 放客户端，不公开存储 Bucket |
| 向量检索 | Qdrant，区分媒体、个人笔记和公开知识索引 | 先视为可选扩展，避免低内存机器强行共部署 |
| Embedding | 百炼文本与多模态 Embedding，按场景独立评测 | 多模态模型接口在 Java SDK 上的支持差异需提前确认 [R17] |
| LLM | 提供工具调用、结构化输出的模型，由 AI Gateway 抽象 | 记录/提醒工具采用 Schema 校验和人类确认 |
| 导出 | HTML 模板 + PDF 渲染任务 | 对外链接有效期、加水印、文件访问权限 |
| 可观测 | OpenTelemetry + 结构化日志、错误上报、指标看板 | 日志隐藏 Token、签名 URL 和敏感医疗内容 |

**资源规划**：如果使用一台 2C2G 公网服务器，不建议把 Java、MySQL、Redis、Qdrant、转码、OCR、LLM 推理全部放在这台机器上。文件上传/转码、向量处理走云 API 或异步工作节点；MySQL、Redis 可以适当配置并压测后决定托管/自建；LLM 不应放在此规格的主机上本地推理。只有真实监控得出内存、CPU、连接数、带宽指标后再扩容。

### 29.1 数据一致性约束

- 一次用户操作使用 `Idempotency-Key` 防重复写入，尤其是“记录喂食”和“完成药物任务”。
- `care_event` 更新采用 revision 乐观锁与变更审计，冲突时提示“照护者刚修改了这条记录”。
- 汇总/报表使用官方统一的统计服务计算，避免前端、AI 和 PDF 三套数值互相矛盾。
- 对多宠共用事件必须有明确归属关系，不允许默认把一笔记录复制为每只宠物的独立摄入。
- 删除流程由 outbox 扩散至 OSS、Qdrant、缓存、导出报告，定期核查未完成任务。

## 30. 媒体处理时序

```text
App: 申请上传凭证 → API: 校验账户/额度/类型/大小
App: 使用限时签名/STS 分片上传到 OSS 私有目录
OSS: 上传完成 → API: 依据 object_key 验证元数据/文件类型
API: 保存 media_asset(status=PROCESSING)
Worker: 生成缩略图 → 提取 EXIF/视频封面 → 可选 AI 标签/向量
Worker: 更新索引与状态 READY，发出通知/轮询可见
App: 显示预览，允许用户修改关联宠物
```

- 不信任客户端传来的尺寸、类型和容量；服务端验证实际对象大小及 MIME 魔数。
- 存储配额计算原件与派生文件，配额策略明确；失败任务支持重试和清理孤儿文件。
- 分片续传、弱网保存草稿、取消上传、失败断点续传为体验重点。
- 缩略图 CDN 配置访问控制，涉及病历/家庭媒体时不要生成无法撤销的公开永久外链。

## 31. 安全、隐私与中国大陆合规检查

### 31.1 首发必做

1. 隐私政策、用户协议，分别说明账号、照片、健康记录、AI 第三方调用和推送等数据用途；必要权限在对应场景请求。
2. 用户信息、家庭媒体、医疗文件按**最小权限**处理；核心权限判断在后端，不能仅靠前端隐藏按钮。
3. 用户可访问、校正、导出、删除个人数据/注销账号，第三方服务与保留期透明。[R20]
4. 中国大陆提供 APP 互联网信息服务涉及的**APP 备案/互联网信息服务备案要求**需在部署与分发前核验；“只给 100 人安装”本身不构成法定豁免。[R21]
5. 公开社区包含评论/点赞等时，将触发额外平台内容治理义务；是否需算法备案应按功能、传播能力等具体标准评估，并非所有个性化功能都自动同等备案。[R22][R23]
6. 面向中国境内公众的生成式 AI 服务及 AI 生成内容标识存在专项规定，应评估使用第三方已合规模型与产品具体责任边界；生成/公开传播的图片文字按适用规则标识。[R24][R25]
7. 动物疾病诊断、治疗、开方等经营性活动受到动物诊疗许可制度约束。AI 模块定位于信息整理、科普、记录辅助和就医准备，不经营无资质动物诊疗服务。[R26]
8. 图片含人脸、住址、定位等信息，公开分享前提供清理 EXIF 和预览机制。对第三方模型传输素材，说明目的、对象及必要性。

**合规备注**：上述是产品设计检查清单，具体上线资质、备案、备案主体与内容运营边界需要在确定分发模式、服务地、AI 提供方式之后由熟悉中国大陆互联网与动物诊疗法规的专业人士核对；不能仅凭本文视为已满足监管要求。

### 31.2 典型威胁模型

| 风险 | 控制措施 |
|---|---|
| 邀请码撞库 | 高熵、过期、限次数、登录后接收、记录撤销 |
| 越权查看其他家庭的宠物/媒体 | 每个读写 API 的 household/pet ACL + 集成测试；下载前重新授权 |
| Qdrant 多租户数据串读 | tenant payload filter + API 二次校验；不得信任模型任意设置 tenant_id |
| OSS 链接泄漏 | 私有 Bucket、短期签名 URL、禁止公开列目录、定期清理 |
| LLM Prompt Injection | 检索结果作为不可信资料，不允许资料指令触发工具写操作 |
| 病历 OCR 幻觉 | 存原文件、显示识别置信度、用户确认、保留修改记录 |
| 隐私照片误公开 | 私有默认值、显式发布流程、敏感信息提示 |
| 数据被“软删不清理” | 真实清理编排、留存说明、索引同步删除 |
| 家庭成员重复给药 | 唯一任务实例、实时同步、提交二次核验、冲突提示 |

# 第七部分：端到端关键流程与验收标准

## 32. 四条主流程（UI/研发按此做原型）

### F1. 新用户首次记录（优先做到极简）

`欢迎 → 登录 → 创建宠物昵称+猫狗 → 今日首页 → 快速记录 → 喂食 →（可选选择食品）→ 成功 → 首页显示“已记录”`。

**验收标准**：不上传头像、不填生日、不创建三视图也能完成；断网后可以保留未提交草稿；同一个请求重复提交不会生成两条记录；用户能找到刚刚创建的记录。

### F2. 家庭协作防重喂

`Owner 发邀请码 → 照护者接入 → A 完成早餐任务 → B 首页实时看到“已由 A 完成” → B 再次执行同一任务时收到核验提示`。

**验收标准**：任务历史保留执行人；权限不足者不能修改计划；邀请撤销后无法再获取受保护数据；并发提交不生成两个同一任务完成事件。

### F3. 一次就医结束后的记录闭环

`上传就医材料 → OCR 生成待确认字段 → 用户校对 → 保存就医事件 → 用户选择创建复诊提醒 → 报告中可追溯原附件`。

**验收标准**：原始图片保留到用户删除；AI 不擅自改药量；复诊日期不确定就不入任务；导出报告不会包含未授权的私人日记。

### F4. 从照片到 AI 记忆

`批量上传 → 自动生成时间分组 → AI 建议宠物标签 → 用户确认/修正 → 搜索“团子在公园奔跑” → 命中照片 → 选素材生成日记草稿 → 用户编辑并保存`。

**验收标准**：零张三视图仍可上传；识别失败保留“未分类”；跨家庭媒体搜索结果为空；背景处理失败不影响查看原图。

## 33. 系统异常与边界状态

- **空状态**：无宠物、无记录、无相簿、无病历、无成员、AI 无法找到证据，都要分别设计插画/简短文案/主 CTA。
- **离线**：记录草稿本地加密缓存、显示“待同步”；高风险药物执行避免在不确定是否同步成功时重复确认。
- **权限失败**：已撤销权限时，页面显示“你已无法访问该宠物”，不能暴露历史缩略图。
- **上传失败**：精确显示哪个文件失败、可单独重试、不会重复计费/占配额。
- **AI 失败**：只读原始记录永远可用；草稿未提交；给出重试/手动录入入口。
- **提醒未到达**：App 内任务仍准确可见，通知为附加交付层；记录投递失败原因。
- **跨时区**：日历以宠物/家庭约定时区或用户设置为准，在 UI 清晰显示。
- **数据冲突**：指出冲突字段、双方版本、允许合并/保留特定版本。

## 34. 指标埋点与实验设计

| 埋点 | 目的 |
|---|---|
| `signup_completed` / `pet_created` | 判断激活漏斗 |
| `first_event_created` / `event_create_latency_ms` | 测量首次价值与记录效率 |
| `care_task_done` / `care_task_snoozed` | 提醒是否真正有用 |

**建议首批 100 用户验证（不是行业事实）**：招募覆盖单宠猫、单宠狗、多宠、家庭协作和健康管理 5 类，前 2 周重点观察访谈、会话回放（仅经同意且脱敏）、埋点漏斗。用户离开时问“哪一步太麻烦”，比单独问“喜欢不喜欢 AI”更可行动。

### 34.1 设计假设与可验证实验

| 假设 | 小规模实验 | 成功判据（初始目标，可调整） |
|---|---|---|
| 一键记录提升重复使用 | 比较快捷记录 vs 完整表单 | 中位完成时间下降，错误率不升 |
| 家庭看板减少重复执行 | 家庭任务前后访谈+事件日志 | 同一餐/药物重复登记次数下降 |
| AI 草稿帮用户节约时间 | 测记录前后时长、人工修改比例 | 真实保存成功、字段纠错负担可接受 |
| 自动相册标签有价值 | 跟踪采纳/纠正/关闭推荐率 | 高信心标签采纳率满足预设阈值 |
| 月报提高次月留存 | 随机邀请部分家庭体验 | 与未看报告组比较，但注意小样本统计功效不足 |

# 第八部分：重点决策记录（相对原案做了什么变化）

## 37. 原案修订清单

| 原案行为 | 保留/调整 | 原因 |
|---|---|---|
| 首次登录强制要求宠物完善大量信息 | **改为只必填昵称和猫狗** | 提高第一次成功体验 |
| 首次头像只允许从文件选择 | **改为相册/文件/拍照均可** | 避免无用户价值的限制 |
| 一张照片需要裁成三种头像 | **保留多裁切预览**，但后台自动派生 | 降低用户操作负担 |
| 全部宠物必须上传三视图才能用相册 | **取消强制** | 算法质量不应阻塞基本功能 |
| 相册全部以标题归组 | **默认时间分组 + 可选故事合集** | 没标题的普通照片也应自然浏览 |
| 首页只显示未记录事项 | **任务与记录分离** | 未记录≠未完成 |
| 未处理待办每 10 秒自动轮播 | **改静态优先卡/手动切换** | 信息可见、稳定、可访问 |
| 亲友只有查看权 | **保留 Owner 核心权，增加角色+作用域授权** | 真正满足共同养宠场景 |
| 删除后在后端永久假删除 | **改归档与删除分离，真实清理** | 合规与隐私信任 |
| 喂食记录基于计划 | **保留引用，但允许无计划直接记录** | 低门槛 |
| 饮水少中多 | **保留定性记录**，不伪造毫升数 | 数据可信度 |
| AI Chat 与 Agent 两个入口 | **统一 AI 助理，读与写权限分层** | 降低理解成本、明确确认责任 |
| AI 抓取所有相关文章加入知识库 | **改为许可/来源/版本可控知识库** | 质量、版权与兽医安全 |
| AI 可自动生成提醒 | **保留建议，但必须用户确认** | 避免错误任务进入日程 |
| AI 自由生成 HTML 报告 | **改固定模板 + 结构化分析** | 稳定、可追溯、可导出 |
| 马上上小红书式公开社区 | **改为后期可插拔模块** | 审核/运营/资质/冷启动成本 |
| 普通账号最多两只宠物 | **暂定价格实验** | 以真实付费与留存反馈验证 |

## 38. 首发版“不做”清单（比“做什么”更重要）

1. 不做 AI 自动确诊、不做非兽医开药或处方自动调整。
2. 不用“健康分数”替代临床评估，不以低置信照片强制判断宠物身份。
3. 不做首发公开社区、陌生人私信、直播、电商、同城服务交易。
4. 不做全量手机相册自动扫描/上传，不默认读取相册库。
5. 不让任意 LLM 生成 HTML/SQL 直接执行，不让模型绕过授权写数据库。
6. 不为 100 人测试搭建复杂微服务和重型实时流计算集群。
7. 不通过反复提醒“你的宠物可能生病”制造焦虑。
