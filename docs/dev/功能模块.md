# 认证

## 登陆接口

```
com.fafa.interfaces.controller.AuthController#login
```
微信code登陆，第一次登陆会注册为新用户，但是信息基本为空，后续登陆会检查MySQL数据库是否存在该用户。

### 设计理念

用户从小程序登陆后，第一次需要授权登陆，之后只要能获得code，就可以直接登陆，跳过用户点击进入。

如果无法实现，则每次小程序登陆界面只预留微信登录按钮，不存在其余登陆方式

## 登出接口

```
com.fafa.interfaces.controller.AuthController#logout
```
用户点击登出后，会清除本地的token，用户需要重新登陆。

## 宠物三视图照片（位1=头像、位2=正面照、位3=侧面照）

> 原「上传头像 + 上传三视图」双接口已合并为按位序上传的一套照片，本节为已实现的最终设计。

### 设计要点

- 头像与三视图合一：小程序端最多三张图片作为三视图，位1自动作为头像，前端可控制头像位序
- 创建宠物必须上传三张照片；后期替换照片时同样强校验三张齐全（`Pet#updatePhotos`）
- 每次替换照片后，被换下的旧文件从 OSS 异步删除（复用调位序的 URL 保留）
- 照片上传在事务外并行执行（虚拟线程），落库成功即返回，不让用户等向量化
- 向量化异步处理：落库时先记录 PENDING 状态，事务提交后再派发任务；
  Python 处理完成后回调更新数据库状态，并把向量写入 Qdrant
- 开发阶段通过 HTTP 接口调用 Python（`fafa.ai.dispatcher=http`），
  生产环境切换 RocketMQ（`fafa.ai.dispatcher=rocketmq`）

### 接口

创建宠物（三张照片必传）：

```
com.fafa.interfaces.controller.PetController#createPet
POST /api/pets  (multipart, photos[0..2])
```

替换三视图（每个槽位二选一：传新文件 avatarFile/frontFile/sideFile，或传现有照片 URL avatarUrl/frontUrl/sideUrl 调整位序免重传）：

```
com.fafa.interfaces.controller.PetController#replacePetPhotos
PUT /api/pets/{id}/photos  (multipart)
```

重新触发向量化（向量化失败/任务丢失时的补偿入口；照片不齐全或已完成向量化时拒绝）：

```
com.fafa.interfaces.controller.PetController#revectorizePhotos
POST /api/pets/{id}/photos/revectorize
```

### 关键实现

```
com.fafa.application.service.PetApplicationService  # registerPet / replacePetPhotos / revectorizePetPhotos / handleVectorizationCallback
com.fafa.domain.model.pet.Pet                       # updatePhotos / resetVectorizationToPending / 向量化状态机
com.fafa.infrastructure.ai.impl.HttpAiTaskDispatcher      # dev：HTTP 派发
com.fafa.infrastructure.ai.impl.RocketMqAiTaskDispatcher  # prod：RocketMQ 派发
com.fafa.interfaces.controller.CallbackController   # POST /api/callback/pet-vectorization（X-Internal-Token 保护）
```

- 无变化短路：按位序三元组完全不变且向量化已完成时，跳过重传与重新向量化；
  纯调位序（URL 集合相同、顺序变化）仍会重新派发——Python 端按 view 分别 upsert，
  view 与照片的对应关系已改变；三元组不变但状态非 COMPLETED 时同样重新派发（即重试路径）
- 事务边界：OSS 并行上传属于慢速网络 IO，放在事务外执行；落库用 TransactionTemplate 短事务
- 孤儿文件防护：上传成功后的落库/标签等任何失败路径，都会异步清理本次已上传的文件
- 回调幂等：COMPLETED 为终态，不会被迟到的失败回调降级（防乱序回调回退状态）

# 素材（照片/视频）

素材上传/融合检索/编辑接口（`PhotoController`，统一前缀 `/api/photos`，素材语义含照片与视频）。上传前预校验并前置扣减存储配额，上传后异步生成 embedding 向量化并自动追加宠物名称标签，向量化状态可在素材详情中查看。

## 批量上传素材

```
com.fafa.interfaces.controller.PhotoController#upload
```
POST `/api/photos/upload`（multipart/form-data）

单批最多20个文件；tags 逗号分隔，应用到全部素材；照片和视频异步生成 embedding 并自动追加宠物名称标签。

事务内流程：预校验全部文件（类型/大小）→ 存储配额原子增量（校验+扣减二合一，配额不足直接失败，一个文件都不上传）→ 虚拟线程并行上传对象存储 → 落库 → 打标联动；上传或落库失败时回滚配额并清理已上传对象。AI 分析分发在事务提交后（AFTER_COMMIT）执行。

参数：files 必填（图片/视频）；tags、petId（指定即确认归属）、takenAt（拍摄时间，缺省为上传时刻）可选。

## 素材检索（确定性 + 语义融合）

```
com.fafa.interfaces.controller.PhotoController#search
```
POST `/api/photos/search`

前端唯一检索入口，按 query 是否有值自动分流：

- **query 为空** → 纯确定性分页检索：宠物ID、标签（多选 OR）、拍摄日期区间过滤，按拍摄时间倒序分页，不限调用次数
- **query 有值** → 语义检索（占 AI 月配额，失败请求不占额度）：petId 与日期下推向量网关，tags 在 MySQL 补全阶段做 OR 硬过滤，结果按语义相关度排序一次性返回（不做翻页）；petId/tags/日期作为确定性硬过滤叠加

两种分支协同成员均按 READ_RECORD 放行，检索范围解析为素材归属人的数据。

参数：query（最长100字符，可空）；petId、tags、startDate、endDate 可选；page 页码从1开始（默认1，仅确定性分支生效）；size 每页条数（默认20，上限100；语义分支作为最大返回条数）。

### 存储与检索整改记录（已实现，2026-10）

> 原「需要后期修正」三条计划（上传配额前置 / 存储迁移 COS / 检索融合）已全部落地，141 个测试回归通过。

#### 1. 上传配额前置（`MediaApplicationService#upload`）

- `increaseStorage` 是「校验 + 原子扣减」二合一（条件 UPDATE `increaseWithinLimit` 防并发超发），配额不足直接抛 `STORAGE_QUOTA_EXCEEDED`，一个文件都不上传
- 执行顺序调整为：预校验全部文件（类型/大小）→ 配额前置扣减 → 虚拟线程并行上传 → 落库 → 打标联动 → AFTER_COMMIT 分发 AI 分析
- 上传或落库失败：回滚配额（`decreaseStorage`）+ 清理已上传对象（`cleanupUploaded`），事务同步回滚

#### 2. 对象存储接入腾讯云 COS（dev 环境）

- 新增 `CosStorageService` + `CosConfig`（`fafa.storage.type=cos` 时装配），与 MinIO/OSS 实现同一 `StorageService` 接口，pom 引入 `com.qcloud:cos_api:5.6.227`
- 桶 `fafa-dev-2026-1335105367`（ap-guangzhou）已设为**公有读**：素材直链展示与 AI 拉图直接用永久 URL（`https://{bucket}.cos.{region}.myqcloud.com/{objectKey}`），无需全链路预签名；`generatePresignedUrl` 仍保留，视频向量化继续走临时 URL（`media-url-expire-seconds`）
- 配置位于 `application-dev.yml` 的 `fafa.cos`，密钥通过环境变量 `FAFA_COS_SECRET_ID` / `FAFA_COS_SECRET_KEY` 注入；MinIO 配置保留，`fafa.storage.type` 可随时切回
- 代码中不存在图片转 base64 的逻辑，百炼/qwen 直接以 URL 拉图，无需改造
- 已知遗留：`OssStorageService` 依赖的 `OSS` bean 无装配工厂（`fafa.storage.type=oss` 会启动失败），属既有问题，本次未修

#### 3. 检索融合（`PhotoController#search`）

- 删除旧 `GET /api/photos`（确定性）与 `POST /api/photos/search/semantic`（语义），统一为 `POST /api/photos/search`（请求体 `PhotoSearchRequest`，返回 `PageDTO<MediaDTO>`）
- 分流规则：query 为空 → 确定性分页检索；query 有值 → 语义检索，petId/日期下推网关，tags 在 MySQL 补全阶段做 OR 硬过滤（网关不支持 tags），协同成员按 READ_RECORD 放行且 scopeUserId 解析为素材归属人
- Agent 内部通道不受影响：`InternalAiQueryController#searchMedia` → `semanticSearchForUser`（`SemanticSearchCommand` / `SemanticSearchResultDTO` 保留），旧公开入口 `semanticSearch` 已删除

包装图片识别任务流：创建 → COMPLETED → confirm（生成食品卡）/reject；EXPIRED 表示超时未处理。

### 创建包装识别任务

```
com.fafa.interfaces.controller.FoodRecognitionController#create
```

Body：`petId`、`mediaId`（待识别的包装图片媒体 ID）必填；`idempotencyKey` 选填（≤100），相同用户和幂等键不会重复创建任务。

### 查询识别任务

任务需处于 COMPLETED 状态且支持幂等重复提交。Body 为用户核对修正后的食品卡字段（`name`、`foodType` 必填，其余与食品卡创建一致），确认后自动创建食品卡。
