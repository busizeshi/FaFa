## 1. 第一阶段要交付什么

用户能够用邮箱注册登录，建立宠物档案，记录照护事实、保存照片和资料、设置并完成提醒、维护食品与喂食计划，最后查看首页概览和导出资料。管理员能够处理反馈、管理品种和赠送测试额度。

第一阶段完成后，即使 Python AI 服务关闭，以上功能仍正常使用。家庭协作、AI 生成/检索、公开社区、支付和 3D 留在后续阶段；第一阶段的数据保留主人与操作者字段，为家庭协作提供基础，但不提前建设邀请和授权全套功能。

### 2.2 应用职责

~~~mermaid
flowchart LR
  APP[移动 APP] --> GW[Gateway]
  WEB[管理 Web] --> GW
  GW --> BIZ[Biz]
  GW --> ADM[Admin]
  ADM -->|类型化 Dubbo 契约| BIZ
  BIZ --> DB[(业务 MySQL)]
  ADM --> ADB[(管理 MySQL)]
  BIZ --> R[(Redis)]
  BIZ --> O[(私有 OSS)]
  BIZ --> Q[RabbitMQ]
  S[PowerJob 扫描器] --> BIZ
  Q --> W[媒体/导出/通知 Worker]
~~~

Biz 拥有 P0 全部业务事实与事务。Admin 只拥有管理员身份、角色与后台操作审计；业务改动经专用 RPC 调 Biz，不直接连接业务库修改表。Worker 按具体用例处理文件、通知、导出，不新建一个允许任意任务/SQL/脚本的万能执行平台。

P0 文件处理和导出 Worker 可作为 Biz 应用的异步消费者组件，先不另拆部署服务；达到独立扩容需求再拆。Python 无模型调用，也不承担必须依赖 AI 服务才能执行的常规导出。

## 3. 最先实施：第一批 WP00 + WP01

这一批的可演示路径是：

~~~text
读取协议 → 输入邮箱/密码 → 发送验证码 → 验证并创建账号
→ 建立会话 → 读取 bootstrap/个人资料 → 退出 → 再次登录
→ 另一设备登录后旧设备失效 → 找回密码 → 新密码登录
~~~

暂时没有宠物时 bootstrap 返回 NO_PET。其余页面不返回伪造宠物、记录或余额；第一批用 API 客户端完成真实后端验收，移动框架确定后再接对应页面，不用临时业务 UI 充当生产 APP。

### 3.1 WP00：接口、路由与持久化基线

按以下顺序实施：

1. **盘点与构建基线**：记录 git diff；在不改变依赖版本的前提下验证现有 Java/Python 构建；发现既有失败时单独记录和修复必要阻塞。
2. **路由基线**：APP /api/v1/** 去除 /api 转发至 Biz /v1/**；Admin /api/admin/v1/** 去除 /api/admin 转发至 Admin /v1/**。
3. **公网隔离**：不建立 /api/v1/internal/** 一类透传入口；旧 /api/biz/**、/api/ai/** 仅本地兼容环境可用，生产默认关闭。旧 broad admin 路由不能抢先吞掉新的 v1 路由。
4. **响应与错误**：保持 R 的四个字段；定义 ErrorDetails 与 FieldErrorDetail，映射 HTTP 状态、业务 code 和字段提示；校验失败不得返回 200。
5. **身份边界**：Gateway 不接受客户端伪造 X-User-Id/X-Operator-Id；Biz 从认证上下文取身份，不能仅信网关注入 ID。公开路由白名单显式维护。
6. **数据库接入**：Biz 业务库、Admin 管理库分账号/权限；加入 Flyway 和实际仓储依赖，配置 UTF-8、UTC 时间读写及连接超时。
7. **契约目录**：建立 app-v1.yaml、第一批请求/返回示例、错误码映射与页面关联；只写已明确的第一批契约，不生成全部 200 个空接口。
8. **运行与验证**：dev 配置能不依赖真实 SMTP 启动，接本地邮件捕获服务；测试与生产配置分离。

路由验证必须用真实目标路径检查，不能只验证 Gateway 200。例如 /api/v1/me 应到 Biz /v1/me；而不是由于路径错误返回内部默认页后仍被认为连通。

错误码对外保留现有 FAFA-* 格式，总规划中的 SESSION_REPLACED、VERSION_CONFLICT 等作为语义标识映射到唯一线码，放入契约表。ErrorDetails.fieldErrors 使用 field、code、message；其中 code 是稳定字段错误标识。APP 按 code 分支，不解析中文/英文 message。新增错误不能与既有线码复用成不同含义。

### 3.3 第一批表与安全数据

| 表 | 关键字段 | 约束与说明 |
|---|---|---|
| user_account | id、emailCanonical、emailDisplay、passwordHash、status、authVersion、createdAt、updatedAt、version | emailCanonical 唯一；authVersion 用于敏感操作撤销会话；不存明文密码/确认密码 |
| user_profile | userId、nickname、signature、avatarMediaId、timezone、version | userId 唯一；默认随机昵称；头像本批留空 |
| user_consent | id、userId、purpose、documentVersion、acceptedAt、withdrawnAt | 记录实际同意版本；不只存一个永远为 true 的字段 |
| legal_document | id、type、version、body/受控内容标识、contentHash、status、effectiveAt | type+version 唯一；本地样本文本不宣称已完成正式法律发布 |
| auth_challenge | id、purpose、targetCanonical、codeHmac、expiresAt、attempts、maxAttempts、consumedAt、sendState、version | challengeId 唯一，用途隔离；有索引便于过期清理 |
| auth_ticket | id、purpose、userId、tokenHash、expiresAt、consumedAt、version | 重置/重新认证票据；明文只返回一次 |
| security_audit | eventId、actorId 可空、action、safeTarget、result、occurredAt、requestId | 不存验证码、Token、密码或邮件正文 |

Sa-Token/移动会话存 Redis；账号、密码、一次性敏感验证的权威结果在 MySQL。Redis 限流丢失不能导致已用过的重置票据复活。邮箱 challenge 消费和创建账号/更改密码等业务在同一数据库事务内完成，避免 Redis 消费成功而 DB 失败导致状态无法解释。

鉴于本阶段部署规模，首批挑战存 MySQL、Redis 负责短期节流即可，不再同步保存第二份 challenge 状态。注册验证防重由 challenge 条件更新和邮箱唯一键共同保证。

公共前缀 /api/v1。细节沿用总规划，以下为本批必须真实实现的集合：

| API | 主要请求 | 成功结果 | 页面 |
|---|---|---|---|
| GET /legal-documents | type/version | 当前发布版本及正文 | auth.legal/welcome/register |
| POST /auth/email-challenges | purpose、email | challengeId、expiresAt、resendAfter | auth.register/forgot |
| POST /auth/registrations | challengeId/code/email/password/confirmedPassword/legalVersions | 已创建账号、会话信息 | auth.verify |
| POST /auth/sessions | email/password/device | Token、有效期、user | auth.login |
| DELETE /auth/session | 当前身份 | 成功退出 | me.logout |
| POST /auth/password-reset-tickets | challengeId/code | resetTicket、expiresAt | auth.forgot |

### 3.5 关键事务与竞态

**注册事务：**

1. 校验邮箱、密码与协议版本。
2. 锁定 challenge，检查 REGISTER、目标邮箱、有效期、尝试上限、发送状态。
3. 失败验证码计数作为独立安全状态更新并提交，不能被后续异常回滚；成功验证码再进入账号创建事务锁定并条件消费。
4. 同事务创建 account、profile、consent、消费 challenge；唯一邮箱冲突时不创建重复用户。
5. 提交成功后创建 Sa-Token 会话；若会话存储暂时失败，账号保持已创建，返回明确登录可重试状态，不回滚用户造成误解。

失败尝试计数不能只在事务内自增后抛异常让事务回滚；并发核验必须按 challenge 行锁/条件更新限制次数。密码和邮箱规范化规则在注册/登录/找回一致。

**重置密码事务：** 验证并一次性消费 resetTicket → 更新 hash 和 authVersion → 提交 → 撤销旧移动会话。Biz 每次认证比较有效 authVersion（可受控缓存失效），撤销 Redis 会话异常不能允许旧密码会话无限继续。

**单设备会话：** 两次登录竞争同一用户时，按用户会话代际原子替换。不要只配置客户端弹窗；旧 Token 实际请求必须失效，返回 SESSION_REPLACED。

**注册重试：** 第一批注册不缓存带明文登录 Token 的通用幂等响应。账号创建由挑战/唯一键保证一次，响应丢失后客户端可用刚设置的密码登录；不能重复创建账号。通用幂等工具在 WP02 的 createPet 首个非敏感写入中落地，存储加密/清理策略另按数据敏感度处理。

### 3.6 邮件与密码策略

- 验证码为 6 位、10 分钟、重发间隔 60 秒、单 challenge 5 次尝试；策略进入类型化配置。
- 重发新 challenge 时原 challenge 失效；用途不同不能互换。
- 使用含服务端秘密的 HMAC 保存验证码，密钥从部署配置注入。
- 密码至少 8 个字符且包含字母与数字，允许粘贴，长度上限 128，不静默截断；Argon2id 参数经实际依赖和性能验证后锁定。
- 找回申请对存在/不存在邮箱给一致提示；内部发送只对实际可重置账号进行，避免日志或明显响应结构泄露。
- SMTP 使用接口适配，开发走本地邮件捕获服务，测试再接真实邮箱；生产凭证不进入仓库。
- 首批 SMTP 在事务外发送，超时设置明确；“SMTP 已接受”不等于最终送达，页面允许重发。不能成功返回一个实际从未发送的 challenge。

邮件发送不跨 MySQL 事务：先记录 PENDING challenge → 发送 → 更新 SENT/FAILED；只允许 SENT 校验。进程在 SMTP 接收后、标记 SENT 前崩溃可能导致收到不可用邮件，应提示重新发送并失效旧挑战，不假装具备端到端 exactly-once 邮件。WP07 接入 Outbox 后再增强邮件恢复，不为首批提前建 RabbitMQ。

### 3.7 第一批完成标准

1. 全新数据库能自动迁移并启动 Biz；测试账号从真实 API 创建。
2. 本地邮件捕获中能看到验证码，注册成功；过期、错误、重发、用途互换、并发注册均有测试。
3. HTTP/业务错误、字段错误、requestId 与 OpenAPI 一致，API 客户端可定位字段。
4. 重置后旧会话失效；新设备登录后旧 Token 被服务端拒绝。
5. bootstrap 能区分匿名、有效账号且无宠物；/me 不能被其他用户 ID 或伪造头读取。
6. 私人/内部 API 不经旧 Gateway 公网路由泄露；生产默认不公开 Python。
7. 邮件依赖失败有明确状态，日志无敏感值；提供已验证运行与请求示例。

## 4. 第二批：WP02 宠物 + WP03 额度与后台

### 4.1 宠物实施顺序

字典 → 最短建档 → 列表/详情/修改 → 当前/默认宠物 → 归档/恢复 → 删除申请/撤回。

第一张头像尚未接 OSS 时保持可选，不上传占位文件。初次体重创建独立测量事实可延至 WP05 接入，此前不能把临时 profile.weight 当作未来永久数据源；对应控件延后开放。

新增 pet、pet_deletion_request、pet_breed、user_preferences、idempotency_request。pet 保存 ownerUserId、createdBy、status、生日/估算月份、version；昵称/物种之外可后补。删除申请有 previousStatus 和 deleteAfter，归档不设置 deleteAfter。

P0 AccessPolicy 只实现 owner 检查和宠物状态；接口接收 ActorContext，为 P1 增加授权查询留清楚入口即可，不提前造空家庭表、假成员或复杂策略语言。

### 4.2 通用幂等的首个真实用例

createPet 要求 Idempotency-Key；唯一键 actorId+operation+key，存 requestHash、state、resourceId、响应中必要安全字段。执行中返回已有操作状态；同键不同内容 409；创建和幂等结果同事务提交。缓存丢失仍由数据库唯一键兜底。

不得用分布式锁代替业务唯一约束，或使用“查一下没有再插入”的竞态实现。时间戳和服务端派生字段不能使同一业务请求重试时 hash 不稳定。

### 4.3 额度和管理员

先实现 STORAGE_BYTES bucket 与账本/预占；AI_POINTS 的枚举/DTO 可以定义，但不伪造 AI 消费、充值或支付逻辑。

新增 quota_account、quota_reservation、quota_ledger、grant_request。后台在自己的库建立 admin_account、role、permission、admin_role、role_permission、admin_audit；首位管理员通过一次性初始化命令/部署秘密创建，不在源码内放默认密码。

管理员登录 → 查询额度申请 → 批准并附原因 → 专用 Dubbo RPC → Biz 锁 quota_account、记唯一赠送流水 → 返回新额度 → Admin 审计。approve 与额度发放要有跨应用可重试的业务操作 ID，不能 Admin 标已通过而 Biz 永远未发放。

后台先完成 API 与权限验证，真实管理 Web 页面在后端稳定后再接入；使用权限码而非前端隐藏按钮作为保护。

### 4.4 验收

- 用户只填昵称和物种即可建档；越权读/改他人宠物返回拒绝。
- 相同幂等键并发创建返回同 petId，换内容返回冲突。
- 归档资料仍可读，归档 15 天不删除；恢复不突然激活停用任务。
- 额度赠送重复请求不重复到账；账户不能因并发预占变成负数。
- Admin 不持有业务数据库直接写权限，额度动作留原因/操作者/操作 ID。

## 5. 第三批：WP04 媒体 + WP05 第一条记录

### 5.1 先跑通单图，再扩文件类型

单图上传：APP 选图 → POST upload-sessions → Biz 鉴权/预占 bytes → OSS 受限直传 → complete → 服务端查对象/验证类型与大小 → 缩略图 → READY → 绑定头像或记录。

先接图片，随后补 PDF 附件和视频/封面/转码。三者最终均属于 WP04 完成要求，不因第一张图成功就宣布全部媒体模块完成。具体格式和工具链接入时依实际版本验证。

新增 upload_session、media_asset、media_binding、album、album_item。会话完成和额度结算幂等；断点/取消/过期均能对账；Bucket 私有，禁止返回长期访问密钥。

图片处理先完成一条有状态链路；开始视频转码等长任务时，在 WP04 内接入 RabbitMQ、outbox_event、consumer_inbox 与 media_processing_job，持久化任务、租约和重试。不能在 HTTP 里转码，或只用 @Async 丢进进程内存。WP07 复用这套消息设施，不再另建一个不同的 Outbox 实现。

相册 CRUD 和精确筛选同批接入；删除相册只解除成员关系。暂不接 Qdrant，不把图片“处理中”与“AI 索引中”混成一个状态。

### 5.2 记录的纵向切片

先实现 FEEDING，再 WATER、WEIGHT：

1. 建 care_record 与 typedPayload/版本；为需要趋势的指标建同事务投影。
2. 创建记录校验宠物 ACTIVE、本人权限、附件 READY 和归属。
3. 返回统一 RecordSummary，列表和详情使用同一展示投影。
4. 保存后首页入口刷新，不让不同页面各算一套标题/实际摄入。
5. 补编辑/版本冲突/删除影响；上传失败时文字保留。

实际投喂与实际食用分开；多食品按 item 记录。饮水观察不变成 ml；体重按发生时间排序，补录历史不覆盖最新体重。

### 5.3 可演示验收链

登录 → 建“雪球” → 上传早餐照片 → 记录投喂 30g、实食未知 → 记录列表 → 详情看到照片和未知实食 → 修改到 32g → 趋势/摘要按事实更新 → 删除相册，原记录照片仍可访问。

另用第二账号猜测同一 recordId/mediaId，必须无法读取/签下载地址。上传额度不足必须在签凭证前拒绝。

## 6. 第四批：WP06 完整记录 + WP07 提醒与信箱

### 6.1 记录与笔记扩展

| 子任务 | 具体交付 | 重点验收 |
|---|---|---|
| 健康记录 | 疫苗、驱虫、用药、就医专用字段/表单/附件 | 医疗原文与主人观察分开；不自动推算剂量/周期 |
| 日常与花费 | 观察、洗护、花费 CRUD，币种分组汇总 | 金额十进制；不把不同币种直接相加 |
| 自定义类型 | 最多 10 字段、有限类型、schemaVersion、停用 | 改类型不破坏旧记录；不执行公式或脚本 |
| 笔记 | Markdown/表格/标签/媒体与安全渲染 | 往返编辑不丢结构；标签删除不删正文 |
| 手动成长 | 标题/副标题/日期/描述/排序素材 | 首页与宠物详情可查看；不依赖自动 AI 周小记 |

没有提醒基础前，健康表单可保存 nextDate 资料但不能展示“已启用提醒”；WP07 完成后开放“加入提醒”并同事务建规则/实例，已有资料由用户显式确认转成提醒，不后台自动补建。

### 6.2 提醒拆成三步

1. **先做任务语义**：规则预览、实例、列表、完成/跳过/延期；不接供应商也能验证站内状态。
2. **再做可靠调度**：PowerJob 展开与触发扫描、Outbox、RabbitMQ、重试/死信/对账。
3. **最后做外部投递**：设备登记、通知授权/免打扰、推送适配与真机测试。

新增 reminder_rule、task_occurrence、note_task_link、notification、notification_recipient、delivery_attempt，复用 WP04 的 outbox_event 与 consumer_inbox。任务与业务事实必须同一 Biz 事务完成；发推送是异步副作用。

首期只做预定义重复子集，每次保存返回未来 5 次预览；规则展开未来 7 天。月底和时区含义采用总规划，测试必须覆盖非东八区/夏令时，不能只测服务器本地时间。

### 6.3 完成任务的实现

普通待办可直接标完成；喂食/医疗/体重等必须先收集所需事实字段，再由同一用例写记录和更新实例。不要页面先创建 records，再请求 task complete，造成中间失败后重复操作。

任务条件更新 PENDING + version → COMPLETED，失败返回最新状态。虽然 P0 没有家庭成员，也要用两个并发请求证明同一实例不会完成两次。

### 6.4 验收

- 重复保存笔记 task block 不生成重复待办。
- 扫描重跑、消息重复和消费者宕机后恢复不新增重复实例。
- 免打扰或关闭系统通知不影响站内待办；不存在“收到推送即算完成”。
- 推送服务接受、系统到达、用户已读是不同状态；真机关闭 APP 后验证实际表现。
- 至少有一个真实目标平台的推送联调记录；准备发布哪个平台，就完成哪个平台的验收。

## 7. 第五批之一：WP08 食品与喂食计划

食品卡 → 食品版本 → 能量单位换算 → 计划预览 → 计划保存/暂停/修改 → 任务 → 填实际记录。

新增 food_card、food_card_version、feeding_plan、feeding_plan_version、feeding_plan_item。计划引用具体食品版本与 gramsPerOccurrence，历史记录保存用量/能量快照。

| 用例 | 处理 |
|---|---|
| 每天 08:00、18:00 喂两种食品 | 一条计划、多时段、每次若干食品项，由 reminder 展开实例 |
| 改食品包装热量 | 生成食品新版本，提示是否更新计划，不改过去记录 |
| 从下周开始减小计划量 | 新计划版本从 effectiveFrom 生效，仅替换未来未完成实例 |
| 食品热量未知 | 返回 hasMissingEnergy，不显示错误的零热量/完整总量 |
| 食品停止使用 | 停用，旧计划/记录仍能读历史版本 |
| 手动推荐量工具 | 先交付包装能量/份量换算；未复核营养规则不开放 RER/DER 推荐 |

从喂食类型页进入食品与计划；不新增一级导航。计划不会自动产生“宠物已吃”记录。

### 8.1 页面与接口集成

| me.preferences / inbox.list | 类别/提前量、免打扰、通知权限状态、阅读消息 |

| report.export / history / detail | 无 AI 数据报告，按宠物/日期/类型选择，生成任务、历史与下载 |

修改邮箱复用旧身份 reauth + 新邮箱 challenge；修改密码校验当前密码，撤销旧会话。当前宠物与默认宠物分开，详情表单始终保留自己锁定的 petId。

### 8.2 数据报告与导出

P0 默认先支持 JSON/CSV/Markdown 数据副本和固定 HTML 照护报告；PDF 可用同一受控渲染链交付。AI 自定义叙述、周期报告、任意模板和长图创作不放进 P0。

用例：创建 export job → 冻结范围/版本 → Java 确定性汇总 → Worker 渲染/打包 → OSS 私有产物 → 信箱/邮件提示 → 鉴权领取短时下载。

导出引用原数据但不依赖原签名 URL 长期有效；产物计量、过期、清理有策略。报告正文不能执行用户 Markdown 中的脚本，附件链接重新鉴权。

### 8.3 删除作业必须闭环

WP02 可以先交付删除申请与等待期，但整个 P0 结束前必须交付到期清理，不能长期停在“已申请”。

清理顺序：冻结状态 → 取消任务/通知 → 删除私人业务与引用 → 检查媒体剩余引用 → 清 OSS 原文件/派生文件/导出 → 实际释放 bytes → 记录完成。P0 无家庭、社区、向量数据时不生成空清理阶段，后续按总规划增加真实消费者。

撤回和 PURGING 竞争用条件状态更新。作业按批/游标推进，失败可查可重试；备份恢复须重放删除墓碑。归档永远不经过这个自动到期清理入口。

## 9. 数据迁移和跨模块接口顺序

### 9.1 迁移约束

- 每个工作包只新增自己需要的表，实际 Flyway 版本号按仓库现存最大序号递增。
- 已被共享/测试环境执行的迁移不原地修改；变更新增 migration。
- 每表在设计时写清主键、唯一键、筛选索引、所有权、version、删除策略。
- 数据库字典种子可随迁移导入基础值，账号密钥和默认管理员密码不得作为种子。
- MySQL/Java 时间统一 UTC，用户的日期和计划另存 timezone；不依赖宿主系统当前时区。

### 9.2 本阶段应稳定的应用接口

| 提供模块 | 供其他模块使用的能力 | 不能泄露的实现 |
|---|---|---|
| identity | ActorContext、用户有效性、偏好读取 | Sa-Token TokenDAO、密码 hash、验证码仓储 |
| pet | PetOwnershipQuery、活动状态、基础摘要 | pet Mapper 与直接表更新 |
| usage | reserve/settle/release、grant、可用额度查询 | 直接改 used、绕过 ledger |
| media | assertBindable、attach/detach、访问地址签发 | 任意 objectKey、OSS 长期凭证 |
| care | 类型化创建/更新/查询、统计投影 | 无校验 payload Map、跨表 SQL 后门 |
| reminder | 规则/实例操作、同事务完成入口 | PowerJob 运行对象、队列直接发“完成” |
| journal | 笔记与 task block 链接 | 从正文二次猜测并重复创建任务 |
| report | 固定范围导出 job 与状态 | 任意模板执行、任意 URL 抓取 |

跨模块强一致调用放 application 用例，包依赖保持单向；通知/处理/清理副作用用 Outbox。避免为了复用把所有 Entity、业务枚举和应用服务塞进 common。

## 10. 配置、环境与启动约定

### 10.1 按批次启动

| 第一批 | MySQL、Redis；完整集成环境使用 Nacos；本地 SMTP 捕获；Java Gateway/Biz |

### 10.2 配置分类

安全密钥：数据库、Redis、SMTP、OSS、Sa-Token/内部签名等按环境注入。业务策略：验证码、上传大小/批量、保留期、重复扫描、额度和清理间隔使用类型化配置。公开能力：APP 通过 bootstrap 得到可用功能，但服务端仍校验，不能仅靠前端 feature flag 禁用能力。

测试环境可开启确定性 Clock/本地邮件捕获与供应商测试适配，必须明确 profile，并禁止在生产启用“固定验证码/跳过鉴权/假上传成功”。

### 10.3 尚待填写的外部配置

移动框架、管理 Web 框架、生产地域/正式协议、邮件域名、OSS Bucket、推送通道、测试赠送空间均需在对应批次前确定。它们不阻止第一批后端契约与账号实现；涉及实际用户信息的生产上线要等配置、文本和通道验证完成。

## 11. 验收与测试分层

### 11.1 每批最低检查

| 层次 | 重点 |
|---|---|
| 单元测试 | 邮箱/密码规则、类型字段、能量换算、日期/周期、权限与状态迁移 |
| 集成测试 | MySQL 唯一键/回滚/版本冲突、Redis 会话、幂等/预占、Outbox、重复消费 |
| 契约测试 | OpenAPI、R/错误结构、数值字符串、时间格式、operationId 和 pageKey |
| HTTP 联调 | 请求经过 Gateway 到真正 Controller，状态码、路径和 requestId 正确 |
| 供应商/真机 | SMTP 收信、OSS 校验、PDF/视频处理、目标平台后台推送 |
| 端到端 | 注册→建宠→上传→记录→提醒→完成→导出→注销撤回/清理 |

单元测试替身不能替代数据库并发或真实推送测试。文案/样式等低风险改动不为覆盖率写重复实现测试。

### 11.2 五条第一阶段发布门槛

1. **事实正确**：计划、提醒、通知和实际记录分离；历史数值不被未来食品/计划修改。
2. **隐私隔离**：两账号互测宠物、记录、媒体、导出、通知均不能越权；内部接口不能公网绕过。
3. **不重复**：重复提交、并发完成、消息重投、回调重放不产生重复记录或账务。
4. **可恢复**：上传失败、SMTP/OSS/推送故障、清理中断、数据库恢复有状态、重试和审计。
5. **后端可交付**：真实 API、错误/状态、OpenAPI 与验收记录完整，后端按 API 客户端验证通过；随后再开始安卓 APP 和管理 Web 接入，页面消费契约不以 mock 成功替代后端事实。

详细异常场景沿用总规划 AT01～AT24、AT25、AT33 中适用的存储并发、AT42～AT44；家庭、AI、社区专属场景不在 P0 假测通过。
