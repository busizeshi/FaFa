# FaFa Java 与 Python 服务端脚手架搭建方案

- 文档状态：实施方案
- 更新日期：2026-10-20
- 相关文档：[技术选型.md](技术选型.md)、[功能描述.md](../功能描述.md)

## 1. 目标与已确认决策

本方案用于分阶段建立 FaFa 服务端基础工程，为业务开发准备项目结构、依赖管理、服务边界、异常处理、配置、日志和 Docker 部署方式。

- 仓库新增两个服务端分类：fafa-java、fafa-python。
- fafa-java 是 Maven 聚合工程，包含三个独立运行的 Java 应用：fafa-gateway、fafa-admin、fafa-biz。
- fafa-common 是共享 JAR，不单独部署；不创建 fafa-contracts。跨服务 RPC 接口、DTO、公共响应、错误码和异常类型统一放入 fafa-common。
- fafa-biz 采用 DDD 思想组织宠物、养护记录、提醒、相册、社区等领域模块；首期由一个 Biz 应用承载。
- fafa-python 是一个独立的 FastAPI 服务，承载 AI 能力，不直接读写 Java 业务数据库。
- 主云使用阿里云，文件使用 OSS，模型使用阿里云百炼/Qwen。邮件先接个人 SMTP 代理，后续可替换。
- 使用 Docker 与 Docker Compose，不引入 Kubernetes。
- Java 21、Python 3.12 为基础版本。首期版本统一锁定如下：

| 组件 | 版本 | 说明 |
|---|---:|---|
| Java | 21 | LTS |
| Spring Boot | 3.5.16 | 与 Spring Cloud 2025.0 / Dubbo 3.3 兼容 |
| Spring Cloud | 2025.0.3 | 对应 Spring Boot 3.5.x |
| Spring Cloud Alibaba | 2025.0.0.0 | 对应 Spring Cloud 2025.0、Spring Boot 3.5；Nacos Client 3.x |
| Apache Dubbo | 3.3.6 | 使用 Triple 协议，Admin 调用 Biz |
| MyBatis-Plus | 3.5.17 | 预留 Boot 3 Starter 版本管理，数据库模块接入时再启用 |
| Knife4j | 4.5.0 | Java Servlet API 文档 |
| Python | 3.12 | 由 `.python-version` 固定 |
| FastAPI | 0.140.13 | 由 `uv.lock` 固定 |
| Nacos Server | 3.0.3 | 与 Spring Cloud Alibaba 2025.0 使用的 Client 对齐 |
| MySQL / Redis | 8.4 / 7.4 | Compose 核心开发服务 |

Spring Boot 3.5.16 是当前为 Dubbo 3.3 兼容而选定的 3.5 补丁版本；Spring 官方说明该版本是 3.5.x 的最后一个 OSS 版本。生产上线前应复核支持周期，并优先在 Dubbo 与生态完成 Boot 4 兼容验证后升级，不应把旧版本长期留在生产环境。

整体调用关系：

FaFa APP / 管理端 → Gateway → Admin 或 Biz；AI 功能开放后，Gateway 也可路由到 FastAPI。
Admin 通过 fafa-common 中的 Dubbo 契约调用 Biz。
FastAPI 通过授权后的 Biz 内部 API 获取业务资料，并调用阿里云百炼。
Biz 拥有业务事实数据；OSS 保存媒体文件，MySQL 保存业务数据与文件元数据。

## 2. 建议目录

- fafa-java/
  - pom.xml：Maven 聚合父工程、依赖版本和插件管理。
  - mvnw、mvnw.cmd：Maven Wrapper。
  - fafa-common/：共享 API、RPC 契约、响应、错误、异常、配置和日志上下文。
  - fafa-gateway/：Spring Cloud Gateway 应用。
  - fafa-admin/：后台管理应用。
  - fafa-biz/：APP 业务应用及 DDD 领域模块。
- fafa-python/
  - pyproject.toml、uv.lock：Python 项目与可复现依赖。
  - app/main.py：FastAPI 应用入口。
  - app/api/：版本化路由。
  - app/core/：Settings、日志和应用生命周期。
  - app/schemas/：请求、响应和 AI 任务模型。
  - app/services/：AI 用例编排。
  - app/integrations/：百炼与 Biz 内部 API 客户端。
  - Dockerfile。
- deploy/docker-compose/
  - compose.dev.yaml、compose.prod.yaml、.env.example。
- docs/：保留现有项目文档并补充服务端运行说明。

Java 包名暂按 com.fafa 规划；建工程前检查仓库现有约定。真实密钥不写入仓库，.env.example 只包含变量名和示例说明。

## 3. Java 服务边界与依赖方向

### fafa-gateway

提供外部 HTTP 入口、路由和基础限流。Gateway 不承载领域规则，也不直接读写业务数据库。网关校验不能替代 Biz/Admin 自身的身份和资源权限校验。

### fafa-admin

提供后台账号、后台角色与运营管理 API。后台身份与 APP 用户身份分开。社区审核、举报和申诉按功能文档的 P2 阶段推进；Admin 首期范围以实际运营需求为准。

### fafa-biz

Biz 独立部署，内部模块按领域边界组织。建议初始领域模块：

| 模块 | 职责 |
|---|---|
| identity | APP 账号、个人资料与认证上下文 |
| pet | 宠物档案、归档状态和成员关系 |
| care | 日常记录、健康资料、喂食计划及事实来源 |
| reminder | 提醒规则、触发时间和处理状态 |
| media | 附件元数据、OSS 对象键、访问权限及记录关联 |
| sharing | 私人分享与家庭照护协作 |
| community | 公开社区和内容治理，按 P2 逐步实现 |

每个领域内部采用 interfaces、application、domain、infrastructure 四层：

- interfaces：HTTP Controller、Dubbo Provider 等入口适配。
- application：用例编排和事务边界。
- domain：实体、值对象、领域规则及仓储接口。
- infrastructure：MyBatis-Plus 仓储实现、OSS、消息与外部 API 实现。

首期只创建一个 fafa-biz Maven 应用，通过包结构、模块公开接口和代码评审守住领域边界，不为每个业务模块提前建立微服务。跨领域协作通过应用接口或稳定 ID 完成，不直接访问对方的 Repository 或表。未来拆分时再依据实际依赖、数据所有权和发布需求处理服务通信与数据迁移。

## 4. fafa-common、响应和异常处理

fafa-common 仅放多个服务都需要的稳定约定，包括：

- 统一 HTTP 响应、分页结构、请求 ID。
- 公共 ErrorCode 接口、通用错误码、FafaException。
- Admin 与 Biz 之间的 Dubbo 接口及其请求/响应 DTO。
- 通用配置、日志上下文和跨服务调用上下文。
- 确实被多个服务共同使用的枚举。

领域枚举留在所属领域模块，例如宠物类型、记录类型、提醒状态和社区内容状态。fafa-common 不依赖 Admin 或 Biz。

统一 HTTP 响应至少包含 code、message、data、requestId。Java 与 Python 遵守同一 JSON 字段约定，但不共用代码；各自维护服务专属 DTO。

Java 在 fafa-common 中提供通用异常类型和全局异常处理：

1. 参数校验错误返回字段级提示。
2. 未认证和无权限映射为不同错误码。
3. 业务异常返回稳定错误码和安全提示。
4. 未知异常返回通用服务器错误及 requestId，堆栈只写服务端日志。
5. Dubbo 边界分别处理业务异常与超时/网络异常；基础设施异常不能伪装为成功响应。

Controller 不重复拼装错误结构，也不静默吞异常。错误响应不暴露 SQL、堆栈、密钥或内部实现。日志避免记录密码、Token、邮件正文和宠物隐私资料。Python 使用 FastAPI 全局异常处理器，保持响应字段一致，运维输出使用 logging。

## 5. 配置、日志、权限与文档

### Nacos 配置

- Nacos 用于 Java 服务发现和非敏感运行配置。
- 初始 Data ID 使用 `.properties`。当前 Spring Cloud Alibaba 2025.0 配置导入方式有 YAML 动态刷新异常报告，先用 properties 格式降低刷新风险；升级 SCA 后再复核并按团队习惯切换。
- 当前版本化配置放在 `docs/nacos/`：`common.properties`、`fafa-gateway.properties`、`fafa-admin.properties`、`fafa-biz.properties`。部署时发布到 `fafa` 命名空间、`FAFA_GROUP` 分组；各应用本地 `application.yml` 只保留服务名、Nacos 连接/认证/namespace 和所需 Data ID 导入。
- 共享配置放通用 Spring 设置及基础设施地址；Gateway、Admin、Biz 分别维护服务专属配置。Admin 与 Biz 的 schema、账号彼此隔离，Gateway 不配置数据库。
- 数据库密码、OSS 密钥、百炼 API Key、SMTP 凭证通过部署密钥或环境变量注入，不写入共享配置或代码仓库。
- Python 用自己的 Settings 管理配置，不直接复用 Java 配置类。

### 日志与诊断

Java 使用 Logback。Gateway 生成或接收 requestId，并将其传给下游；Admin、Biz、Python 记录同一 ID 以便串联日志。运行日志与后台操作审计分开。首期提供健康检查，Prometheus/Grafana 按部署需要接入，健康接口不返回敏感配置。

### 认证与权限

- APP 认证由 Biz 负责，Admin 使用独立后台账号和权限。
- Gateway 做入口级校验，Admin/Biz 仍执行自身授权。
- Biz 每次访问宠物、记录、附件和分享资源都检查当前用户与资源的归属或授权关系。
- OSS 长期密钥不下发到客户端；客户端直传时由服务端校验权限并签发短时凭证或上传地址。

### API 文档与 Javadoc

- Java HTTP API 使用 Knife4j/OpenAPI，生产环境限制文档入口。
- Python API 使用 FastAPI OpenAPI 文档，生产环境按需关闭公开访问。
- Javadoc 统一使用简体中文，重点覆盖 fafa-common 的公共接口、Dubbo 契约、关键配置和复杂领域规则；业务内部实现以清晰命名和模块 README 为主。

## 6. Python FastAPI 边界

FastAPI 是独立应用，不直接复用 Java Entity、Repository 或数据库表。首期只建立应用启动、健康检查、Settings、日志、统一错误响应和外部依赖配置入口。模型调用封装在 integrations 中，AI 用例编排放在 services 中。LangChain/LangGraph 在具体 AI 流程开始时按需加入；Qdrant 在语义检索阶段接入。

AI 对业务数据保持只读查询和待确认草稿流程。只有用户确认后，Biz 才创建或修改正式业务记录和提醒。

## 7. 阿里云与 Docker 成本策略

阿里云作为主云。ECS、数据库和 OSS 尽量放在同一地域，避免不必要的跨地域及跨云流量。首期不预设固定规格，按地域、折扣和预估用量比较月成本。

- 应用运行：阿里云 ECS 上运行 Docker 容器。
- 文件：OSS 私有 Bucket；数据库保存对象键和业务元数据；下载前校验权限并签发短时访问地址。
- AI：Python 调用阿里云百炼/Qwen，模型费用与应用服务器费用分开统计。
- 邮件：首期实现可配置 SMTP 发送适配器，先接个人邮件代理；更换供应商时不改注册/找回密码用例。
- 部署：本地和首期单机部署使用 Docker Compose。初期把 Java/Python 应用拆成独立容器；数据库等状态服务根据现金成本、备份能力和维护投入决定云托管或容器自建。
- 成本核算至少关注 ECS 常驻资源、MySQL/Redis、磁盘与备份、OSS 存储/请求/下行流量、模型输入/输出用量、邮件发送和日志保留。
- 控制台密钥、生产环境变量和证书不提交 Git；Compose 对外仅开放必要的 HTTP/HTTPS 入口，数据库、Redis、Nacos 等仅允许内网访问。

## 8. Compose 中间件分层

通过 Compose profiles 按需启动组件，避免开发时运行当前阶段用不到的中间件：

| Profile | 服务 | 用途 |
|---|---|---|
| core | MySQL 8、Redis、Nacos | Java 服务基础开发与配置发现 |
| async | RabbitMQ、PowerJob Server | 提醒触发、邮件重试等实际接入时启用 |
| ai-search | Qdrant | P1 语义检索开发时启用 |
| apps | Gateway、Admin、Biz、FastAPI | 本地联调或部署应用镜像 |

开发和生产配置分开管理。Compose 示例文件不含真实密码；数据服务声明持久化卷；Nacos 的公共配置与服务专属配置分开维护。

## 9. 分步搭建计划

| 阶段 | 工作内容 | 完成标准 |
|---|---|---|
| 0. 技术基线 | 核对 Java 21、Spring Boot/Cloud、Dubbo、Nacos、MyBatis-Plus、Sa-Token、Python 3.12 的兼容矩阵；确定 Maven 坐标、Python 包名和云地域 | 形成集中版本表；版本兼容；子模块不各自声明冲突版本 |
| 1. 工程骨架 | 创建 fafa-java Maven 聚合工程和 fafa-python 项目；加入 Maven Wrapper、Python 依赖锁定 | 两个分类可独立构建，不包含真实密钥 |
| 2. 公共基础 | 创建 fafa-common，建立响应、错误码、异常处理、公共 RPC DTO/接口、日志上下文和公共配置 | Admin/Biz 可依赖同一 JAR；Common 不依赖应用模块 |
| 3. Java 应用 | 创建 Gateway、Admin、Biz 三个可运行应用，配置健康检查、Nacos 和 API 文档 | 应用分别启动；Gateway 路由到 Admin/Biz |
| 4. Biz 领域结构 | 建立 identity、pet、care、reminder、media、sharing、community 包及依赖约定 | 领域边界清楚，无循环依赖和跨领域表写入 |
| 5. Python 骨架 | 建立 FastAPI、Settings、日志、健康检查和统一错误响应 | Python 可单独启动；缺少必要配置时明确报错 |
| 6. Docker Compose | 建立 core 与可选 profiles、持久化卷、健康检查和环境变量示例 | 按需启动基础设施；容器使用内网通信 |
| 7. 运行文档 | 写 Java/Python 启动、Nacos 配置、错误码、Javadoc 和 Docker 部署说明 | 新开发者可按文档启动服务 |
| 8. 云部署基线 | 在阿里云 ECS 用 Compose 部署应用，配置 OSS 私有 Bucket 和部署密钥 | Gateway 提供外部入口；Admin 和数据组件不直接暴露公网 |

基础验收以构建与启动检查为主：Java 聚合工程可打包，Python 服务可启动，Compose 服务健康，Gateway 路由可用；异常响应包含 requestId 且不泄露堆栈；Nacos 环境配置与生产密钥分离。

## 10. 本轮脚手架实施状态

- 已创建 `fafa-java` Maven 聚合工程、Maven Wrapper、`fafa-common`、Gateway、Admin、Biz 三个应用模块。
- 已建立统一 Java 响应、错误码、异常映射、requestId 传递和 Admin→Biz Dubbo 连通示例。
- 已按 DDD 建立 Biz 的 identity、pet、care、reminder、media、sharing、community 包边界。
- 已创建 `fafa-python` FastAPI 健康接口、requestId 中间件、统一错误响应、Settings、日志和 `uv.lock`。
- 已准备 Nacos 共享/服务配置模板，以及按 profile 启动的 MySQL、Redis、Nacos 和应用 Compose 定义。
- Java Maven Wrapper 聚合打包（跳过测试）成功，fafa-common Javadoc 成功生成。
- Python `uv lock --check`、依赖同步和源码编译检查通过；本机 HTTP 烟测确认健康接口返回统一响应并回传 requestId，未知路径返回统一 404 错误响应。
- Gateway、Biz 和 FastAPI 在本机以不连接 Nacos 的开发方式启动成功；经 Gateway 转发到 Biz 与 FastAPI 的路径均返回预期响应，Gateway 未匹配路由返回统一 404 响应。
- Admin 已通过聚合编译；由于本机没有 Docker/Nacos，未验证 Admin 在 Nacos 环境启动，也未验证 Admin→Biz Dubbo 实际调用。
- Compose 与 Java 应用 YAML 已做静态解析；本机未安装 Docker，未启动 Compose 容器或验证容器健康检查。
- 数据库迁移、认证授权、MyBatis-Plus 实际仓储、OSS、邮件、百炼调用和异步/向量组件留到对应业务集成时实现。

## 11. 部署前待确认项

这些事项不阻止建立骨架，但会影响生产参数：

1. 主要用户和数据部署地域：中国内地、香港或其他地区。
2. Admin 首期必须具备的运营功能。
3. MySQL/Redis 初期采用云托管还是自建容器。
4. 个人邮件代理用于开发验证，还是也承担初期线上发送。
