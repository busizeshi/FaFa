## 2. 用户完整链路和需求调研

FaFa 面向中国大陆猫狗宠主及共同照护者。首版完整提供低负担记录、按时照护、多人协作，以及食品、健康、回忆、AI 和社区能力。食品和医疗记录逐步形成可靠档案；AI 整理与解释已有资料，关键写操作由用户确认。

### 2.1 从安装到长期使用

1. 浏览欢迎介绍，阅读并同意当前版本协议，使用邮箱注册/登录。
2. 选择创建宠物或加入家庭。创建只要求昵称和猫/狗；加入前查看宠物和授权范围。
3. 今日首页显示当前宠物、今天照护状态和下一件待办；用户一键记录喂食或饮水。
4. 从首页、照护页或任务页低成本记录喂食、饮水、排泄、活动、体重、症状；之后能按日期查看由谁记录。
5. 添加食品资料、设喂食时间和份量；计划生成任务，执行时记录实际投喂。未完成任务不能推断没有喂过。
6. 宠主发限时邀请码并选择宠物和权限；照护者加入后能看授权任务，完成时同步执行人和时间，避免重复执行。
7. 记录疫苗、驱虫、体重、就医和附件；是否增加下一次提醒由用户决定，药物方案以兽医原医嘱为准。
8. 用户主动选择照片上传、确认宠物归属并浏览相册/时间轴；素材默认私密。
9. AI 查询授权范围内的历史或常识；如果请求记一条记录，先生成可编辑草稿，确认后保存。
10. 管理提醒、授权、导出范围，或发起归档、撤销授权、删除数据。

### 2.2 公开资料与产品含义

调研支持功能优先级，不代表所有受访者都会用 App，也不能直接推断 FaFa 的留存或付费率。

| 资料 | 可确认的观察 | 对 FaFa 的设计含义 |

## 3. 用户角色和授权规则

权限始终由服务端按用户、家庭成员关系、宠物范围、资源类型和有效期判定；前端按钮可见性不构成授权。

| 角色 | 默认可做 | 默认不可做 |
|---|---|---|
| Owner | 管理家庭、宠物、邀请和授权范围内数据；归档/删除/导出 | 转移所有权前退出或删除唯一家庭 |
| Admin | 管理明确授权的宠物与成员事务 | 自动取得所有权、他人账号或全部私密素材 |
| Caregiver | 查看指定宠物、创建照护记录、完成授权任务 | 修改 Owner 权限、删宠物、看未授权病历/费用/日记 |
| Viewer | 查看指定范围且未过期的资料 | 写记录、管理任务、下载受限媒体 |
| Public | 查看明确发布的公开快照 | 读取家庭私有 ID、生日、家庭信息、私有媒体和病历 |

权限按“宠物 + 资源种类 + 动作 + 有效期”表达。创建邀请时解释可见和可做内容；撤销后新请求立即拒绝，清理缓存，不再续期旧媒体签名链接。

## 5. 首版技术架构与消息队列

当前工作区包含 PRD、页面规格、接口契约和 Pen 资料；未发现可复用的 Java/Python 业务源码或 API 实现。因此以下是首版实现建议，不假定已有依赖。

| 层 | 首版建议 |
|---|---|
| iOS/Android | 优先 Flutter 一个客户端；若选原生，Swift 与 Kotlin 共用同一 REST 合约 |
| Java 业务端 | Spring Boot 模块化单体，按 auth、family、pet、care、food、health、media、community、privacy 分包，使用 Sa-Token |
| 数据存储 | MySQL 保存用户、家庭、宠物、记录、计划、权限、内容和任务；时间存 UTC，并保留业务时区/localDate |
| 消息队列 | **首版必需 RabbitMQ**，通过 AMQP 0-9-1；Java 使用 Spring AMQP，Python 异步消费者可使用 Pika |
| 图片与附件 | 私有对象存储（如 OSS），短期签名上传/访问；后台生成缩略图 |
| Python AI | FastAPI 内部服务，用于 AI、OCR/多模态等处理；Java 控身份、授权、数据取用和业务落库 |
| Redis/语义检索 | Redis 按缓存/限流需求采用；首版语义搜索和知识检索需有向量索引，可部署单节点 Qdrant；不替代 RabbitMQ |

RabbitMQ 与 Spring AMQP 提供任务队列、消息确认和消费者监听机制；RabbitMQ 官方文档说明了 publisher confirms、消费者 acknowledgements 和持久队列的行为。按当前 FaFa 规模，首版可使用一个受监控的 RabbitMQ 实例和持久卷；部署环境支持托管 RabbitMQ 时可减少运维。对运行环境要求更高可用时，使用 RabbitMQ quorum queues 或托管集群。不要因为启用消息队列就同时引入 Kafka、微服务集群或复杂工作流系统。Unity 不用于常规 2D 管理 App；Python AI 不直接访问或写 Java 业务数据库。

### 5.1 消息队列使用范围与消息契约

首版以下任务必须由 RabbitMQ 异步处理，并由 App 通过 job/operation 状态向用户反馈：媒体转码/缩略图/标签；食品与病历 OCR；语义索引和回忆搜索索引；通知投递；报告与数据导出；AI 长任务；公开内容审核与索引更新；数据删除及对象存储清理。快速的普通记录读写仍同步返回；长任务先返回 202 和 jobId，不能显示为已完成。

建议以一个 topic exchange 和按责任划分的 durable queues 起步，例如 media.process、ocr.process、notification.send、search.index、report.generate、export.generate、ai.run、community.moderate、privacy.purge。队列/路由名属于部署配置，最终以代码配置文件和运维手册为准。

消息体使用小型、版本化信封：messageId、eventId、eventType、schemaVersion、aggregateType、aggregateId、jobId、occurredAt、traceId。不要把用户密码、Token、病历原文、私有图片二进制或大段个人数据放进消息体；消费者按 jobId/业务 ID 从受控服务读取所需数据并重新鉴权。

### 5.2 投递可靠性与恢复

- **数据库 Outbox**：业务数据和 outbox 事件在同一数据库事务提交；发布器扫描 outbox 发往 RabbitMQ，收到 publisher confirm 后标记已投递。RabbitMQ 故障时 outbox 保留并重试，避免数据库提交成功但消息丢失。
- **至少一次投递**：消费者使用手动 ack，完成数据库更新/任务状态后再 ack。消费者崩溃会导致消息重投；系统按至少一次处理设计，不假设 exactly-once。
- **幂等消费**：以 messageId/jobId 建立去重记录或唯一约束；同一消息重放只返回既有结果，不重复发通知、创建报告或删除同一资源。
- **有限重试**：可恢复错误使用有上限的延迟重试和退避；参数化错误、权限错误或超过次数的失败进入 DLQ，不能无限 requeue。
- **死信处理**：监控 DLQ 数量、失败原因和消息年龄；管理员修复原因后可审计地重放。DLQ 转发必须使用有确认的可靠转发；对无法可靠配置 broker 死信投递的队列，先把失败消息与原因写入数据库失败记录/outbox，再 ack 原消息。用户界面显示 job 失败和重试入口，不把 DLQ 直接暴露给用户。
- **路由确认**：发布侧打开 publisher confirms 和 unroutable return 检查；不能只凭 publish 调用没有抛错就认为消息进入队列。
- **状态追踪**：每个异步任务有 operationId/jobId、状态、进度、attempt、错误码和可重试标记；服务端提供查询接口。消息只驱动任务，不作为用户可见的最终事实。

开发/测试可用 Docker Compose 单节点 RabbitMQ。首版运行环境至少配置持久队列和持久消息、磁盘告警、连接/队列监控、凭据隔离与备份；HA 是否使用 quorum 或托管服务按部署可用性要求决定。

### 5.3 模块依赖顺序

工程依赖顺序为：基础配置/数据库/消息队列/认证 → 家庭与宠物/权限 → 事件与任务/首页 → 食品与喂食、身体与医疗 → 媒体与回忆、账本与设置 → AI/报告 → 社区/审核/索引。**所有模块均属于同一个首版范围**；这个顺序只表示前置依赖和模块联调顺序，不代表分期发布。

家庭权限是宠物、图片、病历与 AI 的前置依赖。事件、任务和 Outbox 是提醒、趋势、报告、搜索、通知与导出的共同数据基础。

## 6. 前后端通用交互约定

### 6.1 请求与响应

- REST 前缀统一 /api/v1，客户端使用 HTTPS；认证使用安全会话凭据，刷新凭据存系统安全区。
- 服务端从会话确定用户，再检查家庭/宠物/资源授权；客户端传 householdId 只能选择上下文，不能授予权限。
- 成功响应统一 data/meta；失败含稳定业务 code、用户可读 message、fieldErrors、requestId 和 retryable。
- 时间使用带偏移 ISO 8601；数据库保存 UTC。日任务和按天统计另传家庭时区/localDate；事件发生时间与录入时间分开。
- 列表用 cursor；筛选变化废弃旧 cursor。修改带 revision/ETag；冲突刷新并保留未提交输入，不盲覆盖。

### 6.2 写操作统一状态机

编辑中先校验必填、范围、单位和附件状态；提交中禁用按钮并携带 Idempotency-Key；成功以服务端响应更新；失败保留输入并提供重试；冲突显示新版本/冲突字段；权限失效时清理私有缓存；断网或结果未知时标“待核实”，查询原 operation，禁止另发新操作。

离线只保留未提交草稿并标“尚未同步”。任务/给药是否已执行须由服务端或用户核对；推送不代表执行成功。

### 6.3 业务事实规则

- 任务是计划和完成确认；事件是实际发生。未完成不等于没有喂食/用药。
- 完成计划任务时，任务和事件在一个事务关联；唯一约束防止并发重复完成。
- 计划外行为允许新建事件，但须明确选择，不能通过重试绕过任务唯一约束。
- 事件保留 happenedAt、recordedAt、recordedBy、performedBy、宠物/共享范围、source 和 revision。
- 体重、克数、能量用十进制；金额用最小货币单位整数。未知为 null/UNKNOWN，不显示成 0。
- 定性饮水不换算毫升；排泄、症状和摄入状态保留原始观察口径。
- 食品营养含单位、来源和核对状态；未知能量不参与精确总和。AI 不负责权威计算。
- 删除与归档分开；归档保留历史并暂停日程；删除显示影响并反馈清理任务状态。

### 6.4 常见错误和界面动作

| 错误 | 界面动作 |
|---|---|
| 401 会话过期 | 重新登录后恢复原页面，不重发写操作 |
| 403 权限不足/撤销 | 清理缓存并返回可访问页面 |
| 404 不存在 | 刷新来源列表，不泄露其他家庭资源是否存在 |
| 409 重复/完成/版本冲突 | 显示当前事实、执行人或冲突处理入口 |
| 422 字段/单位无效 | 字段旁说明，保留输入 |
| 429 限流 | 展示服务端提供的重试时间 |
| 413 文件过大 | 标出失败文件，可单独移除/压缩/重试 |
| 5xx/断网/结果未知 | 保存草稿、查 operation、提供手工入口 |
| AI 不可用 | 仍能查看普通记录，不伪造回答或行动 |
| 上传处理中 | 查 job 状态；真正成功前不显示“完成” |

## 7. 按模块开发和自测

API 组名和具体路径以接口与数据契约 v2.1 为准。模块完成意味着 UI、Java 后端、授权和本文自测均完成。

### M00 · 启动、注册、登录与隐私告知

**页面**：AUTH-01–05。  
**用户操作与呈现**：可跳过欢迎；登录/注册切换；密码显隐；显示协议版本、验证码倒计时和邀请上下文。相册权限在首次选图时才请求。  
**调用顺序**：BOOTSTRAP 读取服务/功能/协议/字典版本 → 用户同意后 AUTH 注册/登录 → challenge 邮箱验证或重置 → ONBOARD 取得家庭/邀请/建档入口 → 安全存储会话；退出时撤销会话。  
**异常**：验证码过期/错误、限流、断网、账号停用、协议没加载、注册超时应分别处理；登录错误不透露邮箱是否已注册。  
**首版自测**：只填邮箱、密码和协议即可注册；协议不同意不能继续；验证码重发和错误次数正确；重试注册不重复建账号；断网无假登录；登出后缓存不能打开旧账号页面。

### M01 · 家庭、邀请码、宠物档案和权限

**页面**：PET-01–05、FAM-01–05，包含照护交接卡。  
**用户操作与呈现**：建宠只需昵称和物种；未知生日/品种可保存；列表区分活跃和归档；邀请码显示范围/有效期；接受前展示邀请方、宠物和权限。  
**调用顺序**：ONBOARD 原子创建家庭+宠物或 INVITES 预览→接受 → PETS 列表与权限 → PET_DETAIL → 修改带 revision → 图片走 UPLOAD → INVITES/MEMBERS 管理授权 → PET_LIFECYCLE 归档/恢复、DELETION 删除申请。  
**边界**：未知年龄不当 0 岁；归档停止未来任务；切家庭清除旧缓存；撤销后旧会话不得读数据。  
**首版自测**：仅昵称和物种可创建；加入者只能见授权宠物；撤销邀请后旧链接不可用；撤销成员后 API/媒体均拒绝；并发编辑冲突保留输入；归档保留历史且不补发旧任务；无权角色不能删宠物。

### M02 · 今日首页、日程、提醒和任务

**页面**：TODAY-01–04、HOME-02、TODAY-02/03。  
**用户操作与呈现**：看当前宠物/全家、完成数、待办、快速记录、饮食/健康摘要、近期回忆；任务详情展示内容、宠物、到期时间、执行人、历史；完成/稍后/跳过/查看记录。  
**调用顺序**：TODAY 聚合 → TASKS/TASK_DETAIL → TASK_COMPLETE / TASK_RULES → NOTIFICATIONS → NOTIFICATION_PREFS → 刷新受影响分区。完成命令关联事件并带 revision/幂等键。首版先用前台刷新/轻量轮询满足实时状态，不额外引入复杂实时基础设施。  
**边界**：逾期是“待确认”，不指责用户；没任务和没记录分开；关闭系统通知不删除站内任务；时区变更保留本地计划时间。  
**首版自测**：完成任务显示执行人/时间；双设备并发只完成一次；昨日补录日期正确；通知关闭仍可用站内任务；一块失败不遮挡其它首页分区。

### M03 · 照护记录与日常观察

**页面**：CARE-01–04、DAILY-01–05。  
**用户操作与呈现**：快速记喂食、饮水、排泄、活动、症状/行为，之后按宠物、日期、类别、来源、记录人回看；无需每天填所有项。日常护理模板也包含在首版。  
**调用顺序**：QUICK_ACTIONS → 按事件 schema 显示最少字段 → EVENTS 创建并返回 ID/revision/发生/录入时间 → CARE-02 cursor 筛选 → EVENT_DETAIL 查看关联/修订 → 修改删除带 revision 并返回影响的首页/趋势/任务。  
**数据规则**：饮水定性和毫升分开；症状仅为用户观察，不自动生成疾病；无记录日期不插 0。活动首发可手工输入，不需后台定位。  
**首版自测**：新增后首页和历史一致；筛选重置 cursor；并发编辑显示冲突；定性饮水不计入毫升；删除前说明任务关联；空/加载/错误/无权/长备注均完整。

### M04 · 食品卡、计划和实际投喂

**页面**：FOOD-01–06、MIX-01–03、PLAN-01–05、FEED-01–03、PET-04。  
**用户目标**：保存食品信息、制定计划、记录实际提供/摄入，并能比较食品、管理批次库存、观察换粮情况。首版包括食品搜索/条码/OCR人工核对、私人食品卡、食品对比、搭配、能量估算、计划版本与预览、换粮观察、库存、投喂、摄入观察和趋势。  
**调用顺序**：FOOD_SEARCH 搜索候选（条码可返回多个版本）→ FOOD_CARDS 保存私人卡 → 食品版本保存来源/单位/物种/核对状态且被引用后不覆盖 → 计划 draft → DIET_CALCULATE 确定性计算 → PLAN_PREVIEW 显示差异/冲突/任务影响 → 用户确认后 PLAN_ACTIVATE → FEEDING_CREATE 关联任务/计划 → FEEDING_OBSERVATION 更新剩余和摄入观察 → FEEDING_STATS 返回计划、提供、观察和覆盖度。  
**首版自测**：无计划也能记一餐；未知能量不显示 0 或虚假总量；预览后版本变化需重预览；并发同一任务只记一次；计划外零食明确标出；“提供30g、剩余未知”不显示“摄入30g”。

### M05 · 身体、预防医疗、就诊和病历

**页面**：HEALTH-01、BODY-01–03、MEDICAL-01–07。  
**首版范围**：健康总览、体重、BCS/MCS 引导与记录、疫苗/驱虫、用药计划与给药确认、就诊资料、病历 OCR 校对、紧急联系资料和附件。  
**调用顺序**：HEALTH_OVERVIEW → METRICS/ASSESSMENT_GUIDES → PREVENTIVE_EVENTS；用户给出提醒日期时创建 TASK_RULE → MEDICATION_PLANS/MEDICATION_COMPLETE → VISITS/VISIT_DETAIL → OCR_JOB/MEDICAL_FILES → MEDIA_ACCESS 短期鉴权。用药剂量始终引用并展示兽医原医嘱。  
**边界**：不确诊、不自动建议周期/剂量、不建议停换药；急症只提供联系兽医/急诊入口。  
**首版自测**：体重点不覆盖历史且单位正确；BCS/MCS 量表有版本/来源；无下一日期不生提醒；OCR 未核对不落为事实；图片失败不丢资料；宠物 A 医疗不混入 B；给药执行按原医嘱核对；附件处理中/失效/无权分别呈现。

### M06 · 相册、回忆、日记和分享

**页面**：MEDIA-01–03、MEMORY-01–02、NOTE-01–02。  
**用户操作**：主动选图/拍摄，确认宠物归属；浏览回忆时间轴和相簿，按精确条件或语义搜索；编辑日记/里程碑故事；可请求 AI 标签或润色，但需确认后保存。批量上传、处理队列、媒体查看/归属、搜索、日记/故事和相关 OCR/索引能力全部属于首版。  
**调用顺序**：UPLOAD 校验并签名 → 客户端直传私有对象存储 → MEDIA_COMMIT 返回 job → JOBS 查状态 → MEDIA_LIST/DETAIL → MEDIA_ACCESS 访问前鉴权 → 修改归属/相簿/删除带 revision。OCR 只生成待核对草稿。  
**首版自测**：一张普通图可传；拒绝相册权限仍能拍照/选文件；失败项单独重试；撤权后媒体 API 拒绝；私有原图无永久公开 URL；语义索引失败时精确浏览仍可用；删除影响可见且派生图/索引最终清理。

### M07 · AI 助手与报告

**页面**：AI-01–03、REPORT-01–02。  
**首版范围**：AI 对话/流式恢复/中断、授权历史检索与知识来源引用、自然语言行动草稿确认、变化分析、健康/成长结构化报告及报告导出。所有 AI 写操作都由用户确认，报告使用固定模板和数据快照。  
**调用顺序**：AI_CHAT 提交文本、当前宠物和用户同意的附件 → Java 授权并最小范围取数 → 调 Python 内部服务 → 回答/引用/草稿 → AI_DRAFT 列出宠物、时间、事件、数值与未知项 → 用户编辑/取消/确认 → 重算 draftHash/短期确认凭据 → AI_COMMIT 正式写入。Python 不能拿客户端 petId 直接查业务库。报告使用固定模板和数据快照，经 REPORT_JOBS/JOBS 查询。  
**边界**：不确诊/开药/调剂量；不跨家庭；模型传输仅在授权范围内；草稿未确认不算正式事件。  
**首版自测**：只引用授权数据；无数据不编造；取消草稿不落库；编辑值最终生效；重复确认只写一次；Python 停机不阻塞其它记录；报告显示来源/缺项且不带入未授权日记。

### M08 · 我的、隐私、导出、帮助、账本与自定义

**页面**：MY-01–07、BILL-01–02、CUSTOM-01，均属于首版。  
**交互**：ME 管资料；NOTIFICATION_PREFS 管提醒；PRIVACY_PREFS 管用途/可见性；EXPORT_JOBS 提交范围并通过 JOBS 查询；DELETION 查询/取消删除；SUPPORT 反馈；账本和预算走 EXPENSES/EXPENSE_STATS/BUDGETS；自定义模板走 CUSTOM_SCHEMAS。  
**自测**：导出范围可选且预览私密材料；失败可重试、下载有期限；删号显示家庭/公开数据影响且可按规则撤销；关闭个性化后后续不再使用该目的数据；只读成员看不到未授权费用/日记；账本金额精确；自定义 schema 升级不会破坏旧事件读取。

### M09 · 发现、食品分享和社区治理

**页面**：DISC-01–10。首版包括发现/搜索、食品或搭配分享、点评/追评、点赞收藏、评论、作者背景、推荐说明、举报/屏蔽/申诉和审核队列。  
**发布前置**：公开字段白名单、版本快照、发布预览/撤回、内容审核、举报/屏蔽/申诉、审核状态追踪、公共与私有 DTO/媒体隔离。匹配只显示相似维度/缺失数据，不给临床适用结论或虚构分数。  
**验收**：访客只看公开快照；审核中不算发布；撤回后搜索/分享失效；更正不改写历史引用；举报与健康报告分开；推荐失败不影响食品浏览。

### M10 · 食品库存

**页面**：D10 FOOD-06。首版提供包装、批次、开封/到期、剩余量和购买金额管理及变更历史；库存数据与投喂所用食品卡关联。  
**验收**：家庭隔离；日期提醒由用户确认；修改可追溯；单位不明不换算；库存故障不影响投喂。

## 8. 首版模块实施顺序

下面是一个首版内部的开发顺序，不是阶段性发布计划。可以按模块提交和联调，但所有列出的模块必须集成到同一首版并通过第 9 节验收。

| 顺序 | 先完成的依赖 | 可进入联调的条件 |
|---|---|---|
| 1. 平台基础 | API 错误约定、数据库迁移、会话、权限、RabbitMQ、Outbox、job 查询 | 登录读写、队列发布确认、消费者幂等和任务状态可验证 |
| 2. 账号/家庭/宠物 | AUTH、ONBOARD、HOUSEHOLDS、MEMBERS、INVITES、PETS | Owner/照护者/只读角色边界可验证 |
| 3. 今日/任务/统一事件 | TODAY、TASKS、NOTIFICATIONS、EVENTS、QUICK_ACTIONS | 首页状态与两设备任务执行一致 |
| 4. 食品/计划/医疗 | 食品卡、OCR、比较、库存、搭配、计划、投喂、指标、预防、用药、就诊 | 食品计算未知值正确，任务与事件不重复，医嘱来源可追踪 |
| 5. 媒体/回忆/个人工具 | 上传队列、相簿、搜索、日记、账本、设置、导出、删除 | 异步任务/权限撤销/删除清理闭环可验证 |
| 6. AI/报告 | 只读问答、RAG/来源、草稿确认、基线、结构化报告 | AI 不越权、不直接写业务；job 状态可恢复 |
| 7. 发现/社区治理 | 发布、审核、搜索、点评、互动、举报、屏蔽、申诉 | 私有与公开数据隔离，审核/撤回/索引链路完整 |
| 8. 首版整体验收 | 全部页面、API、异步消费者、权限和通知集成 | 第 9 节全量验收全部通过后，作为一个首版发布 |

## 9. 首版跨模块验收矩阵

| 编号 | 场景与操作 | 通过标准 |
|---|---|---|
| E2E-01 首次使用 | 注册，只填宠物昵称/物种，记录喂食 | 可进首页并回查；无头像/生日/品种强制 |
| E2E-02 家庭防重 | A 完成任务，B 另一设备打开 | B 看到执行人和时间；同一任务不能重复完成 |
| E2E-03 补录与时区 | 记录昨日事件，并配置家庭时区 | 发生时间、录入时间、任务日期和月末周期行为一致 |
| E2E-04 两宠隔离 | 猫 A、狗 B 分别记体重/食品/病历 | 摘要、趋势、食品、附件和 AI 上下文不串宠 |
| E2E-05 授权撤销 | 撤销照护者后请求旧媒体和 API | 新请求拒绝、缓存清理、不泄露资源标题 |
| E2E-06 上传队列 | 多图上传，含超限/损坏文件 | 成功图可看；失败项单独说明/重试；处理中状态真实 |
| E2E-07 OCR 校对 | 上传食品标签和就医材料，修改识别值后确认 | 原件保留；OCR 未确认不成为事实；最终值为用户核对值 |
| E2E-08 食品计划 | 建食品卡/搭配/计划，预览后并发修改计划 | 过期预览拒绝生效；历史计划和投喂不被新版本覆盖 |
| E2E-09 能量与摄入 | 食品缺能量、记录提供量但未观察剩余 | 不显示虚假 0/总热量；提供量不冒充摄入量 |
| E2E-10 医疗安全 | 建用药计划、完成给药、录体重和 BCS/MCS | 原医嘱可追溯；未确认剂量不提交；趋势保留缺失和来源 |
| E2E-11 回忆与分享 | 上传素材、标记宠物、搜寻、写故事、发公开内容 | 私密默认；分享预览只含勾选字段；撤回后公共链接失效 |
| E2E-12 AI 确认 | 解析喂食文本、修正字段再确认 | 确认前无正式事件；确认后只写一次且使用修正值 |
| E2E-13 报告/导出 | 选定日期范围和数据类别生成报告/导出 | 202 仅表示受理；显示进度；范围、缺失和权限符合预览 |
| E2E-14 账本/自定义记录 | 新增支出和自定义字段记录，跨用户查询 | 金额精确；schema 版本可读；未授权用户看不到费用 |
| E2E-15 社区治理 | 发布待审核内容、点评、举报、屏蔽并撤回 | 待审不公开；举报可追踪；撤回清理检索结果；公私 DTO 隔离 |
| E2E-16 队列重复投递 | 消费者提交工作后、ack 前崩溃，RabbitMQ 重投 | 同一 job 不重复副作用；最后状态可查询 |
| E2E-17 队列暂不可用 | 停 RabbitMQ 后创建需要异步处理的记录，再恢复 | 业务事务/outbox 不丢；恢复后消息被发布并完成 |
| E2E-18 坏消息/DLQ | 令消费者对某 job 持续失败 | 达到上限后进 DLQ，不无限循环；修复后可审计重放 |
| E2E-19 通知失败 | 关闭推送或让通知消费者失败 | 站内任务仍正确；通知任务可重试且不重复发送 |
| E2E-20 外部服务故障 | 关闭 Python/对象存储/搜索服务 | 可用业务仍可用；异步失败显示可恢复状态，无假成功 |
| E2E-21 删除清理 | 撤销分享或发起宠物/账号删除 | 主库、对象存储、搜索索引和缓存的清理任务均可追踪 |
| E2E-22 无障碍/小屏 | 大字号、读屏、窄屏查看所有主要页面 | 主操作可见，图表有文本，页面无横向裁切 |

每条通过项记录客户端/设备版本、账号角色、测试数据、截图或 requestId、jobId/messageId；不能以“看起来正常”代替结果。异步工作除了返回 202 受理，还要分别验证成功、可重试失败、DLQ 和人工重放。

## 10. 首版范围控制与明确不包含项

当前 FaFa.pen 和配套规格已经设计的功能都按本手册纳入首版，不将这些页面功能推迟到首版之后。范围控制仅排除尚未进入 PRD/画布的额外能力：自动疾病诊断/开药/调剂量；未经用户授权扫描整本手机相册；无用户确认的自动公开发布；AI 任意生成并执行 HTML/SQL/后端写操作；复杂 3D/游戏化重做；自训练基础大模型；独立微服务/Kafka 大规模集群；与已有页面无关的预约交易、商城或智能硬件集成。

上述限制是首版安全与可实现边界，不影响已设计的 OCR 人工核对、AI 草稿确认、食品库存、完整社区审核或媒体搜索。

## 11. 更新规则与待定配置

UI 变更更新 Pen 页面 ID/页面规格；API 变更更新数据契约；首版完整范围变更需同步更新模块清单、消息类型、队列消费者和全量验收矩阵。医疗、AI、公开内容或数据可见范围变化要同步更新安全/授权验收。

OpenAPI 和部署配置定稿前仍需确认：验证码长度/有效期/重发限制、媒体大小/格式上限、删除撤销期、导出有效期、任务月末规则、通知渠道、家庭默认时区、RabbitMQ 队列与路由命名、重试次数/退避间隔、DLQ 保留期限和人工重放权限。业务规则尽量用服务端配置，并在 UI 显示用户需要知道的实际值。
