## 一、产品定位与核心原则

### 1.1 产品定位

> **记录它的一生，也让 AI 记住它的一生。**

FaFa 的核心是：**长期记录宠物数据 → 建立宠物数字档案 → AI 理解这些数据 → 帮助主人查询、分析、守护、回忆和创作。**

### 1.2 三条核心原则

1. **宠物是核心，不是社交关系**  
   数据结构围绕「用户 → 宠物 → 宠物数据」展开，而非「用户 → 用户 → 社交关系」。

2. **AI 不是独立聊天页，而是贯穿所有页面的智能层**  
   AI 是能力，不是一个孤立页面。用户在体重页、照片页、喂食页、报告页都能自然调用 AI。

3. **记录成本决定产品生死**  
   任何每日记录 ≤2 次点击完成。记录越轻松，AI 越有价值。

### 1.3 产品边界（红线）

明确**不做**：
- 社区/广场/动态/评论/点赞/关注/私信/附近宠友
- 商城/电商/二手交易
- 在线问诊/AI 诊断/处方建议（医疗合规红线）
- 智能硬件/IoT 联动
- 宠物交易/领养/配种
- 寄养/上门服务撮合
- 自动发布社交媒体内容（只生成内容，不负责发布）

## 二、技术架构与环境策略

### 2.1 技术栈

**后端（fafa-java）**：
- Spring Boot 3.x + JDK 17
- DDD 分层架构：接口层(interfaces) / 应用层(application) / 领域层(domain) / 基础设施层(infrastructure)
- Sa-Token：认证授权
- MyBatis-Plus：ORM + 分页 + 审计字段自动填充 + 逻辑删除
- Flyway：数据库版本管理
- Knife4j：API 文档
- Druid：数据库连接池 + 监控

**后端（fafa-python）**：
- FastAPI
- Qwen 系列模型（阿里云百炼）
- Qdrant：向量数据库

**存储**：
- MySQL 8.0：业务数据
- Redis：会话管理
- MinIO/OSS：对象存储
- Qdrant：向量存储

**消息队列**：
- RocketMQ：异步任务

### 2.2 环境与条件注册策略

| 能力 | dev（Windows本机） | test/prod（Linux） | 实现机制 |
|------|-------------------|-------------------|---------|
| 对象存储 | MinIO | OSS | `StorageService` 策略 + `@ConditionalOnProperty(fafa.storage.type)` |
| AI 任务投递 | HTTP 直推 | RocketMQ | `AiTaskDispatcher` 策略链（MQ 优先、HTTP 兜底） |
| MQ 消费者 | 不启用 | 独立进程启用 | `python -m app.consumer.photo_consumer` |
| Knife4j | 开 | 关 | spring profile 控制 |
| Druid 监控 | 开 | 关 | spring profile 控制 |

**硬规则**：
1. 环境差异只允许通过配置（profile / 环境变量）+ 条件注册切换，**禁止在业务代码里写 `if (env == dev)`**
2. 新增环境相关能力时，一律先抽策略接口再做条件注册

### 2.3 设计模式应用规范

| 场景 | 模式 | 落地位置 |
|------|------|----------|
| 对象存储 MinIO/OSS | 策略 + 条件注册 | `infrastructure/oss/StorageService` |
| AI 任务投递 MQ/HTTP | 策略链 + 工厂 | `infrastructure/ai/AiTaskDispatcher` |
| 模型选择 | 工厂 | `app/core/llm.py`（`Purpose` 枚举） |
| 回调处理 | 策略注册表 | `CallbackHandlerRegistry` |
| 健康预警规则 | 策略 + 注册表 | `HealthRule` 接口 + 规则集 |
| 报告生成 | 策略 | `ReportGenerator` |
| 会员限额 | 策略 | `QuotaPolicy` |

## 四、Phase 0：用户系统

### 4.1 功能概述

**核心目标**：实现用户注册、登录、信息管理和会员体系框架，为后续所有功能提供用户身份基础。

**业务价值**：
- 微信一键登录，降低用户注册门槛
- 不强制填写资料，提升首次体验
- 会员体系是商业化核心抓手，贯穿所有模块

### 4.2 详细功能点

#### 4.2.1 微信登录与注册

**功能描述**：
- 小程序获取微信 code → 后端换取 openid → 登录
- 首次进入自动注册并返回，**不强制填写资料**
- 再次进入直接跳转主界面，不重复弹登录

**技术实现**：
- 接口：`POST /api/v1/auth/wechat-login`
- 请求参数：`{ "code": "微信临时登录凭证" }`
- 后端流程：
  1. 调用微信 API 获取 openid 和 session_key
  2. 根据 openid 查询用户是否存在
  3. 不存在则自动注册（只存 openid，其他字段为空）
  4. 生成 Sa-Token 令牌，返回给前端
  5. 前端存储 token，后续请求携带 token

**领域模型**：
```java
// User 聚合根
public class User {
    private Long id;              // 用户ID（雪花算法）
    private String openId;        // 微信 openid（唯一）
    private String nickname;      // 昵称（可空）
    private String phone;         // 手机号（可空）
    private String gender;        // 性别（可空）
    private Integer age;          // 年龄（可空）
    private String avatarUrl;     // 头像URL（可空）
    private String city;          // 城市（可空）
    private boolean vip;          // 是否会员
    private LocalDateTime vipExpireTime; // 会员到期时间
    
    // 注册新用户
    public static User register(String openId);
    
    // 更新用户信息
    public void updateProfile(String nickname, String phone, ...);
    
    // 更新头像
    public void updateAvatar(String avatarUrl);
    
    // 开通会员
    public void upgradeToVip(LocalDateTime expireTime);
    
    // 检查会员是否有效
    public boolean isVipValid();
}
```

**数据库表**：
```sql
CREATE TABLE `user` (
  `id` BIGINT NOT NULL COMMENT '用户ID',
  `open_id` VARCHAR(64) NOT NULL COMMENT '微信openid',

  `phone` VARCHAR(20) DEFAULT NULL COMMENT '手机号',
  `gender` VARCHAR(10) DEFAULT NULL COMMENT '性别: male/female/unknown',
  `age` INT DEFAULT NULL COMMENT '年龄',
  `avatar_url` VARCHAR(512) DEFAULT NULL COMMENT '头像URL',
  `city` VARCHAR(32) DEFAULT NULL COMMENT '城市',
  `is_vip` TINYINT(1) DEFAULT 0 COMMENT '是否会员',
  `vip_expire_time` DATETIME DEFAULT NULL COMMENT '会员到期时间',
  `is_deleted` TINYINT(1) DEFAULT 0 COMMENT '逻辑删除',

  `updated_at` DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',

```

**接口设计**：
```java

public class AuthController {

// DTO

    @NotBlank String code;

class LoginResponse {
    String token;

    UserDetailResponse userInfo;

```

**验收标准**：
- [ ] 首次登录自动注册，返回 token 和用户信息
- [ ] 再次登录直接返回 token，不创建新用户
- [ ] token 有效期 7 天，可续期
- [ ] 登录失败返回明确错误信息（code 无效、微信 API 调用失败等）

#### 4.2.2 用户信息管理

**功能描述**：
- 查询当前用户信息
- 更新用户资料（昵称、手机号、性别、年龄、城市）
- 上传/更新头像

**技术实现**：
- 头像上传流程：
  1. 前端上传图片到 MinIO/OSS（通过预签名URL或直接上传）
  2. 前端获取图片URL后调用更新头像接口
  3. 后端更新用户表的 avatar_url
  4. 如果用户之前有头像，先删除旧头像（调用 StorageService）
  5. **数据库 + OSS 双清理**，避免存储浪费

**领域服务**：
```java
@Service
public class UserApplicationService {
    
    private final UserRepository userRepository;
    private final StorageService storageService;
    
    // 更新用户资料

                             String gender, Integer age, String city);
    
    // 更新头像
    public User updateAvatar(Long userId, String newAvatarUrl);
}
```

#### 4.2.3 会员体系框架

**功能描述**：
- 会员权益配置（宠物数量上限、OSS 存储空间、AI 检索次数等）
- 会员状态检查
- 会员到期提醒
- 会员升级接口（暂不实现支付，只提供手动开通接口）

**会员权益表**：

| 权益项 | 普通用户 | 会员用户 |
|--------|----------|----------|
| 宠物数量上限 | 2 只 | 不限 |
| OSS 存储空间 | 2 GB | 20 GB |
| AI 语义检索 | 每月 10 次 | 不限 |
| 食品包装 AI 识别 | 每月 5 次 | 每月 50 次 |
| 报告/分享笔记生成 | 每月 3 次 | 每月 10 次 |
| 家庭协同成员 | 不支持 | 多成员 |

**技术实现**：
- 会员限额策略接口（Phase 0 只定义接口，Phase 1 开始实现）

## 五、Phase 1：宠物档案

### 5.1 功能概述

**核心目标**：用户能完整建立并管理宠物档案，这是后续一切数据的挂载点。宠物档案逐渐成长为「宠物数字主页」。

**业务价值**：
- 宠物档案是所有功能的数据基础
- 三视图向量化用于后续素材的个体识别
- 数字主页提供宠物全貌视图，提升用户粘性

### 5.2 详细功能点

#### 5.2.1 宠物创建

**功能描述**：
- 记录宠物基础信息：名称、类型、品种、性别、年龄、绝育状态、到家时间、初始体重
- 上传三张照片：头像 + 正面照 + 侧面照
- 三张照片用 qwen3-vl-embedding 嵌入，存入 Qdrant，用于后续个体识别
- 创建完成后，自动以宠物名称为用户 tags 增加一个标签
- 受会员数量上限约束（普通用户 2 只，会员不限）

**技术实现**：
- 年龄处理：前端选择「几年几个月」，后端外推出生日期，后续自动计算年龄
- 品种选择：猫/狗提供品种列表（数据库预置），也可手动输入
- 三视图向量化流程：
  1. 前端上传三张照片到 OSS，获取 URL
  2. 调用创建宠物接口，传入三张照片 URL
  3. 后端保存宠物信息到数据库
  4. 异步调用 Python 服务的三视图向量化接口
  5. Python 服务调用 qwen3-vl-embedding，生成 1024 维向量
  6. Python 服务将向量存入 Qdrant（collection: fafa_pet_profiles）
  7. 返回向量 ID 列表

**Python 三视图向量化接口**：
```python
# app/api/pets.py
@router.post("/profile-photos")
async def embed_profile_photos(request: PetProfilePhotosRequest):
    """
    宠物三视图向量化
    1. 调用 qwen3-vl-embedding 对三张照片分别生成向量
    2. 存入 Qdrant（collection: fafa_pet_profiles）
    3. 返回向量 ID 列表
    """
    from app.core.dashscope_client import get_multimodal_embedding
    from app.core.qdrant import get_qdrant_client
    
    photos = [
        {"url": request.avatar_url, "view": "avatar"},
        {"url": request.front_url, "view": "front"},
        {"url": request.side_url, "view": "side"},
    ]
    
    message_ids = []
    for photo in photos:
        # 获取向量
        embedding = await get_multimodal_embedding(photo["url"])
        
        # 存入 Qdrant
        point_id = f"{request.pet_id}_{photo['view']}"
        qdrant.upsert(
            collection_name="fafa_pet_profiles",
            points=[{
                "id": point_id,
                "vector": embedding,
                "payload": {
                    "user_id": request.user_id,
                    "pet_id": request.pet_id,
                    "view": photo["view"],
                    "photo_url": photo["url"],
                }
            }]
        )
        message_ids.append(point_id)
    
    return PetProfilePhotosResponse(
        pet_id=request.pet_id,
        vector_count=len(message_ids),
        message_ids=message_ids
    )
```

### 6.1 功能概述

Phase 2 是产品最重要的数据来源，核心设计公理：**任何每日记录 ≤2 次点击完成**。

日常记录系统让用户能够快速记录宠物的日常状态、照护动作和周期测量数据，并通过合理的交互设计降低记录成本，提高记录意愿。

**核心价值**：
- 建立宠物健康数据的时间序列，为后续AI分析、健康预警、报告生成提供数据基础
- 最小化用户操作成本，让95%的平淡日也能轻松完成记录
- 为健康预警引擎提供规则引擎所需的结构化数据
- 与提醒系统、健康管理、AI助手形成数据闭环

---

### 6.2 详细功能点

#### 6.2.1 三类记录（架构设计原则）

| 类别 | 定义 | 例子 | 形态 | 数据模型 |
|------|------|------|------|----------|
| **状态观察** | 它表现如何 | 食欲、精神、饮水程度、便便质量 | 主观量表，一天一格，upsert语义 | daily_status宽表 |
| **照护动作** | 我做了什么 | 喂食、换水、给药、驱虫 | 事件流，几点几分发生 | feeding_record、medication_record等事件表 |
| **周期测量** | 精确数值 | 体重、克数、毫升 | 独立流程 + 温和提醒，绝不进每日打卡 | weight_record、measurement_record |

**设计原则**：
- 三类记录不得混放，避免用户在一个界面面对过多输入项
- 状态观察是每日打卡主流程，必须极简
- 照护动作是事件流，支持一天多次
- 周期测量独立入口，降低每日打卡压力

#### 6.2.2 每日打卡六维度（状态观察）

| 维度 | 形态 | 选项 | 核心价值 | 字段设计 |
|------|------|------|---------|----------|
| 食欲 | 量表 | 很好 / 正常 / 下降 / 拒食 | 几乎所有疾病的共同首发信号；猫拒食>2天有肝脂沉积风险 | appetite: ENUM('excellent', 'normal', 'decreased', 'refused') |
| 精神/活动 | 量表 | 活跃 / 正常 / 低迷 | 措辞必须是「比平时」而非绝对档位 | energy: ENUM('active', 'normal', 'lethargic') |
| 饮水程度 | 量表 | 正常 / 偏多 / 偏少 / 没注意 | 猫多饮多尿=肾病/糖尿病/甲亢早期信号；必须有「没注意」逃生口 | water_intake: ENUM('normal', 'more', 'less', 'not_noticed') |
| 排便 | 量表 | 正常 / 偏软 / 腹泻 / 便秘 / 没看到 | 特权数据（每天铲屎/捡屎一目了然） | defecation: ENUM('normal', 'soft', 'diarrhea', 'constipation', 'not_seen') |
| 呕吐 | 症状开关 | 无（默认）/ 一次 / 多次 | 拒食+呕吐=急症组合信号 | vomiting: ENUM('none', 'once', 'multiple') |
| 排尿 | 症状开关 | 正常 / 异常 / 没看到 | 公猫排尿困难是按小时计的急症 | urination: ENUM('normal', 'abnormal', 'not_seen') |

**附加字段**：
- `appetite_amount`：食欲对应的克数（可选填，decimal(10,2)）
- `water_amount`：饮水对应的毫升数（可选填，decimal(10,2)）
- `notes`：备注文本（varchar(500)，每个维度后必须有备注入口）
- `record_date`：记录日期（date，非datetime，因为是"一天一格"语义）
- `pet_id`：宠物ID（bigint）
- `operator_id`：记录人ID（bigint，为Phase 10家庭协同预留）

#### 6.2.3 物种差异配置

| 宠物类型 | 默认维度 | 维度排序 | 特殊提示 |
|---------|---------|---------|---------|
| 猫 | 食欲、精神、饮水、排便、呕吐、排尿 | 饮水加权提示多饮多尿风险 | 猫砂盆排尿可见，排尿优先级高 |
| 狗 | 食欲、精神、排便、饮水、呕吐 | 排尿降权（狗排尿观察难） | 捡屎是每日特权数据，排便优先级高 |
| 其他 | 复用猫配置 | - | - |

**技术实现**：
- 配置存储在`pet_record_config`表或配置文件中
- 前端根据`pet.type`动态渲染打卡页面
- 后端验证时根据物种检查必填字段

#### 6.2.4 关键交互设计

**「同上次」按钮**：
- 功能：用户可看到上次记录，点击后直接复用上次的所有维度作为本次记录
- 实现：查询该宠物最近一次的`daily_status`记录，回填到表单
- 场景：宠物状态稳定时，大幅降低记录成本

**「今天一切正常」一键完成**：
- 功能：点击后自动填充所有维度为"正常"状态
- 实现：食欲=normal, 精神=normal, 饮水=normal, 排便=normal, 呕吐=none, 排尿=normal
- 场景：95%的日子是平淡的，必须让平淡日成本最低

**漏记不惩罚**：
- 设计原则：漏一天标「未记录」，绝不做愧疚式UI（如连续打卡天数、打卡日历红绿灯）
- 实现：时间轴上未记录的日期显示为灰色占位，但不强调"漏了"

**记录提醒**：
- 配置：用户可按记录项配置每日提醒时间（如每晚8点提醒打卡）
- 实现：接入Phase 3的提醒系统，提醒类型为`daily_record`

**记录检索**：
- 确定性检索：按宠物名称、时间范围、记录类型筛选
- AI自然语言检索：Phase 5 AI助手接入，支持"豆包上个月有几天拒食"

**记录可修改、可删除**：
- upsert语义：同一宠物同一天只有一条daily_status记录，修改即更新
- 逻辑删除：deleted=1，保留审计字段

#### 6.2.5 照护动作记录（事件流）

**喂食记录（feeding_record）**：
- 字段：pet_id, feeding_time（datetime）, food_type（主食/零食/罐头）, amount（g或ml）, food_id（关联Phase 7食品管理卡）, notes, operator_id
- 特点：一天可记录多次，支持精确到分钟
- 交互：首页"快速记录"区有"喂食"入口，点击后弹出轻量表单

**饮水记录**（废弃，并入daily_status）：
- 原water_record表废弃，饮水程度改为每日打卡维度之一
- 如需记录精确毫升数，在daily_status.water_amount字段填写

**用药记录**（medication_record）：
- 字段：pet_id, medication_time, medication_id（关联Phase 6用药管理）, dosage, notes, operator_id
- 来源：Phase 6用药管理模块生成提醒，用户点击"已完成"自动生成用药记录
- 也可手动记录临时用药

#### 6.2.6 周期测量记录

**体重记录（weight_record）**：
- 字段：pet_id, record_date, weight（decimal(10,2)，单位kg）, notes
- 入口：独立入口，不在每日打卡中
- 提醒：系统每月温和提醒一次，用户可自定义周期

**毛发健康程度**：
- 并入自定义事件记录（Phase 7成长档案）

**体型特征**：
- 并入自定义事件记录或宠物档案的profile字段

CREATE TABLE daily_status (

## 七、Phase 3：提醒系统

### 7.1 功能概述

Phase 3 实现完整的提醒系统，覆盖宠物照护的各种周期性任务（疫苗、驱虫、洗澡等），以及用户自定义的任意提醒事项。

**核心价值**：
- 避免遗忘关键照护任务（疫苗过期、驱虫漏做）
- 提醒完成后自动生成事件记录，与时间轴打通
- 支持灵活的周期配置（一次性/每周/每月/每N天等）
- 为Phase 2的每日打卡提供可选提醒能力
- 为Phase 6的用药管理提供提醒基础设施

**设计原则**：
- 提醒系统是基础设施，服务于多个模块
- 完成闭环：提醒 → 完成 → 生成事件记录 → 自动计算下次时间
- 用户可随时暂停、修改、删除提醒

---

### 7.2 详细功能点

#### 7.2.1 提醒类型

| 提醒类型 | 说明 | 是否生成事件记录 | 特殊处理 |
|---------|------|----------------|---------|
| 疫苗 | 狂犬疫苗、三联疫苗等 | 是，归入就医档案时间线 | 需记录疫苗名称、接种医院 |
| 驱虫 | 体内驱虫、体外驱虫 | 是 | 需记录驱虫药品牌 |
| 洗澡 | 定期洗澡 | 是 | 可记录洗澡地点（自己洗/宠物店） |
| 剪指甲 | 定期剪指甲 | 是 | - |
| 体检 | 年度体检 | 是，归入就医档案时间线 | 需记录体检医院 |
| 用药 | 长期用药提醒 | 是，归入用药记录（Phase 6） | 关联medication_id |
| 生日 | 宠物生日 | 否（纯提醒，不生成事件） | 每年循环 |
| 每日打卡 | 提醒用户打卡 | 否（提醒打卡动作，而非事件本身） | 用户可配置提醒时间 |
| 自定义提醒 | 用户自定义任意事项 | 是（用户可选） | 用户填写提醒内容 |

#### 7.2.2 周期支持

| 周期类型 | 说明 | 示例 | 实现方式 |
|---------|------|------|---------|
| 一次性 | 只提醒一次，不循环 | 明天去宠物店洗澡 | next_remind_time设置一次，completed后不再计算 |
| 每N天 | 每隔N天提醒一次 | 每3天喂一次化毛膏 | interval_type='days', interval_value=3 |
| 每周 | 每周固定星期几 | 每周日剪指甲 | interval_type='weekly', interval_value=周日 |
| 每月 | 每月固定日期 | 每月1号驱虫 | interval_type='monthly', interval_value=1 |
| 每N个月 | 每隔N个月 | 每3个月体检 | interval_type='months', interval_value=3 |
| 每年 | 每年固定日期 | 每年8月21日（生日） | interval_type='yearly', interval_value='08-21' |

**计算逻辑**：
- 完成提醒后，根据interval_type和interval_value计算next_remind_time
- 一次性提醒completed后，状态改为'finished'，不再触发

#### 7.2.3 完成闭环

**完成流程**：
1. 用户点击"已完成"
2. 系统记录完成时间（completion_time）
3. 根据提醒类型生成对应的事件记录：
   - 疫苗/驱虫/洗澡/剪指甲 → event_record表
   - 用药 → medication_record表（Phase 6）
4. 如果是周期性提醒，自动计算下次提醒时间
5. 提醒状态从'pending'改为'completed'（本次完成），同时生成新的提醒记录

**完成记录字段**：
- 完成时间：实际完成时间（可能晚于提醒时间）
- 备注：用户可填写完成时的备注（如驱虫用的什么药）
- 照片：可选上传照片（如疫苗本照片）

#### 7.2.4 提醒状态机

```
状态流转：
pending（待完成） → completed（已完成） → [生成新的pending]
                  ↓
                finished（终止，仅一次性提醒）
                  
paused（已暂停） ← → pending（恢复）
```

**状态说明**：
- `pending`：待完成，会在next_remind_time触发推送
- `completed`：已完成（历史记录）
- `finished`：已终止（一次性提醒完成后）
- `paused`：已暂停（用户主动暂停）

#### 7.2.5 提醒推送策略

**推送时机**：
- 提前1天推送（09:00）：重要提醒（疫苗、体检、驱虫）
- 当天推送（用户设定时间）：每日打卡、用药
- 过期未完成提醒：每天提醒一次，直到完成

**推送渠道**：
- 小程序服务通知（订阅消息）
- 首页"今日提醒"区展示

**推送内容**：
- 标题：提醒类型 + 宠物名称
- 内容：提醒事项 + 距离目标日期
- 示例："豆包明天该驱虫了"

// domain/service/ReminderScheduleService.java
public class ReminderScheduleService {
    
    public LocalDateTime calculateNextRemindTime(
        LocalDateTime currentTime,
        IntervalType intervalType,
        Integer intervalValue
    ) {
        return switch (intervalType) {
            case ONCE -> null;  // 一次性提醒不计算下次
            case DAYS -> currentTime.plusDays(intervalValue);
            case WEEKLY -> currentTime.plusWeeks(1);  // intervalValue存储星期几
            case MONTHLY -> currentTime.plusMonths(1).withDayOfMonth(intervalValue);
            case MONTHS -> currentTime.plusMonths(intervalValue);
            case YEARLY -> currentTime.plusYears(1);
        };
    }
    
    public boolean shouldSendReminder(Reminder reminder, LocalDateTime now) {
        // 提前1天提醒逻辑
        return reminder.getNextRemindTime().minusDays(1).isBefore(now);
    }
}

### 7.7 定时任务设计

**ReminderPushScheduler**（提醒推送定时任务）：

```java
@Component
public class ReminderPushScheduler {
    
    @Autowired
    private ReminderRepository reminderRepository;
    
    @Autowired
    private ReminderPushService reminderPushService;
    
    // 每小时扫描一次，找出需要推送的提醒
    @Scheduled(cron = "0 0 * * * ?")
    public void scanAndPushReminders() {
        LocalDateTime now = LocalDateTime.now();
        LocalDateTime tomorrow = now.plusDays(1);
        
        // 查找下次提醒时间在明天的提醒（提前1天推送）
        List<Reminder> upcomingReminders = reminderRepository
            .findPendingByNextRemindTimeBetween(tomorrow.withHour(0), tomorrow.withHour(23));
        
        for (Reminder reminder : upcomingReminders) {
            reminderPushService.sendReminder(reminder);
        }
        
        // 查找过期未完成的提醒
        List<Reminder> overdueReminders = reminderRepository
            .findPendingByNextRemindTimeBefore(now);
        
        for (Reminder reminder : overdueReminders) {
            if (reminder.isOverdue()) {
                reminderPushService.sendOverdueReminder(reminder);
            }
        }
    }
}

        // 1. 记录完成信息
        reminder.complete(request.getCompletionTime(), request.getNotes());
        
        // 2. 生成事件记录（除了生日和每日打卡）
        if (shouldGenerateEventRecord(reminder.getType())) {
            EventRecord event = EventRecord.fromReminder(
                reminder,
                request.getCompletionTime(),
                request.getNotes(),
                request.getPhotoUrls()
            );
            eventRecordRepository.save(event);
        }
        
        // 3. 保存完成历史
        ReminderCompletionHistory history = new ReminderCompletionHistory(
            reminderId,
            reminder.getPetId(),
            request.getCompletionTime(),
            request.getNotes(),
            request.getPhotoUrls(),
            event != null ? event.getId() : null
        );
        completionHistoryRepository.save(history);
        
        // 4. 计算下次提醒时间（如果是周期性提醒）
        if (reminder.getIntervalType() != IntervalType.ONCE) {
            reminder.calculateNextRemindTime();
            reminderRepository.save(reminder);
        } else {
            reminder.setStatus(ReminderStatus.FINISHED);
            reminderRepository.save(reminder);
        }
    }
    
    private boolean shouldGenerateEventRecord(ReminderType type) {
        return type != ReminderType.BIRTHDAY && type != ReminderType.DAILY_RECORD;
    }
}
```
