## 一、现状基线（Phase 0 已完成）

脚手架已落地并验证（`mvn compile` / `py_compile` / `import main` 均通过）：

**fafa-java**
- 认证全链路：微信登录（自动注册）/ 用户信息 / 登出 / 登录检查
- 统一响应 `Result` + 错误码分段 + 全局异常处理
- TraceId 过滤器（MDC + 响应头 + 跨服务透传）
- Sa-Token 登录拦截 + 内部令牌拦截（`/api/callback/**`）
- Flyway V1.0：`user`、`pet` 表
- MinIO 存储策略（条件注册，见第二节）
- MyBatis-Plus 分页 + 审计字段自动填充
- AI 任务投递策略链：MQ 优先、HTTP 兜底、失败自动降级（本次重构）

**fafa-python**
- FastAPI 骨架 + traceId 中间件 + loguru（按天滚动 30 天）
- 模型路由工厂（`Purpose` -> 模型名，换模型只改配置）
- Qdrant 双集合（`fafa_media` / `fafa_pet_profiles`）+ uuid5 确定性 point id
- photo / chat 接口骨架（501 + TODO 标注）
- MQ 消费者骨架（仅 Linux，独立进程启动，main.py 不导入）

**未实现**：宠物 CRUD 之后的所有业务模块、AI 真实链路（对应原技术文档 M4/M5 的业务部分）。

## 二、环境与条件注册矩阵

| 能力 | dev（Windows 本机） | test（Linux） | prod | 实现机制 |
|------|--------------------|--------------|------|----------|
| 对象存储 | MinIO | MinIO | OSS | `StorageService` 策略 + `@ConditionalOnProperty(fafa.storage.type)`，已实现 |
| AI 任务投递 | HTTP 直推 | RocketMQ | RocketMQ | `AiTaskDispatcher` 策略链（MQ 优先、HTTP 兜底），已实现 |
| MQ 消费者 | 不启用（Windows 客户端不可用） | 独立进程启用 | 独立进程启用 | `python -m app.consumer.photo_consumer`，与 main.py 解耦 |
| 接口文档 Knife4j | 开 | 开 | 关 | spring profile 控制 |
| Druid 监控页 | 开 | 开 | 关 | profile 控制 |

**两条硬规则**：

1. 环境差异只允许通过配置（profile / 环境变量）+ 条件注册切换，**禁止在业务代码里写 `if (env == dev)` 之类的平台判断**。
2. 新增环境相关能力时，一律先抽策略接口再做条件注册，选择逻辑收敛在工厂/注册表，新增实现不改调用方。

## 三、设计模式应用规范（全项目统一）

| 场景 | 模式 | 落地位置 | 状态 |
|------|------|----------|------|
| 对象存储 MinIO / OSS | 策略 + 条件注册 | `infrastructure/oss/StorageService` | 已实现 |
| AI 任务投递 MQ / HTTP | 策略链 + 工厂 | `infrastructure/dispatch/AiTaskDispatcher` | 已实现 |
| 模型选择（轻对话/深推理/视觉/嵌入） | 工厂 | `app/core/llm.py`（`Purpose` 枚举） | 已实现 |
| 回调处理（按任务类型分发） | 策略注册表 | `CallbackHandlerRegistry`（Phase 4） | 计划 |
| 健康预警规则 | 策略 + 注册表 | `HealthRule` 接口 + 规则集（Phase 6） | 计划 |

约定：策略 bean 无状态；策略间不允许互相调用；工厂返回「第一个可用且成功」的结果。

## 五、各阶段详细计划

### Phase 1 宠物档案

**目标**：用户能完整建立并管理宠物档案，这是后续一切数据的挂载点。

**数据库**：无新增（V1.0 已建 `pet` 表，含三视图列与 `sort_order`）。

**Java 交付**：
- `Pet` 领域模型：`register` / `updateProfile` / `updateWeight`（体重大于 0 校验）/ 绝育状态等行为
- PetRepository 四件套（DO / Mapper / Converter / RepositoryImpl），逻辑删除
- `PetApplicationService` + `PetController`：
  - 创建 / 更新 / 删除（软删）/ 列表（按 `sort_order`）/ 手动排序
  - 头像上传、三视图上传（走 `StorageService`，本阶段只存 URL）
- 宠物数量上限：普通 3 只 / 会员 8 只（本阶段写死常量，Phase 7 替换为 `MemberQuotaPolicy` 策略）

**接口清单**：

```
POST   /api/pets                       创建
PUT    /api/pets/{id}                  更新
GET    /api/pets                       列表
DELETE /api/pets/{id}                  删除（软删）
PUT    /api/pets/sort                  排序
POST   /api/pets/{id}/avatar           头像上传
POST   /api/pets/{id}/profile-photos   三视图上传
```

**Python**：无。

**验收标准**：
- Knife4j 完成全流程 CRUD；非会员创建第 4 只被拦截（`PET_LIMIT_EXCEEDED`）
- 删除后列表不可见，库中 `is_deleted = 1`
- 三视图 URL 正确落库并回显

**小程序**：宠物列表页 / 新建编辑页 / 三视图上传引导。

---

### Phase 2 日常记录核心（每日状态打卡）

**目标**：落地「三类数据不混放」的新记录体系，形成时间轴与趋势数据。

**数据库** `V2.0__daily_records.sql`：

```sql
daily_status      -- 一天一条，唯一键 (pet_id, record_date)
                  -- appetite/energy/water/stool/urination: VARCHAR(16) 档位
                  -- vomit: TINYINT 症状开关；note: VARCHAR(512)；source: 记录来源
feeding_record    -- degree(程度) + food_name + amount(可空) + unit + fed_at
weight_record     -- weight + weighed_at（pet.weight 冗余最新值）
```

**Java 交付**：
- `DailyStatusApplicationService`：
  - 当日打卡 upsert（重复提交覆盖，一天一条）
  - 「一键正常」接口（95% 平淡日子的最短路径）
  - 按日区间查询（时间轴数据源）、连续记录天数统计
- 喂食：CRUD + 程度分布统计
- 体重：记录 + 趋势接口（近 N 次变化率），记录后同步 `pet.weight`
- 数据校验：档位枚举值白名单校验

**接口清单**：

```
GET  /api/daily-status                    当日回显
PUT  /api/daily-status                    upsert 打卡
POST /api/daily-status/all-normal         一键正常
GET  /api/daily-status/range              日区间查询（时间轴）
GET  /api/daily-status/streak             连续记录天数
POST /api/feedings                        喂食记录
GET  /api/feedings/statistics             喂食统计
POST /api/weights                         体重记录
GET  /api/weights/trend                   体重趋势
```

**Python**：无。

**验收标准**：
- 打卡 → 二次修改 → 查询返回最新值（upsert 语义正确）
- 「一键正常」后当日记录存在且各档位均为 `normal`
- 体重记录后 `pet.weight` 同步，趋势接口返回变化率

**小程序**：打卡页（三量表 + 两开关 + 一键正常 + 备注）、时间轴页、体重曲线页。

### Phase 3 提醒系统

**目标**：提醒可创建、可触发、可完成，成为用药管理与健康预警的执行通道。

**数据库** `V3.0__reminder.sql`：

```sql
reminder  -- pet_id, type(medication/vaccine/deworm/followup/custom),
          -- title, remind_time, repeat_rule(once/daily/weekly/monthly),
          -- status(pending/done/cancelled), next_fire_at
```

**Java 交付**：
- Reminder CRUD + complete / cancel（完成生成日志，周期性提醒滚动 `next_fire_at`）
- `ReminderScheduledTask`：每分钟扫描 `next_fire_at <= now`，生成到期列表
- 角标统计接口（首页小红点）
- `PushChannel` 策略接口：本期只实现「站内」通道；微信订阅消息受资质与频次限制，仅留扩展点，不承诺

**验收标准**：
- 创建每日提醒 → `next_fire_at` 正确滚动；complete 后状态流转且周期性提醒生成下次触发时间
- 到期提醒出现在列表与角标统计中

**小程序**：提醒列表 / 新建页 / 首页角标。

### Phase 4 素材库与 AI 摄入（差异化核心）

**目标**：打通「上传 → AI 理解 → 向量化 → 语义搜索」全链路；这是 FaFa 与竞品拉开差距的第一条护城河。

**数据库** `V4.0__media.sql`：

```sql
photo     -- user_id, pet_id(可空), object_key, media_type(photo/video),
          -- taken_at, ai_description, recognized_pet_id, tags(JSON),
          -- analysis_status(0待处理/1完成/2失败), error_msg
user_tag  -- user_id, name, use_count（标签管理，替代旧 petId 归属模型）
```

**Java 交付**：
- 上传（批量/视频）：`StorageService` → 落库 `status=0` → `AiTaskDispatcher.dispatch`
  - Windows 开发自动走 HTTP 直推，Linux 走 MQ，业务代码同一条
- 回调处理：`CallbackController` + `CallbackHandlerRegistry`（按任务类型的策略分发），photo-analysis handler 更新 `ai_description / recognized_pet_id / analysis_status`
- user_tag CRUD（热门排序 `use_count`）
- 搜索接口：转发 Python `/api/photos/search`
- 删除照片：软删 + `StorageService.delete` + 通知 Python 删向量
- 宠物三视图上传后触发 `PythonAiClient.uploadPetProfilePhotos`（向量化）
- 宠物删除时尽力清理 `fafa_pet_profiles` 向量

**Python 交付**（用真实实现替换 501 骨架）：
- `photo_service`：qwen-vl 视觉理解（描述 + 拍摄场景）→ 多模态嵌入 → Qdrant upsert（payload 含 `user_id/pet_id/tags/taken_at/media_type`）→ 宠物识别（检索 `fafa_pet_profiles`）→ 回调 Java
- `/api/pets/profile-photos`：三视图嵌入入 `fafa_pet_profiles`
- `/api/pets/{petId}/profile-vectors`：向量清理
- `/api/photos/search`：文本嵌入 + 向量检索 + payload 过滤（用户隔离/标签/时间）
- MQ 消费者：**与 HTTP 直推复用 `photo_service` 同一入口**（防止两条链路契约漂移），Linux 环境联调

**验收标准**（核心链路，Windows dev 环境即可验证）：
- 上传照片 → `photo.analysis_status=1`，Qdrant `fafa_media` 出现对应点（uuid5 point id）
- 「搜索：猫在窗台上」能召回该照片（`user_id` 隔离正确）
- 上传无 petId 照片，若三视图库有匹配 → `recognized_pet_id` 回写
- 删除照片后 Qdrant 对应点消失
- 同一 traceId 在 Java 与 Python 日志中可串联

**小程序**：相册页 / 上传打标流程 / 自然语言搜索入口。

### Phase 5 AI 对话 Agent

**目标**：AI 从「独立聊天页」变成贯穿数据的智能层——回答基于这只宠物的真实记录。

**数据库** `V5.0__chat.sql`：

```sql
chat_session  -- user_id, pet_id, title, last_message_at
chat_message  -- session_id, role(user/assistant/tool), content
```

**Java 交付**：
- 会话列表 / 历史消息 / 删除会话
- `/api/chat/send` 转发 Python（SSE 流式透传）

**Python 交付**：
- LangGraph 状态图：意图分类（闲聊/查记录/统计分析/找照片/健康建议）→ 上下文构建（工具调用 Java 只读接口：daily-status / statistics / photo-search）→ 回答生成
- 模型路由：轻意图走轻量模型，复杂分析走深度模型（工厂已就位）
- 会话历史注入（近 N 轮 + 滚动摘要）
- 流式 SSE 输出

**验收标准**：
- 「我家猫最近一周食欲怎么样」→ Agent 调用记录工具 → 回答包含真实数据
- 「找一张它睡觉的照片」→ 返回照片列表
- 多轮对话上下文正确；同一问题换宠物结果不同（数据隔离）

**小程序**：AI 对话页（流式渲染、照片卡片消息）。

### Phase 6 健康管理

**目标**：把记录数据升级为健康价值——就医档案、用药闭环、规则预警。

**数据库** `V6.0__health.sql`：

```sql
medical_visit  -- pet_id, visit_date, hospital, department, doctor,
                -- chief_complaint, diagnosis, treatment, cost, attachments(JSON)
medication     -- pet_id, name, dosage, frequency, start_date, end_date, reminder_id
medication_log -- medication_id, taken_at
health_alert   -- pet_id, rule_code, level(yellow/red), message, status(active/dismissed)
```

**Java 交付**：
- 就医档案 CRUD + 附件（复用 StorageService）
- 用药管理：CRUD + 绑定 Phase 3 提醒 + 服药打卡
- **预警规则引擎**：`HealthRule` 策略接口（`evaluate(context) -> Optional<Alert>`）+ 规则注册表；每日打卡 upsert 后触发评估
  - 规则集 v1（阈值集中 `HealthRuleConstants`，待兽医资料核验后调整）：
    - 拒食 + 呕吐 → 红（急症信号）
    - 连续 2 天食欲下降 + 精神低迷 → 黄
    - 猫饮水偏多 ≥ 3 天 → 黄（提示排查肾/血糖）
    - 排尿异常 → 红（公猫尿道阻塞风险）
- 就诊摘要导出：`ReportGenerator` 策略，调 Python 生成近 7 天结构化病史

**验收标准**：
- 构造「拒食 + 呕吐」打卡 → `health_alert` 产生 red 记录，列表可见
- 用药绑定提醒后到期出现在提醒列表，打卡记录可查
- 就诊摘要返回含症状时间线与基线对比的文本

**小程序**：健康管理页 / 就医档案表单 / 用药计划 / 预警中心。

### Phase 8 家庭协同与上线

**目标**：多人共管宠物 + 生产上线。**这是全项目最大的一次架构变更，必须放最后**。

**数据库** `V8.0__family.sql`：

```sql
family         -- owner_user_id
family_member  -- family_id, user_id, role(owner/member), invited_at
```

**Java 交付**：
- 家庭创建（创建首只宠物时自动建立）、成员邀请（小程序码）、成员管理
- **数据归属迁移**：宠物/记录/素材查询从 `user_id` 维度迁移为 `family_id` 维度——独立迁移脚本 + 双写过渡期，逐模块切换
- 上线清单：
  - prod profile 全检（文档关闭 / Druid 关闭 / OSS 策略切换 `fafa.storage.type=oss`）
  - MQ 链路在 test 环境回归（Windows 只验证过 HTTP 直推）
  - 虚拟线程下连接池水位压测
  - 日志落盘检查、数据库/Qdrant 备份策略
  - `FAFA_INTERNAL_TOKEN` 等密钥全部走环境变量，确认无硬编码

**验收标准**：
- 两个微信号共管同一宠物，双方记录互相可见
- 单方退出家庭不丢数据，所有权归属 owner
- prod 环境冒烟全通过

## 六、横切规范（每个 Phase 的 Definition of Done）

1. **数据库**：变更一律 Flyway（版本号 `V{phase}.{seq}__desc.sql`），禁止手工改库
2. **接口**：REST + `/api` 前缀（auth 例外）；统一 `Result` 包装；错误码按 `ErrorCode` 分段新增；Knife4j 注解（`@Tag`/`@Operation`）与 DTO 校验注解齐全
3. **验证**：`mvn compile` + 测试通过；Python `py_compile` + `import main` 通过
4. **契约**：涉及 Java↔Python 的变更，双侧同步修改，接口注释中的契约描述同步更新
5. **日志**：一次请求的 traceId 在两个服务日志中均可检索
6. **模式**：新增环境相关能力按第三节规范先抽策略；新增业务规则优先策略/注册表形态
7. **文档**：阶段结束更新本文档勾选状态，新增接口补充到本文档对应 Phase
