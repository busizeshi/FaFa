# 数据库设计

## 一、数据库设计原则

1. **以宠物为核心**：所有记录表都关联 `pet_id`
2. **软删除**：重要数据使用 `deleted_at` 标记删除，不物理删除
3. **时间戳**：所有表包含 `created_at` 和 `updated_at`
4. **合理冗余**：适当冗余提升查询性能（如宠物名称）
5. **JSON 字段**：灵活存储扩展数据（如照片标签、AI 分析结果）

## 三、索引优化说明

### 3.1 核心查询场景与索引

| 查询场景 | 表 | 索引 | 理由 |
|---------|-----|------|------|
| 获取用户的所有宠物 | pets | `idx_user_id` | 高频查询 |
| 获取宠物的喂食记录 | feeding_records | `idx_pet_time` (pet_id, feed_time) | 复合索引，支持时间范围查询 |
| 获取宠物的体重趋势 | weight_records | `idx_pet_date` (pet_id, record_date) | 支持日期范围查询 |
| 照片按时间排序 | photos | `idx_pet_created` (pet_id, created_at) | 时间倒序常用 |
| 查询待提醒的事项 | reminders | `idx_status_next` (status, next_date) | 定时任务扫描 |
| AI 对话历史 | ai_conversations | `idx_session` (session_id, created_at) | 会话连续性查询 |

### 3.2 避免过度索引

- 小表（如 system_configs）不需要过多索引
- 写入频繁的表（如 feeding_records）索引不宜过多
- JSON 字段不建索引（MySQL 8.0+ 可对 JSON 字段创建虚拟列索引，但暂不需要）

## 四、数据冗余设计

### 4.1 合理冗余字段

**feeding_records.food_name**
- 冗余 `foods.name`
- 原因：避免关联查询，食品可能被删除但记录需保留

**pets.current_weight**
- 冗余最新的 `weight_records.weight`
- 原因：宠物主页高频展示，避免每次查询聚合

**photos.description, tags**
- AI 分析结果
- 原因：搜索和展示时高频使用，避免重复调用 AI

### 4.2 不冗余的设计

**不在 feeding_records 冗余 pet_name**
- 原因：宠物名称可能修改，冗余会导致不一致
- 解决：查询时 JOIN pets 表

## 五、JSON 字段使用说明

### 5.1 适合使用 JSON 的场景

**events.tags**
```json
["健康", "异常", "就医"]
```
- 原因：标签数量不固定，不适合建独立表

**events.photos**
```json
["https://cdn.example.com/photo1.jpg", "https://cdn.example.com/photo2.jpg"]
```
- 原因：照片数量少且不需要复杂查询

**photos.ai_analysis**
```json
{
  "scene": "阳台",
  "behavior": "睡觉",
  "objects": ["蓝色猫窝", "阳光"],
  "weather": "晴天",
  "time_of_day": "下午"
}
```
- 原因：结构化 AI 分析结果，便于前端展示和后续 AI 理解

**feeding_plans.schedule**
```json
[
  {"time": "07:30", "amount": 25},
  {"time": "13:00", "amount": 10},
  {"time": "19:00", "amount": 25},
  {"time": "22:30", "amount": 10}
]
```
- 原因：每日时间表固定结构，不需要独立表

### 5.2 不适合使用 JSON 的场景

**❌ 不要用 JSON 存储需要查询的核心字段**
- 如宠物 ID、用户 ID、日期等
- 原因：无法建立高效索引

**❌ 不要用 JSON 存储大量数据**
- 如完整的报告内容（reports.content 是例外，因为报告查询频率低且需要完整结构）

## 九、数据隐私与安全

### 9.1 敏感数据加密

**用户手机号**
- 存储：AES 加密
- 展示：脱敏显示（138****0000）

**微信 openid**
- 不对外暴露
- API 返回时过滤

### 9.2 数据访问控制

**用户数据隔离**
- 所有查询必须包含 `user_id` 条件
- 防止跨用户数据泄露

**软删除**
- 重要数据（pets, photos, diaries）使用 `deleted_at`
- 物理删除仅在用户注销账号时执行

### 9.3 审计日志

```sql
CREATE TABLE `audit_logs` (
  `id` BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  `user_id` BIGINT UNSIGNED DEFAULT NULL,
  `action` VARCHAR(64) NOT NULL COMMENT '操作：create, update, delete',
  `resource_type` VARCHAR(32) NOT NULL COMMENT '资源类型：pet, photo, record',
  `resource_id` BIGINT UNSIGNED NOT NULL,
  `ip_address` VARCHAR(64) DEFAULT NULL,
  `user_agent` VARCHAR(255) DEFAULT NULL,
  `created_at` TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  INDEX `idx_user_created` (`user_id`, `created_at`),
  INDEX `idx_resource` (`resource_type`, `resource_id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci COMMENT='审计日志表';
```
