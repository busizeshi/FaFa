## 三、消息流转详细步骤

### 步骤 1：Java 发送消息

```java
// Java 代码
PhotoAnalysisMessage message = PhotoAnalysisMessage.builder()
    .photoId(1001L)
    .petId(2001L)
    .userId(3001L)
    .url("http://192.168.1.14:9000/fafa/photo.jpg")
    .build();

// 序列化成 JSON
String json = objectMapper.writeValueAsString(message);
// 结果：{"photoId":1001,"petId":2001,"userId":3001,"url":"..."}

// 发送到 RocketMQ
rocketMQTemplate.syncSend("photo-analysis", json);
```

### 步骤 2：RocketMQ 存储消息

```
RocketMQ Broker 存储结构：

CommitLog (顺序写入)
├─ Message 1 [Offset: 0]
├─ Message 2 [Offset: 1024]
└─ Message 3 [Offset: 2048]  ← 新消息

ConsumeQueue (索引)
Topic: photo-analysis
├─ Queue 0
│   ├─ [Offset: 0]  → CommitLog Offset: 0
│   └─ [Offset: 1]  → CommitLog Offset: 2048  ← 新消息索引
├─ Queue 1
└─ Queue 2
```

### 步骤 3：Python 接收消息

```python
# Python 代码
def _callback(self, msg):
    # 1. 获取字节数组
    body_bytes = msg.body
    # body_bytes = b'{"photoId":1001,...}'
    
    # 2. 解码成字符串
    body_str = body_bytes.decode('utf-8')
    # body_str = '{"photoId":1001,...}'
    
    # 3. 解析 JSON
    data = json.loads(body_str)
    # data = {"photoId": 1001, "petId": 2001, ...}
    
    return ConsumeStatus.CONSUME_SUCCESS
```

## 四、消费状态返回流程

```
┌─────────────────────────────────────────────────────┐
│ Python Consumer                                      │
│                                                      │
│  def _callback(self, msg):                          │
│      try:                                            │
│          # 处理消息                                  │
│          process_message(msg)                       │
│          return ConsumeStatus.CONSUME_SUCCESS       │
│      except Exception:                               │
│          return ConsumeStatus.RECONSUME_LATER       │
└──────────────────┬──────────────────────────────────┘
                   │
                   ├──────── 情况 1：返回 CONSUME_SUCCESS
                   │
                   ▼
┌─────────────────────────────────────────────────────┐
│ RocketMQ Broker                                      │
│                                                      │
│  ✅ 标记消息为"已消费"                               │
│  ✅ 从队列中删除消息                                 │
│  ✅ Consumer Offset +1                              │
│                                                      │
│  结果：消息处理完成，不会再次投递                    │
└─────────────────────────────────────────────────────┘

                   │
                   └──────── 情况 2：返回 RECONSUME_LATER
                   │
                   ▼
┌─────────────────────────────────────────────────────┐
│ RocketMQ Broker                                      │
│                                                      │
│  ⏰ 等待一段时间（默认 10 秒）                       │
│  🔄 重新投递消息给 Consumer                         │
│  📊 重试次数 +1                                     │
│                                                      │
│  如果重试次数 > 16 次：                              │
│    → 进入死信队列 (DLQ)                             │
│    → 需要人工处理                                   │
└─────────────────────────────────────────────────────┘
```

## 五、并发消费模型

### 单消费者模式

```
RocketMQ Broker
    Queue 0: [M1, M2, M3]
    Queue 1: [M4, M5, M6]
    Queue 2: [M7, M8, M9]
         │
         │ 所有消息推送给唯一的消费者
         ▼
    Consumer-1
    ├─ 线程 1: 处理 M1, M4, M7
    ├─ 线程 2: 处理 M2, M5, M8
    └─ 线程 3: 处理 M3, M6, M9
```

### 多消费者模式（推荐）

```
RocketMQ Broker
    Queue 0: [M1, M2, M3] ─────┐
    Queue 1: [M4, M5, M6] ─────┼───> Consumer-1
    Queue 2: [M7, M8, M9] ─────┘     处理 Queue 0, 1
    Queue 3: [M10, M11]   ─────┐
    Queue 4: [M12, M13]   ─────┴───> Consumer-2
                                     处理 Queue 2, 3, 4

优点：
✅ 负载均衡：消息自动分配
✅ 高可用：一个消费者挂了，另一个继续工作
✅ 水平扩展：增加消费者提高处理能力
```

## 六、消息重试机制

```
第 1 次投递
    │
    ▼
Consumer 处理
    │
    ├─ 成功 → 结束
    │
    └─ 失败
        │
        ▼
    等待 10 秒
        │
        ▼
第 2 次投递
    │
    ▼
Consumer 处理
    │
    ├─ 成功 → 结束
    │
    └─ 失败
        │
        ▼
    等待 30 秒
        │
        ▼
第 3 次投递
    │
    ... (重复最多 16 次)
    │
    ▼
全部失败
    │
    ▼
进入死信队列 (DLQ)
Topic: %DLQ%photo-analysis-consumer-group

死信队列处理：
1. 人工查看日志，找出失败原因
2. 修复问题后，手动重新投递
3. 或者放弃处理，记录到错误日志
```

## 七、对比：同步调用 vs 消息队列

### 方式 1：同步 HTTP 调用（不推荐）

```
用户上传照片
    ↓
Java 保存照片 (500ms)
    ↓
Java 调用 Python HTTP 接口 (同步等待)
    ↓
Python AI 分析 (10秒)
    ↓
Java 返回结果
    ↓
用户收到"上传成功" (总耗时：10.5秒 ❌)

问题：
❌ 用户等待时间长
❌ Java 线程被阻塞
❌ Python 服务挂了，Java 请求失败
❌ 并发量大时，系统容易崩溃
```

### 方式 2：消息队列（推荐）

```
用户上传照片
    ↓
Java 保存照片 (500ms)
    ↓
Java 发送 MQ 消息 (10ms)
    ↓
Java 返回结果
    ↓
用户收到"上传成功" (总耗时：510ms ✅)
    ↓
────────────────────────────────
Python 后台异步分析 (10秒)
    ↓
分析完成，更新数据库

优点：
✅ 用户体验好（只等 0.5 秒）
✅ Java 线程不阻塞
✅ Python 服务挂了，消息不丢失
✅ 可以水平扩展，提高并发
✅ 削峰填谷，平滑处理高峰流量
```

## 八、总结

### 核心原理
```
生产者 → [Topic/Queue] → 消费者

同步：生产者等消费者处理完
异步：生产者发完就走，消费者慢慢处理
```

### 适用场景
```
✅ 适合用消息队列：
   - 耗时操作（AI 分析、视频转码）
   - 异步通知（发送邮件、推送消息）
   - 解耦服务（订单系统 → 库存系统）
   - 削峰填谷（秒杀活动、抢票系统）

❌ 不适合用消息队列：
   - 实时查询（查看用户信息）
   - 强一致性（转账操作）
   - 简单操作（获取配置）
```

### 记住这张图
```
快递员（Java）把包裹（消息）放到快递站（RocketMQ）
收件人（Python）随时去取包裹
快递员不用等收件人在不在家
```
